# SignalHub 架构设计

跨平台桌面悬浮状态指示器。优先适配 AI 智能体，但不绑定智能体——任何程序都能通过统一的本地 API 上报状态。

- 框架：Tauri 2（Rust 后端 + React/TypeScript 前端）
- 平台：macOS / Windows / Linux (X11)
- 参考项目：[guan-ops/Agent-Signal-Bar](https://github.com/guan-ops/Agent-Signal-Bar)（原生 macOS/Swift，本项目是其跨平台重实现）

---

## 1. 核心判断

三条贯穿全文的设计决策，先说清楚：

1. **上报通道 = 本地 HTTP + 瘦客户端 CLI。** 不采用 Agent-Signal-Bar 的共享 JSON 文件方案。HTTP 让任何语言一行 `curl` 就能接入，可即时调试、有应答、且天然只允许单一写者，从而彻底消除多写者竞态。
2. **优先级保护实现在「聚合层」，不在「会话层」。** 会话内后写覆盖 + 跨会话取 max + TTL 兜底。见 §3.2——这是最容易设计错的地方。
3. **CLI 内置 `signalhub hook <agent>` 子命令**，直接消费智能体 hook 的 stdin JSON。这一个设计消掉了全部 shell 脚本和 `jq` 依赖，安装 hook 退化成「同一行命令注册到每个事件」。

## 2. 整体架构

```
┌──────────────────────────── 外部上报方 ────────────────────────────┐
│  Claude Code hooks    Codex hooks    Cursor hooks    CI / 脚本      │
└───────────────────────────┬────────────────────────────────────────┘
                            │ ① CLI（或直接 curl）
                            ▼
        ┌────────────────────────────────────────────────┐
        │  signalhub CLI (Rust, 无 Tauri 依赖)            │
        │   普通模式: signalhub working --session build-1 │
        │   hook 模式: signalhub hook claude-code ← stdin │
        │   → POST http://127.0.0.1:<port>/v1/state       │
        └────────────────────┬───────────────────────────┘
                             ▼  ② HTTP (127.0.0.1, Bearer token)
┌──────────────────────────── Tauri 进程 ────────────────────────────┐
│  axum Router (/v1/*)                                                │
│         │ ③ report() / clear() / set_paused()                       │
│         ▼                                                           │
│  SignalStore  Arc<Mutex<Store>>        ← 唯一真值来源               │
│    ├─ sessions: HashMap<SessionId, Session>                         │
│    ├─ paused: bool                                                  │
│    └─ aggregate() = max_priority(sessions)                          │
│         │                                                           │
│   ④ TTL sweep (250ms tick)        ⑤ emit_to("main", "signalhub://state")
│         │                                     │                     │
│  ┌──────┴──────┐                    ┌─────────┴──────────┐          │
│  │ Tray 图标    │                    │ 悬浮窗 Webview      │          │
│  │ 右键菜单     │                    │ (React + CSS 动画)   │          │
│  └─────────────┘                    └────────────────────┘          │
│  全局快捷键 → 穿透模式切换   设置窗 (独立 webview)                    │
└────────────────────────────────────────────────────────────────────┘
```

**单一写者原则。** 所有状态变更都必须经过 `Store` 的一个互斥锁。前端和托盘都是纯消费者，从不写状态。这是选择 HTTP 而非文件方案的根本原因——文件方案允许多个进程并发写入，必须自己实现原子写和锁文件，而 HTTP 服务端天然把写操作串行化了。

## 3. 状态模型与聚合

### 3.1 Signal 枚举

| 状态 | 优先级 | 静默超时 | 视觉（颜色 / 节奏） | 含义 |
|---|---|---|---|---|
| `error` | 50 | 300s | 红 `#d0342c`、频闪 340ms（`steps` 硬切） | 出错/阻塞 |
| `permission` | 40 | 600s | 红、平滑闪 900ms | 需要授权/确认 |
| `attention` | 30 | 300s | 黄 `#d99a06`、闪 1000ms | 需要关注 |
| `working` | 20 | 90s | 绿 `#16a34a`、慢闪 1600ms | 正在执行工具 |
| `thinking` | 15 | 60s | 绿、快闪 640ms | 正在推理 |
| `done` | 6 | 30s | 绿、常亮 + 一次入场脉冲 380ms | 任务完成（到期直接消失） |
| `idle` | 2 | 600s | 绿、常亮 | 空闲，无任务 |
| `stale` | 1 | 300s | 灰 `#9ca3af`、常亮 | 会话已沉默（派生） |
| `offline` | 0 | — | 灰、常亮、opacity .45 | 没有任何会话（派生） |
| `off` | 0 | — | 灰、常亮、opacity .45 | 监控暂停（派生，全局开关） |

「静默超时」是会话转入 `stale` 的时限；`stale` 那一行则是它被真正删除前的宽限期。`offline` / `off` 不是会话状态，所以没有意义。

**视觉取向是朴素简约**：纯色圆点，没有发光、没有渐变、没有阴影。状态靠**颜色 + 明暗节奏**表达，不靠装饰。颜色值比常规的 500 号色深一档——扁平色块没有描边也没有阴影，太亮的颜色在浅色桌面上会糊掉。

三个关键区分：

- **`off` 不是会话状态，是全局开关。** `paused = true` 时无论多少会话在报绿都显示熄灭灰。CLI 的 `signalhub off` / `on`（或 `monitor off` / `on`）操作的是这个全局位，不是某个会话。
- **`done` 和 `idle` 颜色相同**，靠一次性的入场脉冲 + 30s TTL 收敛来区分。这是刻意的：`done` 是短暂的确认反馈，`idle` 是稳态。
- **`stale` / `offline` / `off` 是派生状态，不能上报。** 它们是聚合出来的结果，不是外部程序该声称的状态；`Signal::parse` 会明确拒绝它们。三者的视觉差异与取舍见 §3.5。

圆点直径默认 **22px**，可在设置里选 16 / 22 / 32。窗口尺寸由 Rust 侧按可见圆点个数和设置算出（见 §3.7），设置变更和会话数变化时都会同步调整。

`Signal::priority()` 返回上表的数值，聚合时取 max。

### 3.2 聚合算法（核心决策）

规则是「红 > 黄 > 绿，高优先级状态不被普通工作事件覆盖」。有两种实现路径：

**方案 A：会话级单调守卫（不采用）**

```rust
// 新事件优先级低于当前状态时丢弃
if new.priority() < current.priority() { return; }
```

看起来正好实现了规则，但有致命场景：

```
会话 A: PreToolUse        → working(20)
会话 A: PermissionRequest → permission(40)   🔴
用户点了「允许」
会话 A: PostToolUse       → working(20)      ← 20 < 40，被守卫丢弃
                            结果：灯一直是红的，直到 600s TTL 过期
```

要修就得引入 `resolve` 标志、事件白名单……复杂度上升且状态机会卡死。

**方案 B：会话内后写覆盖 + 聚合取 max（采用）**

```rust
impl Store {
    /// 会话内部：最新事件直接覆盖（last-write-wins）
    pub fn report_at(&mut self, now: Instant, session: &str, /* ... */) -> bool {
        let before = self.aggregate();
        self.sessions.insert(session.into(), Session { /* ... */ });
        before != self.aggregate()      // 聚合变了才需要推前端
    }

    /// 聚合：跨会话取最高优先级 —— 「红 > 黄 > 绿」就实现在这里
    pub fn aggregate(&self) -> Signal {
        if self.paused { return Signal::Off; }
        self.sessions.values()
            .filter(|s| s.state != Signal::Off)
            .max_by_key(|s| s.state.priority())
            .map(|s| s.state)
            .unwrap_or(Signal::Idle)
    }
}
```

为什么这就够了：

- 规则真正要防的场景是「A 会话在等授权（红），B 会话还在跑工具（绿），绿灯事件不该顶掉红灯」。取 max 天然解决——B 报 `working`(20)，A 仍是 `permission`(40)，聚合保持红。
- 用户批准后 A 自己发 `PostToolUse → working`，A 的红消失，聚合自然回落。**没有停滞状态。**
- 单会话（最常见的场景：只有一个 Claude Code）根本不存在跨会话覆盖问题。
- `done` 靠 TTL 自动回落 `idle`，不需要人为清场。

如果将来发现某个上报方事件过密导致红灯被同行会话的正常进度掩盖，再加一个 `hold: true` 字段（只允许显式清除）即可。v1 不需要。

### 3.3 四个兜底机制（缺一不可）

| 机制 | 作用 | 缺失后果 |
|---|---|---|
| 每状态默认 TTL | 会话静默超时后转 `stale` | 智能体崩溃在 `working`，灯会一直绿闪到 TTL 到期 |
| 全局 sweep 任务（250ms） | 定期检查过期并重算聚合 | 过期了但无人触发重算，前端收不到更新 |
| `SessionEnd` hook → 清除会话 | 正常结束立即清场 | 跑完的会话残留，多会话界面混乱 |
| `stale` 宽限期（30 分钟） | 沉默的会话先标记再删除 | 「智能体不说话了」和「智能体空闲」分不开 |
| 一切都有 TTL | 没有任何状态能永远粘住 | 早先 `idle` 没有 TTL，一个忘关的会话能显示半小时「空闲」 |

**每个状态都有 TTL 是刻意的**（`default_ttl()` 是个全函数，不再返回 `Option`）。早先 `idle` 没有 TTL，靠「30 分钟无事件回收」兜底——那段窗口太长，正是「智能体走了灯还亮着」的成因之一。现在 `idle` 也有 600 秒窗口。

**「忙碌」那两个的窗口刻意给得很宽（`thinking` 600 秒、`working` 300 秒），这条方向改过一次。** 早先它们是 60 / 90 秒，理由是「干活时每次工具调用都会触发 hook，静默这么久基本可以断定不在工作」—— 这条推理漏了一半：**模型思考、或者跑一段没有工具调用的长回复时，一个事件都不触发**。于是「智能体正在思考」这件事本身就会把灯推成沉默，再过五分钟干脆变成「没有智能体上报」，而智能体明明在干活。这是用户实际报上来的体验问题。

放宽的代价是崩溃的智能体晚一点被发现 —— 但那时它只是转成 `stale`（「沉默」），用户仍然看得到它，比「活着的智能体看着像死了」轻得多。**这个数值仍然直接决定「智能体消失后灯还会错多久」**，是调优时最该动的一个旋钮。（`feedback` 与 `permission` 这类「要你处理」的状态另有 300 / 600 秒窗口，不该动它们 —— 那些状态正是要粘住的。）

### 3.4 `stale`：把「不说话了」和「空闲」分开

会话静默超过 TTL 后**不再直接消失，而是转入 `stale`**，再保留 `STALE_GRACE` 才真正删除。`done` 是唯一的例外——它的语义就是「完成，回到常态」，到期直接消失。

**宽限期从 5 分钟放到了 30 分钟**，和上面那条是同一个体验问题的另一半：5 分钟太短，一个跑长任务的会话超过这个时间没有事件就会从灯上彻底消失，用户看到的是「没有智能体上报」。`stale` 本身已经是「它不说话了」这个信息，没必要那么快升级成「它不存在」。（细环画的就是这一段的剩余比例，所以这个值同时决定环缩短得多慢。）

这一层解决的是个真实问题：智能体崩溃、被强杀、或 `SessionEnd` 没触发时，会话会停在最后一个状态上。没有 `stale` 的话，用户看到的和「智能体正忙」完全一样，只能等 TTL 到期。

`stale` 的优先级**低于 `idle`**：一路会话在报 idle（活着）时，不该被另一路已经沉默的会话盖成灰的。

### 3.5 三档「不在工作」

灰色这一族有三个状态，语义必须分清：

| 状态 | 含义 | 视觉 |
|---|---|---|
| `stale` | 有会话，但它不说话了 | 灰、常亮、不透明 |
| `offline` | 一个会话都没有 | 灰、常亮、更淡 |
| `off` | 用户主动暂停监控 | 灰、常亮、更淡 |

`offline` 与 `off` 视觉一致是**刻意的**：它们都表示「没有在追踪任何东西」，差别只在语义，由 tooltip 和设置面板说明。22px 的圆点里塞不下第三种可区分的灰——与其造一个谁也看不出区别的颜色，不如承认这一点。

`stale` 与它们的不透明度差异是能看出来的，所以保留了。三者都不闪：它们都不是「有活动」。

### 3.6 非颜色编码，以及可辨识性

颜色不是唯一的信息通道，有三处刻意的例外：

**形状（色盲友好）。** 默认 `permission` / `error` 画成圆角方形，其余状态是圆形。红绿是色盲最难分的一对，而这两个恰好是最需要你注意的状态——一种形状区分就解决了关键场景，比换掉整套配色克制。约 8% 的男性分不清红绿，这不是审美问题。这条规则现在是「跟随全局形状」时的默认，解析在 TS 里（见 §3.6.1），用户给某个状态单独指定了形状就以用户的为准。

**细环（沉默时长）。** `stale` 圆点上的细环按剩余宽限期缩短，从满圈到消失。数值由服务端算好（组上的 `stale_progress`）而不是前端自己算——`age_ms` 是「距上次状态变化」，并不等于「沉默多久」，前端要算就得复刻一遍 TTL 常量。前端只把它塞进 CSS 变量 `--progress`，`lamp.css` 的 `ring` 形状直接拿它算 `conic-gradient` 的角度。

**环要会动，而推送不能滥。** 细环是连续的 0.0–1.0，如果直接参与 `sweep` 的前后比对，每 250ms 都会比出「有变化」——于是整段宽限期里灯球每秒重排 4 次，而细环服务的恰恰是「省着看」的状态。所以 `Visible` 里放的是**档位**（`progress_step`，16 档）：跨档才推一帧。为此 `Store` 要记住 `last_pushed` 那一帧 —— `expire` 一次调用的前后是同一个 `now`，不靠基线的话跨档永远发现不了，环就会停在转 `stale` 那一刻的长度上直到会话消失，比不画更误导。

**空闲时 sweep 不建快照。** 它每 250ms 醒一次，而快照要给每个组克隆名字和消息、还要排两次序 —— 零会话时也在每秒白算四遍。现在只在 `expire` 真的报了变化之后才建（**仍然在同一把锁里**：先解锁、变了再重新加锁的话，两次之间别的线程可以改 store，推出去的快照和「什么变了」这个判断就对不上了）。

**组的环取决定聚合那个会话的进度。** 组内两路都沉默时，圆点是因为聚合值更高的那一路才变 `stale` 的，环要缩短的自然也是它。取组内第一个的话，画出来的是另一路的进度——而用户眼里只有一颗点。

**明暗（安静模式）。** 空闲 / 沉默 / 离线时整体压到 0.15 不透明度，只有真正有活动或需要你注意时才完全显形；鼠标悬停恢复（否则压暗之后找不到它来拖）。`done` 也算「有事」——它是任务完成的确认，压暗就失去意义了。可在设置里关掉。

**穿透时安静模式必须让路。** 这条是死锁，不是偏好：安静模式唯一的恢复路径是 `.lamp-root:hover`，而穿透开启后窗口 `set_ignore_cursor_events`，hover **永不成立** —— 于是灯变成一颗永远 0.15、点不到也拖不动的点，比关掉还糟。所以灯上在穿透时直接把 `data-quiet` 收掉，`lamp.css` 里再留一道 `[data-quiet][data-pass-through] { opacity: 1 }` 兜底。

**截断要说出来。** 灯上最多 `MAX_SIGNS`（4）块牌，超出的被服务端截断 —— 而**灯的聚合是全体的**，于是「灯上只有三块、托盘/通知说的却是第四块的状态」。第 4 块牌的牌尾加一枚 `+N` 角标，tooltip 里列出被收起来的组名。角标 `flex: none` 寄住在已有的那块牌里，挤掉的是 `.sign-body`（组名先省略），所以**展开态的窗口尺寸一个字都不用改**。

**暂停和穿透都要持续可见。** 两者原先只有一个颜色变化，而 `off`（暂停）和 `offline` 都是很淡的灰，分不出来；穿透更糟 —— 鼠标点不到它，开启时那条一次性通知早就忘光了。现在两者各在牌尾挂一枚**持续存在**的角标（同时出现时穿透优先），tooltip 带上逃生快捷键：那个状态下谁也点不开设置面板去查，这条信息必须跟着角标走。折叠态没有牌面可寄住，角标单独占一个点的位置，所以 `collapsed_window_size` 要为此多算一个点。

**折叠 / 展开要有反馈。** 单组时切完连窗口尺寸都不变，没反馈就等于「点了没反应」。给一次性 opacity 脉冲 —— **不能用 transform**：本文件 §4.5 对常驻窗口有一条硬约束是「动画只动 opacity」，动 transform 会让它每帧重排。

**牌面（可辨识性）。** 灯球现在是一块**深色圆角牌**：彩点 + 组名 + 状态 + 已持续，有消息时多一行。深色牌面是刻意和**应用图标**同一套语言（深色圆角方块 + 彩点），这样悬浮灯和图标看起来是一个东西。

这一步替换掉了上一版的「外壳」（一圈中性细环）：外壳是给「孤立圆点不够像灯」打的补丁，而牌本身就是那个框，再在牌里套一圈纯属多余。**要的是结构（外框、底色、文字位），不是装饰（阴影、发光、渐变）**——朴素简约仍然成立。

### 3.6.1 用户可以调的外观

| 设置 | 取值 | 为什么提供 |
|---|---|---|
| 外观预设 | 单灯 / 紧凑 / 标准 / 醒目 | 一次设好下面几项，见下 |
| 形态 | 展开牌面 / 一颗灯 | 展开是默认（灯的本职是一眼看到状态），折叠是「让出地方」 |
| 大小 | 小 / 中 / 大 | 整块牌的尺度（牌宽、牌高、字号、灯的大小都由它派生） |
| 形状 | 圆 / 圆角方 / 环 | 全局默认；**环**在桌面上几乎没有别的东西会撞脸 |
| 配色 | 默认 / 色盲友好 / 高饱和 | 全局默认（起点） |
| 背景透明度 | 0–100（`--sign-alpha`） | 调低能看见桌面 |
| 闪烁节奏 | 50–200（100 = 原始） | 全局默认倍率；闪得太快会分心，太慢又看不出在动 |
| 牌上显示 | 组名 / 状态 / 已持续 / 消息，各自可关 | 有人只要一眼颜色，有人要看清「卡在哪一步」 |
| 安静模式 | 开 / 关 | |
| 每个状态的外观 | 颜色 + 形状 + 节奏，逐个覆盖 | 见下，在「灯效」页 |

**外观预设**（`src/lib/presets.ts` 的 `PRESETS`）一次设好大小、形态、牌上显示、背景透明度、闪烁节奏这五项 —— 它们互相牵制（牌面调透了就得把字调少、字多了就得把牌调大），让用户一个个试很难试出一套协调的组合。预设**刻意不含形状和配色**：那两项是语义性的（形状承载色盲区分、配色承载「红 = 危险」），混进同一个预设里会让人以为换个风格就会顺手把配色改掉。预设**只在前端**，不进 `Settings` —— 它不是一个状态，只是「一次把几个字段设成一组值」。

**闪烁节奏**是一个倍率（数字越大闪得越快）。但它**只作用于用户没单独设节奏的状态** —— 见下面「逐个状态」那一层。

**`show.message` 不是纯外观。** 牌有没有消息那一行决定了窗口高度：`lib.rs` 的 `visible_groups` / `sign_heights` 必须和前端 `data-has-message` 算出**同一个**布尔值（消息存在**且**用户没关掉那一段），否则窗口会裁掉最后一块牌。

**`show.age`（已持续）反过来不碰几何，但有一个别处没有的依赖。** 它是同一行里靠右的一段（`flex: none`），不占额外的行，所以 `sign_heights` 不管它。但这个数字是**算出来的**（`now - since`），而灯球只在状态变化时重绘、`sweep` 也只在会话真的过期时才推事件 —— 于是没有任何东西会让它随时间重绘，它会永远停在状态刚变化那一刻算出的 **0s**（`formatAge` 里的 `Date.now()` 只在重绘那一刻被求值，而那一刻的答案恰好就是 0）。所以灯球里挂了一个 `useNow`（`src/lib/useNow.ts`），每秒推一次「现在」。**加任何「算出来的时间显示」之前，先想清楚谁让它重绘。**

**逐个状态：颜色 + 形状 + 节奏。** 全局的 `palette` / `shape` / `blink_speed` 是**默认值**，「灯效」页可以逐个状态覆盖，存在 `Settings.styles: BTreeMap<String, StateStyle>` 里：

```rust
pub struct StateStyle {
    pub color: Option<String>,   // #rrggbb
    pub shape: Option<Shape>,
    pub blink_ms: Option<u16>,   // 0 = 常亮
}
```

**三样都是可选的，没写 = 跟随全局**（颜色跟随 `palette`、形状跟随 `shape`、节奏跟随 `blink_speed`）。为什么是「可选的字段」而不是「填满的表格」：默认值会随版本演进（新增状态、调整默认节奏、改配色），如果用户配置文件里存着一份填满的表，那些改进就永远到不了他那儿。空着 = 跟随，是唯一能让默认值继续演进的表达。这和 §3.13 的 `#[serde(default)]` 是同一个道理。

旧的扁平 `colors` 表会被 `migrate_legacy_colors` 搬进 `styles` 的 `color` 字段，字段本身标了 `skip_serializing` **永不写回** —— 和 §3.10 的旧 `webhook_url` 同一个套路。不搬的话，用户已经调好的颜色会在升级后静默变回默认。

`clamped()` 的清理规则（手改配置文件属于系统边界）：`blink_ms` **恰好为 0 是合法的**（常亮），其余夹回 120–4000ms；颜色格式不合法就丢掉那个颜色，但**同一状态上别的覆盖要留着**；三样都没写的条目**整条丢掉**（它没有任何作用，留着只会让「当前是哪套预设」的判断无谓地失败）；不认识的键名**刻意保留** —— 静默删掉用户写的东西是数据丢失，键名合法性是 `validate_settings` 的职责（它会明确报错）。

**解析在 `src/lib/lampStyle.ts`（前端）**，`resolveShapes` / `resolveAnimations` / `lampVars` 三个函数。两条有实据的规则：

1. **全局 `blink_speed` 倍率只作用于用户没单独设 `blink_ms` 的状态。** 否则「我把 error 调成 300ms」会在全局滑杆一动之后就变得不是 300ms 了 —— 用户给某个状态定的节奏是他明确的意图，不该被一个全局旋钮悄悄改掉。用户显式设的 `blink_ms > 0` 一律变成一个朴素的 `pulse`（于是 `done` 那个一次性的 `pop`，只要用户给它设了节奏，也会变成一个真的会闪的灯）；`0` 变成 `none`。
2. **色盲的形状区分从 CSS 挪到了 TS。** 全局形状是「圆」时，`permission` / `error` 解析成 `rounded`。原来这条写在 CSS 里（`[data-shape="circle"] .dot[data-state=…]`），现在形状是**逐元素**的（一个窗口里多块牌可以是不同形状），根上挂一个值不够用，只能挪到 TS 里算。它只属于**跟随全局**的那部分 —— 用户显式给某个状态指定了形状就照用户说的来（他要给 `permission` 画圆环，那是有理由的）。

**CSS 也随之调整**：`data-shape` 从窗口根挪到**每个灯珠**上（形状是逐元素的了）；每个状态的 `animation` 由 `--anim-<状态名>` 变量驱动，兜底值就是原来写死的那条，所以样式表单独也能用（和 `state.css` 的 `var(--c-idle, 兜底)` 一个思路）。`--blink-speed` 变量去掉了 —— 倍率现在在 TS 里做除法。

**灯效预设**（`STYLE_PRESETS`）与外观预设是**两组不同的问题**：外观预设管「整块牌多大、多透、显示哪几段」，灯效预设管「红灯和绿灯怎么区分开」。混在一起会变成一套谁也说不清的组合，所以分开。四套 —— 跟随全局 / 形状区分 / 节奏分级 / 只在需要时闪 —— 每套给的是**完整的一份 `styles` 表**，应用就是整份替换，所以「当前是哪一套」可以靠逐字段相等判断出来；用户改掉任意一格，高亮就消失（它已经不是那一套了）。

**配色仍然是两层：预设 + 逐个覆盖。** 配色方案（默认 / 色盲友好 / 高饱和）是起点，用户的逐个覆盖优先 —— 可以先选「色盲友好」，再单独把 `error` 调成更醒目的红。只给预设是不够的：不同桌面背景、不同显示器、不同人对颜色的判断差很多，最终得让用户自己调；但一上手就让人从空白开始配，很容易配出一套自己都认不出的灯，所以预设仍然保留。

**颜色在 TS 里解析，不在 CSS 里。** 「预设 + 逐个覆盖」需要一层解析逻辑；写在 CSS 里会变成 10 状态 × 3 套配色的规则矩阵。所以 `lib/palettes.ts` 算出每个状态最终的颜色，转成一组 `--c-<状态名>` 变量挂在窗口根元素上，`state.css` 只负责消费（`var(--c-idle, 兜底)`，兜底值就是默认配色，让 CSS 单独也能用）。

挂在**根**元素而不是每个圆点上：一个窗口里可能同时有多个状态点（折叠态的几颗灯、设置面板里每个会话一颗），挂一次全都生效。

**描边和细环由填充色派生**（`color-mix(in srgb, var(--state) 74%, #000)`），所以用户只挑一个颜色，不用分别调描边——否则每加一个自定义颜色都得再算一遍。`color-mix` 万一不可用（很老的 WebKitGTK），自定义属性会退化成「保证无效」，`border: 1px solid var(--edge, var(--state))` 于是取兜底值（描边和填充同色、看不见），布局不受影响。

**键名包含派生状态。** `styles` 的键可以是 `stale` / `offline` —— `Signal::parse` 刻意不接受它们（派生状态不能被上报），但用户要能改它们长什么样，所以这里单独用 `Signal::ALL_NAMES` 校验。校验必须在 `clamped()` **之前**：`clamped()` 会静默丢掉不合法的项（那是给手改配置文件用的兜底），先 clamp 再校验用户就永远收不到「你写的颜色不合法」这条反馈。

**一个已知的取舍**：色盲的形状区分（`permission` / `error` 圆角方）只在**跟随全局、且全局形状是「圆」**时生效——用户把全局形状改成圆角方或环，或者显式给这两个状态指定了别的形状，这个区分就没了。没有偷偷保留它，因为「形状设置在某些状态下失效」比「设置被明确覆盖」更难理解。设置面板里写明了这一点，并建议此时配合色盲友好配色。

### 3.7 多组：几块牌

**分组**由上报方决定：请求里带一个可选的 `group`（不传就是 `default`）。灯球上每组一块牌，各组自己聚合。于是「一路在等授权、另一路在跑测试」不再是两个点挤在一起，而是两块各有名字、各有状态、各有消息的牌。

四件事：

1. **全局聚合 = 各组里最高的那个**。通知、钩子、托盘都用它，与分组无关——你不必为了「要不要弹通知」去理解分组。
2. **牌的排序由服务端定**（最紧急在最前，平局按组名），客户端**不再排**。原因不是省事：灯球窗口的高度取决于「哪几块牌可见」，两边必须算出同一批牌，排序只能有一个判断点。
3. **组是临时的**：组里最后一个会话消失（TTL 过期或 `DELETE`），牌就消失。没有「建组」这一步，也就没有需要清理的孤儿组。
4. **组名重复即合并**：同一组的会话一起聚合。别把不同项目的会话塞进同一个组。
5. **藏起来 ≠ 当它不存在**：右键可以把一组从灯上藏掉（`Settings::hidden_groups`），藏掉的组不再占牌的位置，但**仍然参与聚合、通知和钩子**。聚合是全局概念（「有事找你」），藏一块牌不该让应用悄悄不再提醒你。想彻底忽略一组，应该让它的上报方别再报。恢复在设置面板的「状态」页（按组点「显示」，或「全部显示」）。
6. **显示偏好不影响语义**：`Settings::group_meta` 给每组存一个显示名和置顶权重。组名是上报方给的标识（`build-1`），用户想让它读起来像人话、或者想让它永远排在最前面。这两样**只改灯上怎么显示** —— `/v1/state` 返回的组名、隐藏 / 静音的匹配、聚合、通知、钩子全都仍然按原始组名。

   **置顶只把置顶的组拎到前面，其余仍按紧急程度排。** 让用户把顺序整个接管过来的话，一盏红灯就可能被排在绿灯下面 —— 而「瞥一眼先看到该看的那块」正是这盏灯存在的理由。所以这是个 pin，不是「自定义排序」。置顶组之间用权重排（`Option<i16>`），权重由界面按「先钉的先看」分配，省掉一个拖拽界面。

   **顺序在 `visible_groups` 里算，不在 `Store` 里。** `snapshot.groups` 的顺序是**紧急度**，那是状态语义（`/v1/state` 也按它返回）；置顶是**显示偏好**。混进 `Store` 就得让 `Store` 知道 `Settings`，而它们是分开的两块状态。代价是排序规则在 Rust 和前端各有一份 —— 和隐藏、`MAX_SIGNS` 截断一样，两边必须算出同一批牌，否则窗口高度会对不上。
7. **静音 ≠ 隐藏**：右键（或设置面板）可以把一组**静音**（`Settings::muted_groups`）。静音只让这一组**不再触发通知和提示音**，其余一律不变——灯上照常显示、聚合照常算、钩子照常触发、`/v1/state` 照常返回。它和「隐藏」是两件事，可以各自独立：一组可以「看得见但不打扰」（只静音），也可以「看不见但照常提醒」（只隐藏）。最容易读混的就是这一条，所以单独列出来，细节见 §3.17。

8. **兜底分组由服务端推导**（`Settings::group_by`）。上报自带 `group` 时它优先；没带时才看 `group_by`：

   | 取值 | 一个组是什么 | 什么时候用 |
   |---|---|---|
   | `none`（默认） | 所有上报归 `default` | 单会话 / 单智能体，只要一眼状态 |
   | `cwd` | 一个工作目录 | 几个项目并行，各占一行 |
   | `session` | **一个会话** | 同一个智能体并行开了几个窗口 / worktree，状态各不相同 |

   **`session` 是补的第三种**，起因也是个真实反馈：同一个智能体开两个会话时，只按目录分组会把它们挤在同一块牌上，只能看到最紧急的那一个 —— 而它们的进度往往是两码事。按会话分就把每个会话摊成自己的一块，多个智能体自然也分开了（它们的会话必定不同）。代价是组名是上报方给的会话 id（多半是 UUID 那样不好读的串），牌上会自动截断，想去「外观 → 各组的显示」改名也行。

   **这一步做在 `server.rs` 的 `apply()`，不在 CLI、也不在钩子命令里。** 钩子命令是写死的字符串，而按目录 / 按会话分组要的是**每次调用各自的值**，写进命令行就只能是个常量，根本表达不了；而且改服务端顺带覆盖了 `curl` / CI / 手写脚本，不用去动用户的智能体配置文件。代价是上报路径也要读设置，所以 `SharedSettings` 和 `SharedStore` 一样是 `Arc` 共享的同一份，不是启动时的快照 —— 否则用户在面板里一改开关，得重启才生效。

   **默认必须是 `none`**，这条比看着重要：一旦默认分组，所有现有用户的灯会从一块牌变成若干块、窗口尺寸跟着变、没配过的组显示名还是原始路径 —— 属于无声改变既有行为。

窗口尺寸：展开时牌竖着叠（宽度不随牌数变），高度按每块牌累加；折叠时一组一颗点、外加一枚全局状态角标，横着排：

```
展开：牌宽   = size × 7
      牌高   = size × 3/2（一行）/ size × 5/2（带消息两行）
      牌间距 = size / 2
      牌尾的角标（+N / 暂停 / 穿透）flex: none，挤掉的是牌身，不另占高度
折叠：宽 = (dots + flags) × size + (dots + flags − 1) × (size / 3)
      高 = size + 20
留白 = 20（LAMP_MARGIN，两侧各 10）
```

**有消息的牌会变高** —— 那是刻意的：牌子长出一行本身就是「有东西可读」的提示。但用户把「消息」那一段关掉之后牌永远是单行，窗口高度也得跟着少一行（见 §3.6.1）。

最多同时显示 `MAX_SIGNS`（4）块，超出的截断（服务端已按优先级排好，所以留下的恰好是最紧急的）。折叠态的上限 `MAX_DOTS` **刻意等于 `MAX_SIGNS`**：折叠只是换个外形，不该顺带少显示几个组——那会让人以为一折叠就把状态弄丢了。宽度**固定、超出用省略号截断**：让宽度跟着文字走会让窗口每次消息变化都跳一下。

**折叠态的点数是「组数 + 角标数」。** 暂停 / 穿透那枚角标在折叠态单独占一个点的位置（展开态则寄住在牌尾，不占额外高度），所以 `collapsed_window_size(size, dots, flags)` 有三个参数。**两个上限分别封**：组数按 `MAX_DOTS`，角标按 1 —— 封住它们的和会让「多一枚角标」被当成「少一个组」，那正是截断要避免的那种谎。

几何在 Rust（`config::sign_width` / `sign_height` / `collapsed_window_size`）和 CSS（`.sign` / `.lamp-dot` 的 `calc()`）各写了一份，**必须严格对齐**——差了 1px 就会被 `overflow: hidden` 切掉最后一块牌。这是本项目里反复出现的一类耦合（折叠点距、设置窗高度也是），所以每个几何常量旁边都写了「CSS 里对应哪条规则」。

**「哪几块牌可见」只有一个判断点**：`lib.rs` 的 `visible_groups`（先滤掉隐藏的，再截断到 `MAX_SIGNS`）和 `sign_heights`（每块多高）。前端照着同一条规则渲染。两边算出不同的组，窗口要么裁掉最后一块牌，要么底下空一条。

### 3.8 通知：把「被动」补成「主动」

灯是**被动**的：你不盯着屏幕它就白搭，而「不用看终端」恰恰意味着你可能根本没在看灯。所以聚合**新变成** `permission` / `attention` / `error` 时弹一条系统通知。

两个不显然的设计点：

1. **只在跃迁时弹一次，不是每次状态变化都弹。** 一轮工具调用会触发几十次状态推送，每次都弹就成了骚扰。核心判断就是 `previous != Some(current)`。
2. **权限在启动时申请，不在第一次要发通知时申请。** 弹权限框和发通知没法同时发生——放在第一次要发通知时，那条通知必然丢掉，而它往往正是最要紧的一条。

通知正文取「胜出会话的项目名 + 智能体自己写的说明」，例如 `proj · 需要批准: rm -rf build`。`Signal::label()` 在 Rust 侧也有一份中文名（界面上的文案在前端的 `signals.ts`）——重复一份是因为通知由 Rust 发，比前端可靠（webview 出问题也照发）；那个 `match` 是穷尽的，所以新增状态时编译器会强制补上标签。

> **dev 模式的限制**：`tauri dev` 跑的是未打包的裸二进制，而 macOS 的 `UNUserNotificationCenter` 需要 bundle identifier。所以通知在 dev 下可能**不显示**（调用本身会成功、不报错）。要确认真的能弹，得 `npm run tauri build` 出真正的 .app。这一点没在 dev 下验证过，不要当成已验证。

**出站钩子**见 §3.10 —— 它和系统通知共用「只在聚合跃迁时触发」这个语义，但钩子自带过滤条件（`when`），所以不受「只在需要注意的状态」限制：用户可以配「done 时跑个脚本」。

**提示音**（`Settings::sound`，默认开）挂在通知上。**声音名没有三平台通吃的写法**，只能逐平台取值：macOS 认 `NSUserNotificationDefaultSoundName` 这个哨兵；Windows 的 toast 只接受 `Default` / `IM` / `Mail` / `Reminder` / `SMS` / `Alarm*`，喂它 macOS 那个哨兵会**静默无声**；Linux 走 XDG 的 `sound-name` 提示，而 dunst / GNOME 这些常见的通知守护进程根本不理会它——所以那一栏的常量是 `None`，设置等于没接。`alerts.rs` 里用 `#[cfg]` 分平台选常量，并在注释里写明了每个平台的实情。

声音**只有在通知发得出去时才存在**：关掉通知，这条路径根本不会被调用，声音自然一并没了。这是刻意的——不为一个提示音再单开一条音频通路和它的跨平台麻烦。

**「该不该吵你」还叠了三道闸门** —— 按组静音、持续多久才提醒、勿扰时段，见 §3.17。它们都只影响通知（和声音），不影响灯怎么显示、聚合怎么算。

`ureq` 因此**必须带 rustls**（钩子目标都是 HTTPS）。选 rustls 而不是 native-tls，是因为后者在 Linux 上要系统 libssl，跨平台构建会多一道坎。

### 3.9 一个把三个功能同时静默废掉的接线 bug

这一条值得单独记，因为它的形态很典型。

现象：webhook 配好了、地址正确，但从不发出；系统通知也从没弹过。

根因：**通知器有两个构造方式**。`notify::to_lamp_window(app)` 只负责把事件推给前端窗口；而 lib.rs 在 setup 里组合了一个「推事件 + 核对窗口尺寸 + 记统计 + 发通知 + 转发」的闭包，把它 `manage` 进 Tauri state。但 `server::spawn` 自己又调了一次 `notify::to_lamp_window(app)` —— 于是**所有走 HTTP 上报的状态变化全部绕过了那一整套逻辑**。而智能体的 hook 恰好全走 HTTP。

更糟的是它**不报错**：`alerts::send` 和 `alerts::forward` 根本没被调用，所以既没有通知、也没有失败日志。我早先「通知没有报错」的验证是个**假阴性**——它验证的是「没有错误」，而真相是「没有尝试」。

**修法不是补一处调用，而是去掉另一种构造方式**：把组合逻辑收进 `notify::compose(app)`，让它成为唯一入口，`to_lamp_window` 降级为模块私有的 `emit`。这样「某个路径用错通知器」在结构上就不可能发生。

教训：**当一个功能有多条入口路径（HTTP / sweep / 命令 / 托盘）时，共享的那层逻辑必须只有一个构造点**。否则漏掉一条路径的表现不是报错，而是「功能静默不生效」。

### 3.10 出站钩子：让 SignalHub 成为信号中枢

入口本来就是通用的（HTTP + CLI，任何程序都能报，8 个状态词是共享词汇表），但出口最初只有**一条 webhook**，而且只转发「需要注意」的三种状态。要做成信号中枢，出口必须是**多条带过滤的钩子**：

```json
{ "when": ["permission", "error"], "type": "http",    "url": "https://ntfy.sh/x" }
{ "when": ["done"],               "type": "command", "command": "say 完成" }
{ "when": [],                     "type": "http",    "url": "http://localhost:9000/ingest" }
```

`when` 空数组 = 任何变化都触发。模型和触发在 `outbound.rs`（注意和 `hooks.rs` 方向相反：那个是入站，把智能体的 hook 装进它们的配置文件）。

**四条设计约束：**

1. **必须异步。** 触发点在状态变更路径上（HTTP 上报和 sweep 都会走到），同步发网络请求或等命令结束会把状态机卡住。每条钩子丢进 `spawn_blocking`，互不影响。
2. **命令必须带超时。** 走 `sh -c`（Windows 上 `cmd /C`），用户因此能写管道和重定向 —— 这正是钩子有用的地方。但挂死的命令会把 tokio 的阻塞线程池占满，所以轮询 `try_wait` 到 10 秒就杀掉。输出全部丢弃：钩子是用来触发副作用的。
3. **只在聚合跃迁时触发**，不是每次快照变化。同一个状态内的变化（某个会话的说明文本改了）不算。语义和系统通知一致。
4. **空目标不算错。** 目标留空的钩子不触发也不报错 —— 编辑时必然要经过「刚点添加、还没填目标」这个中间态，那时候报错就没法编辑了。面板上会标「未填目标」，所以它不会静默失效。

**安全性：`type: "command"` 会执行本地命令，没有额外开关。** 信任模型和 git hooks / npm scripts 一样——配置文件在用户自己的主目录里，能改它就能执行任何东西。加一个开关只会给人一种「关掉就安全」的错觉，而文件本来就在用户手里。文档里写明了这一点，并提醒不要把别人的 `config.json` 直接拿来用。

**一次迁移：** 旧的单条 `webhook_url` 在启动时会被搬成一条 `when = [permission, attention, error]` 的 HTTP 钩子，字段本身标了 `skip_serializing` 永不写回。不搬的话，用户已经配好的转发会在升级后静默失效——而那正是最难发现的一类回归。出口只保留一种表达，不让「单条 webhook」和「钩子列表」并存。

### 3.11 今日状态时长统计

按「前端给的本地日期」分桶——**本地日期只有前端知道**（Rust 这边没有时区数据，`SystemTime` 只给 UTC），所以由前端推过来（`new Date().toLocaleDateString("sv")` 给的就是本地时区的 ISO 日期）；日期一变就重置。这样不必引入时区依赖。

**日期跟着那个每分钟一次的时钟心跳走，而不是只在查询时带过来。** 这条一开始做错了：跨天只在 `report`（也就是有人在查统计）时才判，而那个查询只在设置面板开着时发生 —— 灯球是常驻应用，整天不开面板是常态，于是「今日时长」会横跨多天一路累加。现在 `Stats::rollover` 被摘成独立方法，`set_local_clock` 每分钟调一次它（`useLocalClock.ts`），跨天在分钟级就能被发现。**注意 `useLocalClock` 和 `useStats` 必须用同一个日期写法**，否则两边字符串不等，会白白触发一次跨天把统计清掉。

四个不显然的点：

1. **第一次拿到日期只记下来，不清空。** 否则从启动到第一次拿到日期之间累计的时间会被白扔。
2. **跨天时当前这段也重新起算**，否则会把昨天那段算进今天。
3. **查询会把「正在进行的那一段」也算进去**，所以不必等状态变化就能看到当前进度；结算完立刻把这段重新打开，否则反复查询会漏时间。
4. **`rollover` 只认日期字符串变了没有**，不自己算日期 —— 它没有时区数据，算出来的「今天」可能是错的时区。

时长平局时按优先级排——否则顺序取决于 `HashMap` 的迭代顺序，界面每次刷新都可能换个次序。

**每日合计会落盘**（`~/.signalhub/stats.json`）。灯球是常驻应用，但「常驻」不等于「永不重启」：改设置、升级、崩了重来，而用户对「今天等了多久」的期待是跨重启的。

落盘里有四个不显然的地方：

- **内存用 `Instant`、文件用日期。** `Instant` 是单调钟（不受系统时钟调整影响），但它存不下来、跨重启也没有意义 —— 所以文件里只有「某天某状态多少秒」，当前这一段是**存的时候现折算**的。
- **今天只存一处。** `history` 放**过完的日子**，`totals` 放今天。读盘时全部进 `history`；等前端第一次推来日期，把那一天从 `history` **取出来**（`remove`）放进 `totals`。不取走的话，落盘时「history + 今天的 totals」会把今天写两遍。
- **跨天归档前必须先把当前这段结算掉。** 不清的话，一天里最后那一段（从上次状态变化到跨天，可能几小时）整个丢掉 —— 它在 `segment_start` 里、还没进 `totals`。这条有单测盯着。
- **文件的键是状态名的字符串，不是 `Signal`。** `Signal` 的 `Deserialize` 是给**外部上报**用的，刻意拒绝 `stale` / `offline`；而统计里那两个恰恰要有。所以走 `Signal::from_name`（接受全部名字），绕开那个属于上报的约束。

落盘挂在**时钟心跳**上（`set_local_clock`，前端每分钟推一次）—— 那是「应用还活着」的现成节拍，不必再起一个定时器。代价是崩掉最多丢一分钟，对一个「今天等了多久」的数字完全够用。

**近 30 分钟的时间线**是同一份数据回答的另一个问题。`Stats` 本来就收到每一次聚合变化，现在多留最近 `TIMELINE_CAPACITY`（512）次**状态转换**——只在状态真的变了时才记一笔，同一个状态反复上报不刷屏。

`timeline(now, window)` 返回首尾相接的 `Segment { state, ms }`，覆盖 `[now − window, now]`，从旧到新：第一段在窗口边界处截断，最后一段截到 `now`。它取 `&self`——不像 `report`，它**不能**改自己（查询时间线不该影响统计）。第一个样本之前没有已知状态，所以覆盖区间从 `max(now − window, 第一个样本的时刻)` 起算：宁可短一点，也不假装知道应用启动前是什么状态。

设置面板的「状态」页把它画成一条色带，**每一段的宽度就是它的时长**。今日统计回答「一共多久」，这条回答「什么时候」——两个问题不一样，所以两条都留着。`Segment` 直接给时长而不是给时间戳：`Instant` 换成墙上时钟要处理时区和时钟回拨，而前端只需要「这一段占多宽」。

### 3.12 窗口位置记忆

用 `tauri-plugin-window-state`，但**只让它记位置，不记尺寸**：

```rust
.with_state_flags(StateFlags::POSITION)   // 默认是 all()，会把尺寸也一起恢复
```

尺寸由设置和会话数决定、是程序自己管的（`apply_window_size`），让插件跟着恢复会和它打架。这是这个插件最容易被误用的地方——默认值 `all()` 会连尺寸、最大化、可见性一起恢复。

插件的默认存储位置是 app 配置目录下的 `.window-state.json`（macOS 上是 `~/Library/Application Support/<identifier>/`）。它在**正常退出**时写入，所以 dev 下反复重建期间看不到这个文件是正常的。

**位置记住 + 尺寸由内容决定，这两件事凑在一起会咬人。** 组一多、或者从旧版本升上来（默认从一颗灯变成一叠牌），窗口就会长大 —— 一个原本贴着屏幕右下角的点会长到屏幕外面去，用户看到的是一块被裁掉一半的牌子，而且多半想不到是尺寸变了。

所以 `apply_window_size` 在**尺寸真的变了**之后会调一次 `keep_on_screen`，把窗口夹回工作区（`work_area`，不是整屏 —— 任务栏 / Dock 占掉的那一条不算可用空间）。三个细节：

1. **只在尺寸变了的分支里调**，所以不会和用户拖动打架：用户把窗口拖到哪就是哪，只要没越界就一个像素都不动。
2. **用刚设下去的逻辑尺寸换算，不读 `outer_size()`** —— `set_size` 是往事件循环投一条消息，紧接着读回来拿到的还是旧值，用它算会把窗口夹到错的位置。
3. **窗口比工作区还大时 `clamp` 会 panic**（min > max），所以先取 max 保证区间非空。夹紧的数学抽成了纯函数 `clamp_to_area`，边界情况（比屏幕还大的窗口、副屏在左侧时的负坐标）都有单测 —— 那些在真机上很难复现。

### 3.13 设置文件的向前兼容

`Settings` 带 `#[serde(default)]`。这是用户可手改、也会跨版本留存的文件，缺字段时应该退回**该字段**的默认值，而不是整份解析失败——否则每新增一个设置项，都会把用户已经调好的其他设置一起重置。

这个坑是真实踩到的：加 `notify` 字段之后，已有的 `config.json`（里面存着用户调过的 `size: 32`）直接解析失败，圆点尺寸会被静默重置回 22。日志里那行 `config.json 无法解析（missing field notify），使用默认设置` 就是它。

### 3.14 两种形态，以及拖拽与点击的冲突

灯有两种形态，左键在两者之间切换：

- **展开（默认）** —— 一叠交通牌，每组一块（§3.7）。默认展开是刻意的：灯的本职就是让人一眼看到状态，折叠是用户主动要的例外。
- **折叠** —— 每组一颗裸灯，横着排，没有牌面。

选择存在 `Settings::collapsed` 里，所以重启后还是用户上次选的那个。三条路径都能切（灯上左键、灯上右键菜单、托盘），它们**共用 `lib.rs` 的同一个 `set_collapsed`**——写两份行为迟早分叉。

窗口尺寸仍由 Rust 算（见 §3.7 的几何），前端只负责「点了一下」。

> 上一版这里是另一种设计：点圆点把窗口放大成一张**会话列表**（`Settings::panel_size` / `PANEL_CHROME` / `PANEL_ROW`）。那一套连同 `.lamp-panel` 的 CSS 和 `set_lamp_expanded` 命令一起删掉了——会话级明细现在只存在于设置面板的「状态」页，灯上不再有第二套列表。

**这里踩到一个真实的冲突：同一个元素不能既用 `data-tauri-drag-region` 又响应点击。**

`data-tauri-drag-region` 让系统在 `mousedown` 时接管鼠标、进入原生拖拽循环，之后的 `click` 就不再可靠地送到 webview —— 表现是「点一下折叠」时灵时不灵。而把拖拽区域去掉又会丢掉拖窗口的能力，那是这个工具的基本操作。

解法是自己在 JS 里区分：按下时记下坐标，移动超过 4px 才认为用户在拖窗口（此时才调 `getCurrentWindow().startDragging()` 交给系统），否则在 `mouseup` 时当作点击。于是灯上**没有 `onClick`**，点击是从 `mouseup` 里判出来的。

**两个推论，都还在生效：**

1. **两种形态都仍然可拖拽**。上一版为了「点击收不起来」而让展开态不可拖，现在不需要了——点击是从 `mouseup` 判的，和拖拽不冲突。
2. **右键能穿透到 `contextmenu`**，因为只有主键会记下拖拽起点（`if event.button !== 0) return`）。所以右键菜单和「左键拖拽 / 左键点击」可以共存于同一个元素上。

空白处（牌之间、留白）也 `preventDefault` 掉右键，否则会冒出 webview 自己的菜单。

### 3.14.1 每组右键菜单（`menu.rs`）

右键一块牌（或折叠态的一颗点）弹出：隐藏该组 / 静音该组（或取消静音该组）/ 清除该组的状态 / 折叠成一颗灯（或展开牌面）/ 打开设置…。

**为什么是原生菜单而不是 HTML。** 灯球窗口是按内容**精确**尺寸的（§3.7），而且 `overflow: hidden`——一个 HTML 菜单画在窗口里必然被裁掉。原生菜单由系统绘制，不受窗口边界约束，位置也由系统避开屏幕边缘。这是这个项目里「窗口尺寸即内容尺寸」这条约束的又一个后果。

**两个实现点值得记：**

1. **运行时构造的 `Menu` 没有自己的事件回调。** `TrayIconBuilder` 有 `on_menu_event`，但 `Menu` 没有——只能挂在 `AppHandle::on_menu_event` 上。关键在于那是往 `global_event_listeners` 这个 `Vec` 里 **push** 而不是替换（tauri 2.12.2 的 `manager/menu.rs` 与 `tray/mod.rs::register` 都往同一个 vec 里推），所以**托盘自己的回调照常工作**，两者共存。为了让这一点成立，菜单 id 用 `group:` 前缀和托盘的 id（`quit` / `toggle` / `pause` / …）隔开，收到不认识的 id 直接放行。
2. **组名没有编进菜单 id。** 组名是任意用户字符串（`ci`、`我的构建`），编进 id 要转义、还可能和别的 id 撞上。所以 id 只用固定的几个动作名，被点的组名存在 `menu::Target(Mutex<Option<String>>)` 里，处理事件时再取。

**菜单上有三个关于「这一组」的动作，别混：** **隐藏**只是不让它占灯上的位置（`hidden_groups`，见 §3.7 第 5 条）；**静音**只是不再为这一组弹通知 / 出声（`muted_groups`，见 §3.17）；**清除**是把这一组的会话全部删掉（`Store::clear_group`）。清除是「这个组的状态卡住了」的解药——上报方崩了或者没发收尾事件时，灯会一直停在最后一个状态上等 TTL 到期，而清除是立刻的。

**措辞跟着当前状态走。** 静音那项在已静音时显示「取消静音该组」，切形态那项在折叠时显示「展开牌面」——写「切换」的话，得先看一眼设置或灯才知道会切成什么。

### 3.15 单实例、穿透、自启

**单实例**（`tauri-plugin-single-instance`）要**最先注册**。多开会让两个进程抢同一个端口文件、互相覆盖状态，表现出来是「灯球偶尔不动」这类极难排查的现象。第二个实例起来时把灯球亮出来——用户多半是没找到它才又点了一次图标。

**点击穿透是这里唯一有危险的功能**：开启后整个窗口忽略指针事件，鼠标再也点不到、拖不动它。所以：

1. **全局快捷键必须先注册成功**，它才是键盘上的出路（另一条是托盘菜单）。注册失败只记日志、不阻断启动，因为托盘那条路还在。
2. **开启时发一条通知说明怎么退出**——一个没有逃生通道的穿透模式就是个陷阱。
3. **不替用户改外形。** 上一版会在开启穿透时顺手把展开的面板收起来，理由是「否则留下一个点不动的大窗口」。现在外形是用户自己选的、存在设置里的，而穿透下窗口本来就点不动——替用户改掉反而是越权，所以这一步删了。
4. **不落盘**。它是瞬态开关，重启后必须回到可点击状态；否则用户一开机就面对一个点不动的圆点，还不知道为什么。这也是它没进 `Settings` 而是单独放在 `UiFlags` 里的原因。

托盘里的「切换点击穿透」刻意**不显示开关状态**：快捷键也能切换它，菜单里的状态会漂移。准确状态在设置面板里（`get_toggles`），并且 Rust 在每次变更后都会发 `signalhub://toggles` 事件——不发的话面板会一直显示过时的状态。

### 3.16 设置面板的组织：左栏七项

设置面板拆成七项 —— **状态 / 外观 / 提醒 / 接入 / 通知转发 / 指南 / 系统**，列在左侧栏里。理由是它曾经是一列 5 个小节、7 个开关、1 个输入框、4 段说明加一张会话列表全堆在一起，**总高约 1000px，比很多 13 寸笔记本的可用高度还大**。需要靠窗口跟着内容长来迁就，本身就是设计有问题的信号。

| 页 | 内容 |
|---|---|
| 状态 | 近 30 分钟时间线 + 按组列出的会话（一行一个会话：状态点 + 项目名 + 状态 + 说明）。**只读**：这一页回答的就是「现在发生了什么」。底部是最近消息流 |
| 外观 | 全局那层：预设、形态、大小、形状、配色方案、背景透明度、闪烁节奏、牌上显示哪几段、安静模式。**再往下是逐状态的颜色 / 形状 / 节奏表**（10 行，`PerStateStyles`），最后是**各组的显示**：显示名 / 置顶 / 隐藏 / 静音 |
| 提醒 | 需要时弹通知、通知带提示音、**系统通知权限状态**、持续多久才提醒、勿扰时段 |
| 接入 | 把智能体接上（检测 + 一键接入 / 卸载）→ 只用命令行的那几家 → **试一下** → 分组方式 → 局域网访问 |
| 通知转发 | 出站钩子列表（多条、可过滤、支持本地命令） |
| 指南 | 手册：这是什么、三步接上、接口速查、不工作了怎么办 |
| 系统 | 保持在最前、托盘跟随状态、界面语言、开机自启、点击穿透、**配置导出 / 导入** |

标题区（当前聚合 + 组数与会话数 + 今日时长）、左栏底部的「暂停监控」和面板底部的退出按钮**固定在内容区之外**——它们是「为什么我打开这个面板」和「怎么关掉」，任何时候都该看得到。

**「状态」页和「外观」页的分工是「读」与「写」。** 改名、置顶、隐藏、静音原先散在「状态」页的组卡上：那一页因此成了全窗最长的一页，而且把只读的实时会话和写进去的偏好混在一起 —— 前者跟着上报每秒在变，后者是你设完就不动的。现在四样全部搬进「外观」的「各组的显示」一节，并且「隐藏」「静音」各自收敛成一个开关（原先是一个「点一下恢复」的徽标加一个「静音」按钮，三种控件表达两个布尔量）。

**两次改版是为了同一件事：让每一页只回答一个问题。** 最早那次（见上面的来历）是分页；第二次是**把「灯效」并进「外观」** —— 它们是同一件事的两层（全局默认 + 逐状态覆盖），分成两个页签只会让人在两个之间来回找「改颜色到底在哪」。所以「外观」页里有 `PerStateStyles` 小节，用一条标题把那两层分开。

**控件只有两种「选法」。** `seg`（带外框的分段按钮）管一组里选一个，`chip` 管选几个（筛选条件、牌上显示哪几段）。两者的选中态是同一套：浅灰底 + 正文字色 + 中等字重 —— 曾经 chip 是 accent 整块实心加白字，成了全窗最重的元素，而它表达的只是「这个筛选项开着」。两组「预设」（外观页的整块牌预设、逐状态页的风格预设）都是单选，所以都是 `seg` 而不是 chip。逐状态表里那两列因为列宽受限用 `select`，是**唯一记录在案的例外**。

**`.hint` 是次级文字，不是一个盒子。** 它曾经有边框、有内边距，一页三到六个，比正文还抢眼 —— 和「靠字号与灰度分层」这条自述原则直接冲突。现在它只是一段灰色说明；真需要重样式的是 `.error` 那类。

**「接入」页瘦下来的办法是把接口速查搬去「指南」。** 那一页曾经有 1013px 的内容、而可视区只有 433px —— 两倍多的内容墙。根因是它同时在干两件事：「点哪个按钮把智能体接上」（动作）和「端点表、状态词表、curl 示例」（查细节）。前者是第一次用的人要的，后者是已经接好的人要的，混在一起就把按钮淹没了。现在「接入」只剩智能体列表，「指南」是一份可以滚的手册 —— 并且「状态」页的空态里挂了一个入口，因为那是第一次用的人最可能撞上的地方。

**内容区改成「左栏导航 + 右内容」两栏，右栏高度交给 flex（窗口 720×690）。** 之前是顶部一行七个页签加一块**固定 495px** 的内容区：固定高是为了「切页签不会跳」，代价是短页留一大片空白、长页还得在里面滚。改成左栏之后，窗口高度固定，`.page` 用 `flex: 1` 吃掉标题区和底部之间的全部空间 —— **「切页签不会跳」从「写死一个够大的数」变成了结构性成立**，不必再为英文比中文多折一行预留余量。**「外观」和「指南」仍然允许滚**：前者的长度由那张 10 行的表加「各组的显示」决定，后者本来就是一份手册。

**页签从顶部一行挪进左栏，同时把窗口从 560 加宽到 720。** 左栏不能白占地方 —— 720 − 140（栏宽）− 16（栏与内容间距）− 40（面板左右内边距）= 524 的内容区，比原来的 520 还宽一点。栏宽按最长的英文页签名（`Forwarding` / `Guide`）量出来，再宽就是从内容区身上刮肉。

> **附带删掉了「按内容自动定高」。** 上一版为了让那一列不再被裁切，写过一个 `fit_settings_window`：前端量出内容高度、Rust 把窗口设成那么高。改成固定内容区之后，`.settings` 的高度恒等于窗口高度，`scrollHeight` 也就恒等于 `clientHeight` —— 那个测量变成了空转，留着是死代码。**它是被新设计取代的，不是被推翻的**：分页之前它确实解决了真问题。

**改设置的路径有三条**（设置面板、托盘、灯上右键菜单），而两个窗口都得跟着变。所以写设置的逻辑收在 `lib.rs` 的 `persist_settings` 一处：夹紧 → 存盘 → 改内存 → 应用（窗口尺寸 / 置顶）→ 广播 `signalhub://settings`。

这是 §3.9 那条教训的同一个形状：**当一个功能有多条入口路径时，共享的那层逻辑必须只有一个入口**。三条路径各写一遍的话，漏掉「广播」那一步**不会报错**——只是设置窗里的开关偶尔显示过时的状态，最难查。

### 3.17 通知的三道闸门：静音 / 持续阈值 / 勿扰时段

**这三道闸门都只影响「要不要打扰你」，不影响「世界是什么样」。** 灯照常显示、聚合照常算、钩子照常触发、`/v1/state` 照常返回——它们只决定系统通知（和挂在通知上的提示音）发不发。

**按组静音（`muted_groups`）。** 静音掉的组不参与告警：`alerts::alerting_aggregate(snapshot, muted)` 在**没被静音**的组里取最高优先级的聚合，通知的**标题和正文都用它**。和 `snapshot.aggregate` 分开是刻意的——那个是全局的（托盘、钩子、`/v1/state` 都用它），静音一组不该让托盘变色、也不该让钩子不触发。全被静音时返回 `Offline`（不是紧急状态，闸门直接放行成「不弹」）；正文也按静音过滤，否则静音组的消息还是会出现在通知里。

> 这里踩到过一个不一致：标题原来用**全局**聚合，而正文过滤了静音组。当一个被静音的组恰好处于全局最高优先级时，通知的标题写着那一组的状态、正文却是另一组的会话——一条自己跟自己打架的通知。两处都改用 `alerting_aggregate` 就好了。

**持续多久才提醒（`alert_after_secs`，默认 5 秒，0 = 立刻）。** 智能体经常在一秒内进出 `permission`（先问再自己答，或者弹一下就被自动批准），立刻弹的话，用户被叫过去看到的是一个已经解决的问题。所以「需要你注意」的状态要**持续**够久才弹。

它替掉了原来那个 `should_alert(previous, current)`（那个只能表达「跃迁时弹一次」），换成 `alerts::Gate`：

```rust
pub enum Decision { Now, Later, None }
impl Gate {
    pub fn observe(&mut self, alerting: Signal, threshold: Duration, quiet: bool) -> Decision;
    pub fn confirm(&mut self, alerting: Signal) -> bool;
}
```

三个设计点：

- **`Gate` 是纯逻辑，不碰 `AppHandle`**，所以「阈值 + 静音 + 勿扰」三者怎么交互是被单测覆盖的，不是只靠跑起来看。它用两个标志接过了老逻辑：`notified` 实现「这个 episode 只弹一次」（一轮工具调用推几十次同样的状态，每次都弹就是骚扰），`pending` 保证一轮里只排一次延迟检查（否则几十次推送就是几十个定时器）。
- **延迟到点后重新从快照判断，不信排任务时捕获的值。** 到点时先重读 `alerting_aggregate`，再问 `sustained()`——后者读 `GroupView::since_ms`（「这一组进入当前状态的时刻」）。状态离开又回来是一个**新的 episode、新的计时**，只看捕获的 `Signal` 值会让一个过期的定时器提前开火。`sustained` 读 store 而不是自己记一份时钟，也是这个道理：store 是唯一的事实来源，自己记一份恰恰在那种情况下会说谎。判定用「任一组已持续够久」而不是「最早的那组」——几组同时处于同一紧急状态时，只要有一组卡了很久，这个状态就该算数。
- **`confirm` 顺手把 `notified` 置上**，于是重复到点的定时器不会再弹第二次。

**勿扰时段（`quiet_hours`）。**

```rust
pub struct QuietHours { pub enabled: bool, pub start: u8, pub end: u8 }
```

**只有小时、没有分钟**：分钟级精度只会让配置变麻烦，而「晚上十点到早上八点别吵我」本来就不需要分钟。起止都按**本地时间**，`covers(hour)` 处理跨午夜（22–8 读作 `[22,24) ∪ [0,8)`）；`start == end` 读作**空窗口**而不是「全天」，所以一个手滑调成一样，后果是「没生效」，而不是「从此再也不提醒我」。

**判断留在 Rust，前端只提供「现在几点 + 今天几号」这个事实。** Rust 这边没有时区数据（只有 UTC，仓库刻意不引 `dirs` / `chrono`），所以当前本地时钟只能由前端推——`src/lib/useLocalClock.ts` 每 60 秒调一次 `set_local_clock`，两个窗口谁活着谁推（值一样，多推一次没有代价）。而「在不在窗口内」的判断留在 Rust，因为跨午夜那种边界逻辑只有一处实现才敢信，而且那边能单测。**前端还没推过第一帧时，Rust 当作「不勿扰」**——宁可多弹一条，也不要因为一个尚未建立的事实把通知永久静掉，那会表现为「通知功能坏了」，最难归因。日期顺带推过去，是为了让**今日统计**也能跨天结算（见 §3.11）。

**勿扰期间彻底不弹，而且不补发。** 这一轮会被标记成「已通知」，之前排下的延迟定时器到点也会被 `confirm` 判成 false。刻意不做「延后补发」：补发意味着早上醒来面对一整夜攒下的通知，而那正是勿扰想避免的事。灯照常显示状态，所以什么信息都没丢。

### 3.17.1 卡住了就一直提醒

`Gate` 的 `notified` 实现的是「一个 episode 只弹一次」。那对「一轮工具调用推几十次同样的状态」是对的，但对**真正卡住**的情形不够：智能体卡在等授权上时是**真的什么都不做**，没人去管它就永远停在那儿。第一次通知弹的时候你正好在开会，回来只看到一盏红灯，完全不知道它已经卡了一小时。

所以通知之后会排一条**重复提醒链**：5 分钟、15 分钟、30 分钟各再提一次，然后停（`alerts::REMIND_GAPS`）。50 分钟后还没人管，再响多半也没用，而一直响就成了骚扰。

三个设计点：

- **正文不是把第一次那条重发一遍，而是明说等了多久**（`alerts::send_reminder` → `lang::stuck_for`）。「还没解决」和「已经卡了 20 分钟」是两条不同的信息，**后者才推得动人**。时长读 `GroupView::since_ms`，和 `sustained()` 同一个事实来源 —— 各算一份的话，两处迟早会对「到底卡了多久」给出不同的答案。
- **`Gate` 多了一个 `episode` 计数。** 状态离开又回到同一个值时是一轮新的（`alerting` 变过，只是恰好变了回来），上一轮排下的提醒必须认得出并失效 —— 否则它会替新一轮发一条「已等待 20 分钟」，而新一轮才刚开始。同样地，`Decision::Later` 那条延迟检查也补上了轮次判断：原来只看 `confirm(alerting)`，那对「离开又回来」是认不出来的，会拿旧一轮的检查替新的一轮开火、跳过它自己的阈值。
- **链上每一步都重判，不一路睡到底。** 这中间状态可能已经过去了、用户可能把通知关了、也可能进了勿扰时段 —— 任何一步发现不该提就整条停掉。判据全部现读（快照、设置、本地时间），不看排链时捕获的值。进了勿扰是**停掉**而不是延后补发，和第一次通知同一条理由：早上醒来面对一夜攒下的通知，正是勿扰想避免的。

### 3.18 托盘图标跟随状态

`Settings.tray_follows_state`（默认开）让托盘图标画一颗**实心圆点**、颜色取当前聚合状态的颜色，而不是那个单色的三点模板字形——不看悬浮灯也能知道现在什么情况。关掉（或某个状态没有可用颜色）就退回单色模板字形，跟着菜单栏明暗自动反色。

**宽高比换了一套。** 三点模板字形刻意压扁到 2.16:1（见 `tray.rs` 的注释：三颗点排成一行本来约 3.7:1，菜单栏放不下），而跟随状态的单点没有「排成一行」的问题，套用 2.16:1 会被拉成一个椭圆——所以单点另取**方形**边长，宽等于高。

**颜色表不在 Rust 里复制一份。** 颜色是「配色方案 + 用户逐个覆盖」解析出来的结果，只存在于前端的 `lib/palettes.ts`；前端用 `usePalettePush`（在 `App.tsx` 里调用）把算好的 `状态名 → #rrggbb` 表通过 `set_palette_colors` 推给 Rust。在 Rust 里复制一份就意味着两处会漂移，而「用户改了颜色但托盘不变」是最难注意到的那种 bug。`set_palette_colors` 收到后立刻重画一次托盘，否则用户改完颜色要等下一次状态变化才在托盘上看到。

**重画托盘有三条路径**（状态变了、颜色表变了、`tray_follows_state` 开关变了），都走 `lib.rs` 的 `refresh_tray`——少走一条的表现是「托盘图标偶尔不更新」，很难归因。这是 §3.9 那条教训的又一面。

**一个实现点：** 更新图标用 `set_icon_with_as_template`，而不是先 `set_icon` 再 `set_icon_as_template`——tauri 2.12.2 的源码注释里写明两步会在 macOS 上渲染两次、肉眼可见地闪一下。非 macOS 平台它会退化成 `set_icon`，模板标志本来也只有 macOS 认。

### 3.19 通知上的动作按钮

通知带两个按钮：**打开项目目录** / **静音该组**。目的是把「知道有事」变成「能动手」——原来的通知只告诉你哪个项目卡住了，剩下的还得自己回终端里找。

**按钮属于一个「动作类型」，而动作类型必须先注册。** 这是 macOS 的 `UNNotificationCategory` 那一套，插件在三个桌面上抹平了：`Notification::register_action_types` 注册一组按钮，通知再用 `action_type_id` 引用它。**注册类型和挂处理函数必须一起做**——插件在「没有处理函数」时会干脆不显示按钮（否则点下去没人接），而只做一半的表现是「按钮从来没见过」，且不报错。所以这两件事绑在 `alerts::wire_actions` 一个函数里。

**目标在发通知时记下来，不在回调时重算。** 按钮是用户点的时候才回调的，而那时状态可能早就变了：从当前快照重新算「优先级最高的会话」会指向另一个会话，用户点的按钮就作用到了别处。所以 `alerts::LastAlert` 存住这条通知说的是哪一组、哪个目录。只存最后一条——告警本身有节流（一个 episode 只弹一次），同时存在两条待处理通知实际上不会发生。

**目标会话和标题、正文用的是同一个**：`alerting_session` 算一次，三处都用它。各算一遍的话，一旦算得不一致就会出现「正文说 ci 要授权、点『静音该组』却静音了 work」这种自相矛盾的通知。

**「打开项目目录」把路径作为独立的 argv 传，绝不过 shell。** 那个路径来自智能体上报的 `cwd`，是不可信输入；拼进 `sh -c` 就是一个命令注入。（`outbound.rs` 的钩子走 shell 是因为那里用户就是要写管道和重定向，这里没有那个需求。）目录不存在时什么都不做——弹一个「找不到」的报错框比不动更烦人。三个平台各一条命令（macOS `open -R`、Windows `explorer /select,`、Linux `xdg-open`），子进程起完在一条后台线程上回收，免得留下僵尸进程。

**两个平台细节：**

- macOS 上**两个及以上的动作会收进「选项」菜单**，而点「选项」本身会上报**第一个**动作。所以第一个动作是「打开项目目录」——点了也无害的那个。
- 一旦挂上处理函数，插件对**所有**通知都会起一条线程等用户交互（它要靠这个才知道用户点了什么）。告警有节流，所以挂着的线程最多就是「今天弹过几条通知」那么多，不值得为它绕路。

> **未验证**：这一条同样受 §3.8 那条限制——`tauri dev` 跑的是未打包的裸二进制，macOS 的 `UNUserNotificationCenter` 需要 bundle identifier，所以按钮在 dev 下看不到。要确认得 `npm run tauri build` 出真正的 .app。菜单构造、回调分派、目标记录这几层都有单测，但「按钮真的出现在通知上、点了真的触发」没有实证。

### 3.20 界面语言

界面可以切成英文。**代码注释和 `docs/` 保持中文** —— 它们是给维护者的，这个仓库的行文（为什么这么决定、踩过什么坑）本身就是它的核心资产，翻译一遍既稀释了它，又让每次改动都要维护两份。

**分工和时区那条一模一样**：Rust 不知道系统语言（就像它不知道时区），所以 `Settings::locale` 存的是用户的**偏好**（`auto` / `zh` / `en`），由**前端**把它解析成具体语言（`navigator.language` 以 `zh` 开头就是中文），再调 `set_lang` 推给 Rust。前端提供事实，Rust 用它挑文案。

因此有两个「语言」类型，别混：

| 类型 | 在哪 | 取值 | 谁用 |
|---|---|---|---|
| `config::Locale` | `config.rs` | `auto` / `zh` / `en` | 用户的**偏好**，落盘 |
| `lang::Lang` | `lang.rs` | `zh` / `en` | **解析后**的语言，瞬态 |

`Locale` 定义在 `config.rs` 而不是 `lang.rs`，是因为 `Settings` 要被 CLI 通过 `#[path]` 共用，而 `lang.rs` 是 app 侧的模块。同理，`Signal::label()` 从 `state.rs` 搬到了 `lang.rs` —— 它现在要分语言，而 `state.rs` 也在 CLI 的共用名单里。

**原生界面必须单独处理。** 托盘菜单、灯上的右键菜单、通知的动作按钮、设置窗的标题都不经过 webview，前端换不了，所以语言一变就得重建。这几件事收在 `lib.rs` 的 `apply_lang` 一个函数里 —— 漏掉一处的表现是界面上混着两种语言，而那只有肉眼能发现。两个细节：

- 托盘菜单是启动时建好就一直挂着的，换语言只能整个换掉（`TrayIcon::set_menu`）。菜单项的 **id 不变**，所以事件分派不用动。
- 通知的动作类型重新注册一次即可（同 id 覆盖）。顺带一提，插件在「没有注册处理函数」时会干脆不显示按钮，所以 `wire_actions` 必须整体再走一遍，不能只改文案。

**文案表用「对象」而不是「字符串键」。** 前端是 `MESSAGES: Record<Lang, Messages>`，`Messages` 是一个接口 —— 加一条文案就得两种语言都加，TypeScript 会盯着。`t("look")` 那种键查找没有这个保障，漏一条就是界面上冒出一句另一种语言。Rust 那边同理：`NativeText` 结构体的每个字段都是 `&'static str`，两种语言各一份静态实例，`text(lang)` 挑一份。

**有一条测试专门盯「英文里还有没有中文」**（`lang.rs` 和前端各自一份）：把英文那份的每一条文案过一遍，看有没有 CJK 字符。漏译是这类改动里最容易发生、又最难自查的问题 —— 它不会报错，只会让用户看见一句中文。

### 3.21 配置导出 / 导入

整份 `Settings` 序列化成 JSON 存到用户选的文件里，「系统」页两个按钮。换机器、重装、或者想手工看一眼自己配了什么的时候用。

**职责切在最要紧的那一刀上：前端只用 dialog 插件拿一个路径，读写和校验全在 Rust。** 前端自己读文件再塞进 `set_settings` 就绕过了校验 —— 而导入这条路上校验是必须的。

导入走的是**和设置面板改设置完全同一条路**（`validate_settings` → `persist_settings`），所以：

- **不认识的状态名、非 `#rrggbb` 的颜色 → 明确报错。** 这两种是手改配置文件最常犯的错，而它们的兜底（`clamped` 是静默丢掉）只在「启动时读配置」那条路上合适 —— 那条路上总得起得来，这条路上用户是主动点的，静默什么都等于骗他。
- **超范围的值（尺寸填了 500）→ 夹回合法区间**，不拒绝整份文件。对「从别处拷来的配置」而言，因为一个数字越界就把其余全部退掉太苛刻了。

**坏文件报错，不静默套默认值。** 这一条和 `load_settings` 的兜底**刻意相反**：启动时读不出来必须继续启动（否则一个手滑的文件就让应用起不来），而导入读不出来必须说 —— 用户以为导进去了、其实什么都没变，是最糟的结果。

**导出用的是原子写**：导出的文件用户多半会留着当备份，而写了一半的备份比没有更糟。

有一条单测把每一项都设成非默认值再往返一遍（`Settings` 派生了 `PartialEq`，所以是精确比较）：漏一个字段、类型对不上，都会在那里露馅 —— 而不是等到用户换机器导入时才发现。

### 3.22 局域网访问：一个显式放宽安全模型的开关

默认只绑 `127.0.0.1`。跑在别的机器、容器或 WSL 里的智能体连不进来 —— 那正是「本机服务」这个安全模型的代价，也是它的价值。想跨机上报的人可以打开「允许局域网访问」，服务改绑 `0.0.0.0`。

**打开之后唯一的防线只剩 token。** 那道「带 `Origin` 头一律拒绝」的中间件挡的是「你正在浏览的某个网页偷偷去打本机端口」——它是**针对浏览器**的，对 `curl` 这类客户端完全无效（人家不发 `Origin` 就行了）。所以开了之后，同一网段里任何人拿到 token 就能上报。这不是实现缺陷，是这个功能本身的代价，所以：**默认关、要显式打开、界面上把代价写清楚**（说明分两段，代价那一段单独成句，不藏在操作说明的尾巴上）。

**改完要重启应用才生效。** 监听地址只在启动时绑一次；运行中重绑会让端口变化（首选端口可能已被占用，于是退到系统分配），CLI 的自动发现跟着断一下 —— 出错时表现为「灯突然收不到上报」这种极难归因的现象。与其在运行中做这件事，不如写明「下次启动生效」。

界面靠**两个值**判断要不要提示那句话：设置里的 `lan_access`（用户想要什么）和服务**实际**绑到哪了的 `bound_lan`（`server::spawn` 在真的 `bind` 成功之后回填）。两者不一致时才提示 —— 无条件挂一句会让人以为一直没生效。

**唯一真正决定安全模型的那一行被抽成了纯函数**（`server::bind_host(lan)`），配了单测钉住两个分支和「默认必须是关的」。写成内联的三元表达式就只能靠跑起来看，而这一行值得比那更硬的保障。

`local_ip()` 用「连一个 UDP socket 再看自己的 `local_addr`」这个经典办法拿本机在局域网里的地址：UDP 的 `connect` **不发任何包**，只做一次路由查找，所以不引入依赖、也不产生流量。取不到就返回 `None`，界面上不显示 —— 它只是给人看一眼，不该因此报错。

## 4. 悬浮窗实现

### 4.1 窗口配置

Tauri 2 的配置键是 lowerCamelCase，注意 `skipTaskbar` 的 `b` 是小写（历史遗留）。

```json
{
  "label": "main",
  "url": "index.html?window=light",
  "width": 42, "height": 42,
  "resizable": false,
  "decorations": false,
  "transparent": true,
  "alwaysOnTop": true,
  "skipTaskbar": true,
  "shadow": false,
  "focus": false,
  "visible": false,
  "maximizable": false, "minimizable": false, "closable": false
}
```

- `width`/`height` 只是初值：真实尺寸由设置决定（圆点直径 + 20px 边距），启动时和每次改设置都会由 Rust 侧重设一遍。
- **`transparent: true` 在 Tauri 2.12.1+ 不再需要 `macos-private-api` feature**（旧 2.x 需要）。用 `cargo tree -p tauri` 确认版本。
- **`visible: false` + setup 里先套用设置再 `show()`**：否则会先按配置里的默认尺寸闪一下再跳到设置里的尺寸。
- **`closable: false` + `decorations: false` + `skipTaskbar` + Accessory 激活策略 = 用户没有任何办法退出应用。** 必须提供一个退出入口，见 §4.4。

**第二个窗口：设置面板。** 同一个 Vite 应用、同一份 bundle，靠查询参数分流，比配 Vite MPA 多入口简单得多：

```json
{
  "label": "settings",
  "url": "index.html?window=settings",
  "width": 720, "height": 690,
  "resizable": false,
  "center": true,
  "visible": false,
  "maximizable": false
}
```

三个非显然的点：

1. **高宽都是定值，内容自己滚。** 宽度 720 = 左栏 140 + 间距 16 + 内容区 524 + 左右内边距 40；高度 690 固定，内容区用 flex 填满余下的空间（见 §3.16）；会话多了在内容区里滚，不会把窗口撑高。改布局后要在浏览器里量一次再定值——把视口固定成 720×690 再量，才能避开移动端视口模拟的干扰。
2. **关闭时只隐藏、不销毁**（`WindowEvent::CloseRequested` + `api.prevent_close()`），这样重开是瞬时的。
3. **Accessory 策略下窗口不会主动到前台**，所以打开设置时临时切回 `ActivationPolicy::Regular`，关闭时切回 `Accessory`。副作用是设置打开期间应用会出现在 Dock 里——这反而是对的，用户正在和它交互。
4. **两个窗口都不是透明的**，但 `lamp.css` 里有一份全局的 `html, body { background: transparent }`（灯球窗口需要）。设置面板靠 `html[data-window="settings"]` 属性选择器压过它，这样覆盖关系是确定性的、不依赖两个 CSS 文件的打包顺序。`main.tsx` 负责把 `data-window` 写到 `<html>` 上。

### 4.2 setup：置顶与 Dock 隐藏

```rust
#[cfg(target_os = "macos")]
app.set_activation_policy(tauri::ActivationPolicy::Accessory);  // 不在 Dock / Cmd-Tab 出现

let win = app.get_webview_window("main").unwrap();   // 需要 use tauri::Manager;
win.set_visible_on_all_workspaces(true)?;            // 所有桌面空间可见
win.set_always_on_top(true)?;
win.show()?;
```

`skipTaskbar` 在 macOS 无效，隐藏 Dock 图标必须用 `ActivationPolicy::Accessory`。

### 4.2.1 崩了会留记录：`panic = "abort"` 与 panic hook

release 打开 `panic = "abort"`（见 `Cargo.toml`），进程直接消失。**这对这个应用是很危险的一条**：灯球没有 Dock 图标、没有窗口，Accessory 策略下连个能报错的地方都没有 —— 用户看到的只是圆点不见了，而「灯自己退了」和「我没注意到」在他那儿分不出来。

所以 `run()` 的第一件事是 `install_panic_hook()`：把 panic 信息和位置写进 `~/.signalhub/hooks.log`，同时打一份到 stderr。`panic = "abort"` 下 hook **照样会跑**（跑完才 abort），所以来得及落盘。

**为什么不干脆去掉 `abort`**：一来那 55 处 `.expect("... poisoned")` 全靠它成立（不展开栈 ⇒ 锁永不中毒，那些分支构造上不可达；改成 unwind 它们会变成活的，而且真走到那一步只会连环 panic，比直接退出更难查）；二来 wry / tao 会从 Objective-C 回调里调回 Rust，让 panic 展开着穿过 C 帧是 UB。这两条都比「一个已经出了错、状态未知的进程继续跑」更值得保住。

hook 里**绝不能再 panic**（双 panic 直接 abort，什么都来不及记），所以全程 `let _ =` / `unwrap_or_else`。

### 4.3 拖拽

`data-tauri-drag-region` 在 v2 仍然有效，并新增了 `"deep"` 值——让任意后代元素的点击也能拖动。因为灯球会盖满整个窗口，必须用 `"deep"`：

```html
<div class="root" data-tauri-drag-region="deep">
  <div class="lamp" />
</div>
```

Tauri 只响应鼠标**主键**的按下事件，所以右键可以正常穿透到 `contextmenu`。`A / BUTTON / INPUT / SELECT / TEXTAREA / LABEL / SUMMARY` 会阻止拖拽——自定义右键菜单时不要用这些标签。备选方案是 JS 调 `appWindow.startDragging()`（需要 `core:window:allow-start-dragging` 权限）。

### 4.4 点击穿透：必须警惕的坑

`set_ignore_cursor_events(true)` 让**整个窗口**忽略指针事件——包括拖拽和右键。一旦开启穿透，鼠标就无法再操作它。

**铁律：永远不要在全局快捷键注册成功之前开启穿透。** 逃生通道顺序必须是：注册快捷键 → 提供托盘菜单项 → 才允许切到穿透模式。UI 上切换时也应提示用户按什么键退出。

因为核心诉求是「可拖拽」，v1 **默认不开穿透**，仅作为托盘菜单/快捷键的可选模式。

**退出入口（v1 必需）**：因为窗口无边框、不可关闭且不在任务栏显示，灯球右键菜单必须提供「退出」，走一个自定义 Tauri command（自定义命令不需要额外 capability）：

```rust
#[tauri::command]
fn quit(app: tauri::AppHandle) { app.exit(0); }
```

### 4.5 动画方案选型

| 方案 | 评价 |
|---|---|
| **CSS keyframes（采用）** | GPU 合成，只动 `opacity`/`transform`，零 JS 开销；换状态只改一个属性；天然支持 `prefers-reduced-motion` |
| Canvas / WebGL | 浮窗只有几十像素，过度设计 |
| 帧序列图 / Lottie | 视觉最好，但 v1 成本过高 |

实现方式是把状态映射成根元素的 `data-state`，配色集中在 `styles/state.css` 一份 `[data-state] { --state: … }` 里（灯球和设置面板的会话小圆点共用），动画则按状态挂在 `.lamp` 上。切换状态 = 改一个 DOM 属性。

```
[data-state="working"]  .lamp { animation: pulse 1600ms ease-in-out infinite; }
[data-state="error"]    .lamp { animation: pulse 340ms steps(2, end) infinite; }
```

`error` 用 `steps()` 硬切做出频闪感，与 `permission` 的平滑闪烁区分开——两者颜色相同，节奏是唯一的区分手段。

`error` 用 `steps()` 硬切做出频闪感，与 `permission` 的平滑闪烁区分开。

无障碍：`@media (prefers-reduced-motion: reduce)` 下禁用所有动画，降级为常亮色块。

**`hooks.rs` 和 `outbound.rs` 名字里都有 hook，但方向相反：** 前者是**入站**（把 SignalHub 的 hook 装进智能体的配置文件，让它们能上报进来），后者是**出站**（状态变化时 SignalHub 主动往外 POST 或执行命令）。两个文件顶部都写了这句区分。

**关于 `hooks.rs` 为什么不是 `integration/{claude_code,codex,cursor}.rs`：** 原计划按智能体拆三个文件，实际写下来发现三者的差异只在「配置路径 + 事件名清单 + handler 形状」这张表里，而**安装逻辑（保留无关键、幂等、备份、解析失败中止、精确摘除自己的 handler）各家完全一样且是最需要谨慎的部分**。拆成多个文件会把这段逻辑抄好几遍，或者抽出一层反而更绕。所以是一个 `hooks.rs`，内部用一个小 `Agent` 枚举和一张事件表区分差异。

这个判断后来被验证了两次：**加 Gemini CLI 和 Goose 各只花了不到一小时**，而且改的确实是那张表 —— 唯一的例外是 Goose，它走插件目录而不是共享配置，安装/卸载各多了一步（写清单、删目录），那也只在 `install`/`uninstall` 两个入口里各加了十来行，`install_at` 那条共用的核心逻辑一行没动。

**Pi Agent 不走这条路，因为它没有能写 hook 的配置文件**（只有命令行上报）。这是那张表装不下的一类，所以它**不进 `Agent` 枚举、也没有 `install`/`uninstall`**：接了也没地方写。它的接入方式就是「在自己的脚本里调一次 `signalhub`」，所以界面上给的是一条可抄的命令而不是一个按钮 —— 「接入」页专门有一节放它。

这一节单独列出来、而不是混进上面那个列表，是因为上面每一行都有「接入 / 卸载」按钮：把一个没有按钮的条目混进去，用户会以为按钮没渲染出来。**同一个列表里的条目形状必须一致**，不一致的东西该另起一节 —— 这比「少一节标题」重要。

顺带一提，这也说明「支持一个智能体」有两种含义：**能自动接线的**（有配置文件可写）和**只能命令行上报的**（要用户自己接线）。前者是一条 `match` 分支，后者只需要文档和一条能抄的命令 —— 后者不该被硬塞进前者的形状里。

**关于两个二进制。** 这个包里有两个 bin：app（`signalhub-app`，源自 `src/main.rs`）和 CLI（`signalhub`，源自 `src/bin/signalhub.rs`）。两者同名会冲突，而 app 的名字用户看不到（通过 .app 启动），CLI 的名字却要写进智能体的 hook 配置里，所以让给 CLI。`[package] default-run = "signalhub-app"` 让 `cargo run`（也就是 `tauri dev`）选 app 那个，`tauri.conf.json` 的 `mainBinaryName` 同步设为 `signalhub-app`。

**Cargo 包名不叫 `signalhub`，叫 `signalhub-desktop`。** 纯粹是为了绕开一条 Tauri 的限制：sidecar 不允许和包同名（「Cannot define a sidecar with the same name as the Cargo package name」）。包名本身没有被任何二进制用上 —— 两个 bin 都是显式命名的，`[lib] name = "signalhub_lib"` 也是显式的。

**CLI 是作为 sidecar 打进应用包的**（`bundle.externalBin`）。这不是锦上添花：装了 `.dmg` 的用户手上没有 `signalhub` 这个命令，而「接入」页一键接入写进智能体配置的恰恰是 `signalhub hook <agent>`。不把它一起装进去，那条命令就是个跑不起来的东西 —— 而且是静默的。`resolve_hook_command` 因此按「PATH 上的裸名字 → 与主二进制同目录的那个 → 裸名字兜底」三级找它，**绝不能用 `current_exe()` 兜底**（原来就是那么写的）：那是 GUI 二进制，它不认 `hook` 参数，而单实例插件会把它变成「把已经开着的窗口叫到前面」，不报状态也不报错。

**这条 sidecar 给 `cargo` 加了一个前置步骤，值得知道。** `tauri-build` 在**构建脚本阶段**就校验 `externalBin` 里的文件在不在，所以 `cargo test` 之前必须先 `npm run stage-cli`（`scripts/stage-cli.mjs`）—— 哪怕测试根本不碰那个文件。脚本内部还有一层蛋生鸡：编译这个包里的任何东西（包括 CLI 自己）都会跑 `build.rs`，于是「编译那个文件」的命令本身要求那个文件已经存在；解法是给那一次 cargo 调用设 `TAURI_CONFIG` 把 `externalBin` 临时置空。`tauri dev` / `tauri build` 会自己先跑这一步，只有直接调 `cargo` 时才需要手动补。

**关于 `notify.rs`：** 状态变化的通知出口被抽成一个 `Notifier = Arc<dyn Fn(&Snapshot)>`，而不是让各处直接持有 `AppHandle`。原因是 `AppHandle` 在单测里造不出来——有了这层间接，`server.rs` 可以用一个只记数的闭包当通知器，起一个真实监听端口跑完整的 HTTP 层测试，覆盖鉴权、路由、状态码、聚合结果。这个抽象不是为未来预留的，它当场就换来了 16 个能跑的集成测试。

**关于 CLI 的 crate 组织**：CLI 用 `#[path = "../config.rs"] mod config;` 直接包含源码，而不是 `use signalhub_lib::config`——后者会把整个 Tauri 拖进这个本该很小的二进制（实测 3.1MB 且不链接 Tauri）。同样的原因，它不校验状态名，只把状态字符串原样转发给服务端，避免出现两张别名表。将来若构建时间或体积成为问题，再抽成 cargo workspace 里的 `crates/signalhub-cli`。

**state.rs 是关键**：它是纯逻辑、无 I/O、时间可注入（`apply(now, …)`），因此可以完整单测而不需要跑起 Tauri 或等待真实时间流逝。整个仓库的单测：`cargo test` 跑出 lib 184 + CLI 134（CLI 通过 `#[path]` 复用了 config / hooks / state 三个模块，所以两边有一部分是同一批用例）。

## 6. 路径约定

```
~/.signalhub/
├─ port          实际监听端口（app 启动时写入）
├─ token         32 字节随机 token，权限 0600
├─ config.json   用户设置（圆点大小、是否置顶）
├─ stats.json    每日状态时长（按本地日期分桶，保留最近 30 天）
├─ hooks.log     hook 调用日志 + 崩溃记录（每次调用一行，UTC 时间戳，512KB 轮转）
└─ pending.jsonl 可选：app 未运行时的暂存事件，启动时回放（v1.1）
```

**这里的每个文件都走原子写**（`config::atomic_write`）：先写同目录的临时文件、再 `rename` 过去。理由很直接 —— `load_settings` 的失败兜底是**静默退回全部默认值**，非原子写写到一半崩溃（断电、强杀、磁盘满）留下的残缺 JSON 会让用户调了一小时的颜色、钩子、分组一声不响地全没。智能体自己的配置文件（`~/.claude/settings.json` 之类）也走同一个函数。

三个要点，见那个函数的注释：临时文件**必须和目标同目录**（跨文件系统 `rename` 会 `EXDEV`）；私密文件的权限在**建临时文件时**就设好，不留「已是正式文件但还没收紧权限」的窗口；目标是**符号链接**时写到它指向的地方 —— 用 dotfiles 管配置的人常把 `~/.claude/settings.json` 做成链接，`rename` 会把链接本身替换掉，用户的仓库就此断了还不报错。

主目录只从环境变量解析（`HOME`，Windows 上是 `USERPROFILE`），**不引入 `dirs` 之类的依赖**——CLI 是独立二进制，少一棵依赖树是实打实的收益。代价是两者都缺失时会明确报错而不是静默写到别处，这是可接受的。app 由终端或 launchd 启动时两者必有其一。

## 7. 平台注意事项

**下表的每一条都是查过依赖源码或实测过的**，不是「大概是吧」；真没验证的会明说。

| 事项 | 说明 |
|---|---|
| macOS 全屏 Space 无法覆盖 | `alwaysOnTop` 不能浮在别的应用的全屏 Space 之上，需要更高的 NSWindow level 和私有 API。所有同类工具的共同限制，**不要在 v1 承诺**。 |
| Windows 透明窗口白闪 | 已按官方建议设 `noRedirectionBitmap`（对应 `WS_EX_NOREDIRECTIONBITMAP`）。不设的话，webview 内容渲染出来之前会闪一下白底。 |
| Windows 上 `set_visible_on_all_workspaces` 是**静默 no-op** | `tao` 里那个方法只在 macOS / Linux 上实现，Windows 上返回 `Ok` 但什么都不做。所以 `setup` 里那个 `?` 不会让启动失败 —— 但它也不提供任何效果。 |
| **Windows 不给托盘图标反色** | 模板图（RGB 全 0、只有 alpha）在 macOS 上由系统按菜单栏明暗着色；非 macOS 上 `is_template` 参数是被直接丢掉的（`tray-icon` 里那个方法连图都不收），托盘实现把原始位图交给系统、没有任何主题逻辑。所以那张图在 Windows 上就是**纯黑**，深色任务栏上等于看不见。`tray::monochrome_glyph()` 因此在非 macOS 上把三点图涂成中性灰。 |
| Windows 上 PATH 里的可执行文件带 `.exe` | `Path::is_file()` **不做 PATHEXT 展开**，只找 `signalhub` 会永远找不到 `signalhub.exe`。所以查命令时要把 `.exe` 也试一遍（见 `hooks::candidates`）。 |
| **Windows 只出 NSIS（`-setup.exe`），不出 MSI** | `bundle.targets` 原本是 `"all"`，会同时出 WiX 的 `.msi` 和 NSIS 的 `-setup.exe`。但 `light.exe` 生成 msi 那一步在这套配置上失败了：`failed to bundle project: failed to run light.exe`，而 Tauri **把 light.exe 自己的 stderr 吞了**，看不出原因（candle 那一步是过的，所以不是 `.wxs` 本身解析不了）。`tauri.windows.conf.json` 因此把 targets 收成 `["nsis"]` —— 那份本来就是 Tauri 推荐的 Windows 安装器。**这是绕开，不是修好**：根因没查出来，只是把出问题的那条路关掉了；想要 msi 的话得另做一轮诊断（用 `--verbose` 重跑，或者把生成的 `main.wxs` 打出来手动跑 light）。 |
| Linux/Wayland | 透明窗口与 `shadow` 官方标注不支持。Linux 是硬需求时优先 X11。 |
| `set_shadow` | Linux 不支持；Windows 上对无边框窗口加的是 1px 白边（Win11 上是圆角）。 |
| `set_skip_taskbar` | macOS 不支持（用 Accessory 策略替代）；Windows 上有效。 |
| 首次运行防火墙弹窗 | 绑定 127.0.0.1 通常不弹，但仍可能提示。 |
| **灯球在 Windows 上能不能拖** | **未验证**。窗口配了 `focus: false`（Windows 上走 `SW_SHOWNOACTIVATE`，即不可激活），而拖拽是 JS 调 `startDragging()`（Windows 实现是发 `WM_NCLBUTTONDOWN` / `HTCAPTION`）。理论上可行，但没有真机试过 —— 而拖动是这个工具的基本操作，所以这条值得优先验。 |

### 7.1 跨平台这件事靠 CI 兜着，不靠自觉

平台相关的代码（`#[cfg(windows)]`、`#[cfg(unix)]`）**在开发机上根本编不进去**。macOS 上 `cargo test` 全绿，完全不能说明 Windows 上能编过 —— 上面那张表里的两个 Windows 缺陷（托盘纯黑、`.exe` 没试）都是这么漏掉的，而且第二个是**编译期就该发现**的那一类。

所以 `.github/workflows/ci.yml` 在 macOS / Windows / Linux 三个 runner 上各跑一遍 `cargo test`、`cargo clippy`、前端构建和前端单测。Linux 那个 job 要装 webkit2gtk / gtk，否则连 `cargo test` 都链不过。

**clippy 也用 `-D warnings` 跑，而且必须三平台都跑** —— 理由和 `cargo test` 一字不差。加它之前先清了那 4 处积压的警告（两个手写的 `Default` 改成 `#[default]`、一处文档注释后面多空了一行、一处测试里的字段赋值），所以基线是 0，任何新警告立刻变红。

**这条 CI 已经真的救过一次命**：`shortcut_label` 在非 macOS 上把 Super 写成了 `Alt+Super+S`，而那条测试当初是 `if cfg!(target_os = "macos")` 分叉的 —— 开发机是 macOS，永远走不到出问题的那一支。Linux 和 Windows 两个 job 连红了三次才被发现。修的时候把平台写法抽成了 `KeyStyle` 枚举 + `shortcut_label_for(mods, key, style)`，**两套写法在任何平台上都能被测到**，这个 bug 类别才算关上。

**前端也终于有单测了**（vitest，`npm test`）。目前只覆盖**与 Rust / CSS 有「必须逐字一致」契约**的那几个纯函数 —— 典型是 `lib/lampSort.ts` 的置顶排序：它和 Rust 的 `visible_groups` 是同一条规则的两份实现，两边算出的可见牌不一致，窗口高度就对不上（多算一块是底下空一条，少算一块是最后一块被切掉）。这类逻辑**类型系统盯不住**，只能靠断言。它原本埋在 `SignalLamp.tsx` 里，摘出来单独放一个文件就是为了让它有地方被测。

## 9. 依赖清单

```toml
# src-tauri/Cargo.toml —— 已实现部分
[dependencies]
tauri = { version = "2", features = ["tray-icon"] }
axum = "0.8"                  # 0.8 的路径参数写作 /{name}，0.7 是 /:name
serde = { version = "1", features = ["derive"] }
serde_json = "1"
tokio = { version = "1", features = ["time", "net", "io-util", "macros", "rt-multi-thread"] }
getrandom = "0.3"             # 已在 Tauri 依赖树里，复用版本即免一次编译；用于生成 token
ureq = { version = "3", default-features = false, features = ["rustls"] }
#   ↑ CLI 连本机明文端口用不上 TLS，但 app 侧的出站 webhook 目标
#     （ntfy / Slack）都是 HTTPS，所以必须带 rustls
tauri-plugin-window-state = "2"   # 只用来记窗口位置，见 §3.12
tauri-plugin-notification = "2"   # 需要你注意时弹通知，见 §3.8
tauri-plugin-single-instance = "2"  # 多开会抢端口和状态文件，见 §3.15
tauri-plugin-autostart = "2"
tauri-plugin-global-shortcut = "2"  # 点击穿透的逃生通道，见 §3.15
```

几点取舍：

- **锁用 `std::sync::Mutex` 而不是 `tokio::sync::Mutex`。** 所有临界区都是纯内存操作、不跨 `await`，同步锁更简单也让 Tauri 命令能保持同步函数签名。将来若临界区里出现 I/O，必须换成异步锁。
- **依赖尽量挑树里已有的版本**，避免同一 crate 出现两个版本、白付一次编译。加依赖前先 `grep Cargo.lock` 看一眼是划算的习惯。
- **`dirs` 一度选了 7.x，后来去掉了**：它拖进 `dirs-sys` → `option-ext`，而主目录解析用环境变量 8 行就够了。CLI 的依赖树越小越好。
- **`ureq` 关掉默认的 `rustls`/`gzip`**：只连本机明文端口，用不上。

Tauri 已内置 tokio，`tauri::async_runtime::spawn` 可直接用，无需自建 runtime。

## 11. hook 对接的已核实结论与残留风险

以下结论对着 **官方文档 https://code.claude.com/docs/en/hooks** 和**本机安装的 Claude Code 2.1.296** 双向核实过：文档里的每个事件名（含 `PermissionRequest`、`StopFailure`、`PostToolUseFailure`、`TeammateIdle`、`PostCompact`）以及 `asyncRewake`、`disableAllHooks`、`statusMessage`、`hookSpecificOutput`、`agent_needs_input`、`notification_type`、`stop_hook_active` 等字段，都在 2.1.296 的二进制里存在。细节见 [api.md §4](./api.md#4-智能体接入)。

1. **Claude Code 有 33 个 hook 事件**，名字和大小写以该页面的事件表为准。其中 `PermissionRequest`（工具调用需要权限决策时触发）是「需要授权」的主信号，`Notification` 的 `permission_prompt` 是触发更晚的回落路径。映射表和**明确忽略**的事件清单见 api.md §4.2——把忽略项写清楚同样重要，因为 `TaskCreated`/`FileChanged` 这类事件频繁且与「一轮工作」无关，误用会让灯球乱闪。
2. **`"async": true` 是 `type: "command"` 独有字段**，且异步 hook **不受 `timeout` 约束**、**不能做决策**、**stdout 输出畸形 JSON 会崩溃会话**（v2.1.202 之前）。因此 CLI 必须自己限制 HTTP 超时，且 hook 模式下 stdout 必须为空。
3. **Codex 与 Cursor 都有 hook 系统**，字段与 Claude Code 大致同构（Codex 是 PascalCase + `session_id`，Cursor 是 camelCase + `conversation_id`），**不需要日志监听**。三家的配置路径、事件名、字段差异见 api.md §4.6 / §4.7。

仍然残留的风险：

- 事件处于活跃演进中，我们核实的是 2.1.296 这一个版本。映射表是 `match` 语句，将来加分支的成本很低；不需要为了「未来可能有新事件」预先设计抽象。
- Codex 的 `PermissionRequest` 输出 JSON 的确切键名只在解析器里见过（`decision`，未能确认是否为 `permissionDecision`）。我们不上报决策，所以不影响。
- Cursor 没有可直接映射的「需要授权」事件（它的授权是靠 hook 返回 `permission: allow|deny|ask` 实现的，上报型 hook 不返回该字段）。这是 Cursor 侧的能力缺口，不要假装有。
- Codex 的 `SessionEnd` 默认超时只有 1 秒（上限 3 秒），且总是同步执行——这条路径上的 HTTP 调用必须极快，超时要设得比其它事件更短。

### 11.1 「更多智能体」为什么不是加 `match` 分支就能解决的

上面六家（Claude Code / Codex / Cursor / Gemini CLI / Goose，加命令行上报的 Pi Agent）都是**逐家核实过**的。想把「市面上常见的智能体」都加进来，直觉是「加几条 `match` 分支」—— 但加一家需要三样确切信息：**配置路径 + 事件名 + handler 形状**，而这三样各家都不同、也都在变。

猜测的代价不是「不生效」，而是**静默失效**：`hooks.rs` 顶部那三条安全底线里，第二条（「解析失败就中止，绝不覆盖」）防的正是拿一个猜的格式去写用户的配置文件。所以本项目立的标准是「对着官方文档**和**本机二进制双向核实过才写」—— `§11` 开头那句就是它。

**`signalhub run`（api.md §4.13）是绕开这个问题的另一条路**：不猜格式，改成**包一条命令**。任何跑在终端里的工具都能这么接，对方不需要任何 hook 支持。它换来的代价是**状态粒度粗**（只有 working / done / error，报不出「需要授权」）—— 但那比「猜一个格式、装上去了、不报错也不上报」好得多。

**这一节也记下了接不了的**：只活在 VS Code 侧边栏面板里的扩展（Cline / Roo Code / Continue 这类）没有可包的进程、也没有可写的 hook 配置 —— 通用的两条路对它都不适用。**不要为了「覆盖面」假装支持它们。**
