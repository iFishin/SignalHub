# SignalHub 架构设计

跨平台桌面悬浮状态指示器。优先适配 AI 智能体，但不绑定智能体——任何程序都能通过统一的本地 API 上报状态。

- 框架：Tauri 2（Rust 后端 + React/TypeScript 前端）
- 平台：macOS / Windows / Linux (X11)
- 参考项目：[guan-ops/Agent-Signal-Bar](https://github.com/guan-ops/Agent-Signal-Bar)（原生 macOS/Swift，本项目是其跨平台重实现）

---

## 1. 核心判断

三条贯穿全文的设计决策，先说清楚：

1. **上报通道 = 本地 HTTP + 瘦客户端 CLI。** 不采用 Agent-Signal-Bar 的共享 JSON 文件方案。HTTP 让任何语言一行 `curl` 就能接入，可即时调试、有应答、且天然只允许单一写者，从而彻底消除多写者竞态。
2. **优先级保护实现在「聚合层」，不在「会话层」。** 会话内后写覆盖 + 跨会话取 max + TTL 兜底。见 §3.2——这是最容易设计错的地方。
3. **CLI 内置 `signalhub hook <agent>` 子命令**，直接消费智能体 hook 的 stdin JSON。这一个设计消掉了全部 shell 脚本和 `jq` 依赖，安装 hook 退化成「同一行命令注册到每个事件」。

## 2. 整体架构

```
┌──────────────────────────── 外部上报方 ────────────────────────────┐
│  Claude Code hooks    Codex hooks    Cursor hooks    CI / 脚本      │
└───────────────────────────┬────────────────────────────────────────┘
                            │ ① CLI（或直接 curl）
                            ▼
        ┌────────────────────────────────────────────────┐
        │  signalhub CLI (Rust, 无 Tauri 依赖)            │
        │   普通模式: signalhub working --session build-1 │
        │   hook 模式: signalhub hook claude-code ← stdin │
        │   → POST http://127.0.0.1:<port>/v1/state       │
        └────────────────────┬───────────────────────────┘
                             ▼  ② HTTP (127.0.0.1, Bearer token)
┌──────────────────────────── Tauri 进程 ────────────────────────────┐
│  axum Router (/v1/*)                                                │
│         │ ③ report() / clear() / set_paused()                       │
│         ▼                                                           │
│  SignalStore  Arc<Mutex<Store>>        ← 唯一真值来源               │
│    ├─ sessions: HashMap<SessionId, Session>                         │
│    ├─ paused: bool                                                  │
│    └─ aggregate() = max_priority(sessions)                          │
│         │                                                           │
│   ④ TTL sweep (250ms tick)        ⑤ emit_to("main", "signalhub://state")
│         │                                     │                     │
│  ┌──────┴──────┐                    ┌─────────┴──────────┐          │
│  │ Tray 图标    │                    │ 悬浮窗 Webview      │          │
│  │ 右键菜单     │                    │ (React + CSS 动画)   │          │
│  └─────────────┘                    └────────────────────┘          │
│  全局快捷键 → 穿透模式切换   设置窗 (独立 webview)                    │
└────────────────────────────────────────────────────────────────────┘
```

**单一写者原则。** 所有状态变更都必须经过 `Store` 的一个互斥锁。前端和托盘都是纯消费者，从不写状态。这是选择 HTTP 而非文件方案的根本原因——文件方案允许多个进程并发写入，必须自己实现原子写和锁文件，而 HTTP 服务端天然把写操作串行化了。

## 3. 状态模型与聚合

### 3.1 Signal 枚举

| 状态 | 优先级 | 静默超时 | 视觉（颜色 / 节奏） | 含义 |
|---|---|---|---|---|
| `error` | 50 | 300s | 红 `#d0342c`、频闪 340ms（`steps` 硬切） | 出错/阻塞 |
| `permission` | 40 | 600s | 红、平滑闪 900ms | 需要授权/确认 |
| `attention` | 30 | 300s | 黄 `#d99a06`、闪 1000ms | 需要关注 |
| `working` | 20 | 600s | 绿 `#16a34a`、慢闪 1600ms | 正在执行工具 |
| `thinking` | 15 | 600s | 绿、快闪 640ms | 正在推理 |
| `done` | 6 | 180s | 绿、常亮 + 一次入场脉冲 380ms | 任务完成（到期直接消失） |
| `idle` | 2 | 600s | 绿、常亮 | 空闲，无任务 |
| `stale` | 1 | 300s | 灰 `#9ca3af`、常亮 | 会话已沉默（派生） |
| `offline` | 0 | — | 灰、常亮、opacity .45 | 没有任何会话（派生） |
| `off` | 0 | — | 灰、常亮、opacity .45 | 监控暂停（派生，全局开关） |

「静默超时」是会话转入 `stale` 的时限；`stale` 那一行则是它被真正删除前的宽限期。`offline` / `off` 不是会话状态，所以没有意义。

**视觉取向是朴素简约**：纯色圆点，没有发光、没有渐变、没有阴影。状态靠**颜色 + 明暗节奏**表达，不靠装饰。颜色值比常规的 500 号色深一档——扁平色块没有描边也没有阴影，太亮的颜色在浅色桌面上会糊掉。

三个关键区分：

- **`off` 不是会话状态，是全局开关。** `paused = true` 时无论多少会话在报绿都显示熄灭灰。CLI 的 `signalhub off` / `on`（或 `monitor off` / `on`）操作的是这个全局位，不是某个会话。
- **`done` 和 `idle` 颜色相同**，靠一次性的入场脉冲 + 180s TTL 收敛来区分。这是刻意的：`done` 是确认反馈，`idle` 是稳态。180 秒是「离开一会儿回来还看得到」和「别赖着不走」之间的折中，可在「行为 → 静默超时」里调。**牌到期走掉之后，灯不会立刻翻脸说「没有智能体在上报」** —— `Store::last_done` 记着最近一次完成的墙钟时刻（`Snapshot::last_done_ms`），十分钟之内空状态改说「刚完成 · N 分钟前」。这份记忆不参与聚合、不参与过期、也不进 `Visible` 的比对，纯粹是给空状态补一句话：它比会话活得久，因为 `done` 到期是被整个删掉的，会话一没就再没有别人记得这件事了。
- **`stale` / `offline` / `off` 是派生状态，不能上报。** 它们是聚合出来的结果，不是外部程序该声称的状态；`Signal::parse` 会明确拒绝它们。三者的视觉差异与取舍见 §3.5。

圆点直径默认 **22px**，可在设置里选 16 / 22 / 32。窗口尺寸由 Rust 侧按可见圆点个数和设置算出（见 §3.7），设置变更和会话数变化时都会同步调整。

`Signal::priority()` 返回上表的数值，聚合时取 max。

### 3.2 聚合算法（核心决策）

规则是「红 > 黄 > 绿，高优先级状态不被普通工作事件覆盖」。有两种实现路径：

**方案 A：会话级单调守卫（不采用）**

```rust
// 新事件优先级低于当前状态时丢弃
if new.priority() < current.priority() { return; }
```

看起来正好实现了规则，但有致命场景：

```
会话 A: PreToolUse        → working(20)
会话 A: PermissionRequest → permission(40)   🔴
用户点了「允许」
会话 A: PostToolUse       → working(20)      ← 20 < 40，被守卫丢弃
                            结果：灯一直是红的，直到 600s TTL 过期
```

要修就得引入 `resolve` 标志、事件白名单……复杂度上升且状态机会卡死。

**方案 B：会话内后写覆盖 + 聚合取 max（采用）**

```rust
impl Store {
    /// 会话内部：最新事件直接覆盖（last-write-wins）
    pub fn report_at(&mut self, now: Instant, session: &str, /* ... */) -> bool {
        let before = self.aggregate();
        self.sessions.insert(session.into(), Session { /* ... */ });
        before != self.aggregate()      // 聚合变了才需要推前端
    }

    /// 聚合：跨会话取最高优先级 —— 「红 > 黄 > 绿」就实现在这里
    pub fn aggregate(&self) -> Signal {
        if self.paused { return Signal::Off; }
        self.sessions.values()
            .filter(|s| s.state != Signal::Off)
            .max_by_key(|s| s.state.priority())
            .map(|s| s.state)
            .unwrap_or(Signal::Idle)
    }
}
```

为什么这就够了：

- 规则真正要防的场景是「A 会话在等授权（红），B 会话还在跑工具（绿），绿灯事件不该顶掉红灯」。取 max 天然解决——B 报 `working`(20)，A 仍是 `permission`(40)，聚合保持红。
- 用户批准后 A 自己发 `PostToolUse → working`，A 的红消失，聚合自然回落。**没有停滞状态。**
- 单会话（最常见的场景：只有一个 Claude Code）根本不存在跨会话覆盖问题。
- `done` 靠 TTL 自动回落 `idle`，不需要人为清场。

如果将来发现某个上报方事件过密导致红灯被同行会话的正常进度掩盖，再加一个 `hold: true` 字段（只允许显式清除）即可。v1 不需要。

### 3.3 四个兜底机制（缺一不可）

| 机制 | 作用 | 缺失后果 |
|---|---|---|
| 每状态默认 TTL | 会话静默超时后转 `stale` | 智能体崩溃在 `working`，灯会一直绿闪到 TTL 到期 |
| 全局 sweep 任务（250ms） | 定期检查过期并重算聚合 | 过期了但无人触发重算，前端收不到更新 |
| `SessionEnd` hook → 清除会话 | 正常结束立即清场 | 跑完的会话残留，多会话界面混乱 |
| `stale` 宽限期（30 分钟） | 沉默的会话先标记再删除 | 「智能体不说话了」和「智能体空闲」分不开 |
| 一切都有 TTL | 没有任何状态能永远粘住 | 早先 `idle` 没有 TTL，一个忘关的会话能显示半小时「空闲」 |

**每个状态都有 TTL 是刻意的**（`default_ttl()` 是个全函数，不再返回 `Option`）。早先 `idle` 没有 TTL，靠「30 分钟无事件回收」兜底——那段窗口太长，正是「智能体走了灯还亮着」的成因之一。现在 `idle` 也有 600 秒窗口。

**「忙碌」那两个的窗口刻意给得很宽（`thinking` 600 秒、`working` 600 秒），这条方向改过两次。** 早先它们是 60 / 90 秒，理由是「干活时每次工具调用都会触发 hook，静默这么久基本可以断定不在工作」—— 这条推理漏了一半：**模型思考、或者跑一段没有工具调用的长回复时，一个事件都不触发**。于是「智能体正在思考」这件事本身就会把灯推成沉默，再过五分钟干脆变成「没有智能体上报」，而智能体明明在干活。这是用户实际报上来的体验问题。

放宽的代价是崩溃的智能体晚一点被发现 —— 但那时它只是转成 `stale`（「沉默」），用户仍然看得到它，比「活着的智能体看着像死了」轻得多。**这个数值仍然直接决定「智能体消失后灯还会错多久」**，是调优时最该动的一个旋钮。（`feedback` 与 `permission` 这类「要你处理」的状态另有 300 / 600 秒窗口，不该动它们 —— 那些状态正是要粘住的。）

**带进程号的会话不靠这条窗口兜底。** sweep 的探活把「pid 还活着、又没收到结束事件」读成「它还在这一轮里」：TTL 到了只续期，**不**把 `working` / `thinking` 降成 `idle`，也不清掉「正在跑什么」。长任务（20 分钟的构建、十分钟的推理）在整段时间里保持原状态；一轮什么时候结束由智能体自己的结束事件（`Stop` / `agent_end` / `execution.succeeded` …）说了算，进程没了则下一拍立刻收掉。早先这里会在 TTL 到期时降成 `idle`，于是「跑了几分钟就自己暗下去」—— 那是拿「多久没说话」当「有没有在干活」，对长任务正好是反的。`permission` / `attention` / `error` 不适用这条（进程活着不能说明授权已经批了）。

没有进程号的接入（Codex / Cursor / Gemini / Goose / CSC / WorkBuddy，以及没重装过的旧 hook）仍按上面的 TTL 走 —— 它们的长任务在 `working` 600 秒后还是会转 `stale`，因为「没事件」和「进程没了」在那一侧仍然分不开。真遇到更长的静默，可以在「行为 → 静默超时」里把这一档再放宽，或由上报方显式带 `ttl_ms`。Windows 的命令式 hook 由 CLI 沿父进程链补 pid（`win_pid.rs`），但那是**保守近似、真机未验**，找不到就仍走这条路；插件式在 Windows 上本来就有 pid。

### 3.4 `stale`：把「不说话了」和「空闲」分开

会话静默超过 TTL 后**不再直接消失，而是转入 `stale`**，再保留 `STALE_GRACE` 才真正删除。`done` 是唯一的例外——它的语义就是「完成，回到常态」，到期直接消失。

**宽限期从 5 分钟放到了 30 分钟**，和上面那条是同一个体验问题的另一半：5 分钟太短，一个跑长任务的会话超过这个时间没有事件就会从灯上彻底消失，用户看到的是「没有智能体上报」。`stale` 本身已经是「它不说话了」这个信息，没必要那么快升级成「它不存在」。（细环画的就是这一段的剩余比例，所以这个值同时决定环缩短得多慢。）

这一层解决的是个真实问题：智能体崩溃、被强杀、或 `SessionEnd` 没触发时，会话会停在最后一个状态上。没有 `stale` 的话，用户看到的和「智能体正忙」完全一样，只能等 TTL 到期。

`stale` 的优先级**低于 `idle`**：一路会话在报 idle（活着）时，不该被另一路已经沉默的会话盖成灰的。

### 3.5 三档「不在工作」

灰色这一族有三个状态，语义必须分清：

| 状态 | 含义 | 视觉 |
|---|---|---|
| `stale` | 有会话，但它不说话了 | 灰、常亮、不透明 |
| `offline` | 一个会话都没有 | 灰、常亮、更淡 |
| `off` | 用户主动暂停监控 | 灰、常亮、更淡 |

`offline` 与 `off` 视觉一致是**刻意的**：它们都表示「没有在追踪任何东西」，差别只在语义，由 tooltip 和设置面板说明。22px 的圆点里塞不下第三种可区分的灰——与其造一个谁也看不出区别的颜色，不如承认这一点。

`stale` 与它们的不透明度差异是能看出来的，所以保留了。三者都不闪：它们都不是「有活动」。

### 3.6 非颜色编码，以及可辨识性

颜色不是唯一的信息通道，有三处刻意的例外：

**形状（色盲友好）。** 默认 `permission` / `error` 画成圆角方形，其余状态是圆形。红绿是色盲最难分的一对，而这两个恰好是最需要你注意的状态——一种形状区分就解决了关键场景，比换掉整套配色克制。约 8% 的男性分不清红绿，这不是审美问题。这条规则现在是「跟随全局形状」时的默认，解析在 TS 里（见 §3.6.1），用户给某个状态单独指定了形状就以用户的为准。

**细环（沉默时长）。** `stale` 圆点上的细环按剩余宽限期缩短，从满圈到消失。数值由服务端算好（组上的 `stale_progress`）而不是前端自己算——`age_ms` 是「距上次状态变化」，并不等于「沉默多久」，前端要算就得复刻一遍 TTL 常量。前端只把它塞进 CSS 变量 `--progress`，`lamp.css` 的 `ring` 形状直接拿它算 `conic-gradient` 的角度。

**环要会动，而推送不能滥。** 细环是连续的 0.0–1.0，如果直接参与 `sweep` 的前后比对，每 250ms 都会比出「有变化」——于是整段宽限期里灯球每秒重排 4 次，而细环服务的恰恰是「省着看」的状态。所以 `Visible` 里放的是**档位**（`progress_step`，16 档）：跨档才推一帧。为此 `Store` 要记住 `last_pushed` 那一帧 —— `expire` 一次调用的前后是同一个 `now`，不靠基线的话跨档永远发现不了，环就会停在转 `stale` 那一刻的长度上直到会话消失，比不画更误导。

**空闲时 sweep 不建快照。** 它每 250ms 醒一次，而快照要给每个组克隆名字和消息、还要排两次序 —— 零会话时也在每秒白算四遍。现在只在 `expire` 真的报了变化之后才建（**仍然在同一把锁里**：先解锁、变了再重新加锁的话，两次之间别的线程可以改 store，推出去的快照和「什么变了」这个判断就对不上了）。

**组的环取决定聚合那个会话的进度。** 组内两路都沉默时，圆点是因为聚合值更高的那一路才变 `stale` 的，环要缩短的自然也是它。取组内第一个的话，画出来的是另一路的进度——而用户眼里只有一颗点。

**明暗（安静模式）。** 空闲 / 沉默 / 离线时整体压到 0.15 不透明度，只有真正有活动或需要你注意时才完全显形；鼠标悬停恢复（否则压暗之后找不到它来拖）。`done` 也算「有事」——它是任务完成的确认，压暗就失去意义了。可在设置里关掉。

**穿透时安静模式必须让路。** 这条是死锁，不是偏好：安静模式唯一的恢复路径是 `.lamp-root:hover`，而穿透开启后窗口 `set_ignore_cursor_events`，hover **永不成立** —— 于是灯变成一颗永远 0.15、点不到也拖不动的点，比关掉还糟。所以灯上在穿透时直接把 `data-quiet` 收掉，`lamp.css` 里再留一道 `[data-quiet][data-pass-through] { opacity: 1 }` 兜底。

**截断要说出来。** 灯上最多 `MAX_SIGNS`（4）块牌，超出的被服务端截断 —— 而**灯的聚合是全体的**，于是「灯上只有三块、托盘/通知说的却是第四块的状态」。第 4 块牌的牌尾加一枚 `+N` 角标，tooltip 里列出被收起来的组名。展开态那枚 `flex: none` 寄住在已有的那块牌里，挤掉的是 `.sign-body`（组名先省略），所以**展开态的窗口尺寸一个字都不用改**；折叠态没有牌面可寄住，它得像暂停那枚一样单独占一个点位（`config::more_badge` 决定出不出现，几何见下）。

**暂停和穿透都要持续可见。** 两者原先只有一个颜色变化，而 `off`（暂停）和 `offline` 都是很淡的灰，分不出来；穿透更糟 —— 鼠标点不到它，开启时那条一次性通知早就忘光了。现在两者各在牌尾挂一枚**持续存在**的角标（同时出现时穿透优先），tooltip 带上逃生快捷键：那个状态下谁也点不开设置面板去查，这条信息必须跟着角标走。折叠态没有牌面可寄住，角标单独占一个点的位置，所以 `collapsed_window_size` 要为此多算一个点 —— 加上 `+N` 那枚，折叠态最多同时有两枚角标。

**牌面的颜色变量挂在根上，不在 `.sign` 上。** `--sign-bg` / `--sign-line` / `--sign-fg` / `--sign-muted` 一度只声明在 `.sign` 里 —— 展开态没问题（牌就在那儿），**折叠态一个 `.sign` 都没有**：只有一排点、外加两枚角标。于是那两枚取不到 `--sign-line`（描边退回 `currentColor`）、取不到 `--sign-bg`（底色变透明），在透明窗口上就是一枚黑圈黑字 —— 而其中一枚恰恰是「穿透中，鼠标点不到我」，最不该看不见的那枚。现在它们声明在 `.lamp-root` 上，两种形态都取得到（`--sign-bg` 里的 `var(--sign-alpha)` 也在同一层解析，值不变）。

**可读性靠滑杆下限 + 提亮次要文字，不靠给字描边。** `--sign-bg` 是 `rgba(28,28,32, --sign-alpha)`，牌里的字是近白的 `#ececef`（组名）和 `#c2c2cb`（状态、消息、时长）—— 对比**全部**来自牌面那层深色。α 低到一定程度，从牌面透出来的桌面比牌面本身还显眼，字其实是画在**桌面**上的：近白的程序窗口、浅色壁纸上就淡得看不见。所以 `sign_opacity` 的下限是 **65**：`config::MIN_SIGN_OPACITY` 和 `src/lib/lampStyle.ts::SIGN_OPACITY_MIN` 是同一个数字的两份声明（前端拿它当滑杆的 `min`，Rust 在 `Settings::clamped()` 里夹住手改的 config.json、以及旧版本存下的 0–64）。**65 是量出来的**：同一块牌按 50/60/65/70/78/86 排一列铺在近白窗口（`#fbfbfc`）与浅灰壁纸（`#cfd3da`）上对照，50% 时次要文字对比只有约 1.1:1（那不是淡，是消失），60% 余量太小，65% 才稳。想要更「隐形」的灯走另一条路：**安静模式**（没事时整盏压到 `opacity: 0.15`），那条路上本来就不指望你读字，也就不存在「字读不清」。

**「灰字太灰」是第二个病因，得一起治。** 次要文字原来是 `#9b9ba3`，就算牌面满不透明，它在浅底上也只有 3.9:1 —— 用户报的「提示字体的颜色是灰色，在浅色程序上根本看不清」一半是这个原因，另一半才是牌面太淡。现在提到 `#c2c2cb`：与组名（`#ececef` + 600 字重）仍有明显差距，层次靠字重和字号继续表达，不必靠压暗字色。**只抬下限不动字色等于让灰字配更深的灰底**，两件事必须一起改。

**曾经给字加过描边，已经撤掉。** α < 50 时补一圈四向深色 `text-shadow`（`[data-sign-translucent]`，宽度 `max(0.75px, 0.09em)`）确实能让浅色桌面上的字读得出来，但代价是笔画被边吃掉、小字号糊成一团、近白字心配黑边读起来像空心字——用户看到的是「这块牌被救过」，不是「这块牌好看」，而且这层观感问题没法靠调参解决。所以不再事后补救，改成在源头取消那个状态：滑杆到底就是 65%，牌底始终保持足够的深色托着浅字。安静压暗（`opacity: 0.15`）也因此不再触发任何换字逻辑——安静的本意就是「别读我」，压暗了还描一圈边反而更扎眼。

**为什么不去读桌面颜色做反色。** 那要拿灯后面那块桌面的像素（macOS 上是 CoreGraphics / ScreenCaptureKit），必须先获得「屏幕录制」权限；这个应用是 ad-hoc 签名的，每次更新 cdhash 都变，授权大概率还要重给。为一个常驻小灯付这个代价不划算——这也是当初选描边的原因（不依赖背景信息）。描边撤掉之后这条判断仍然成立：**下限**本身就是不依赖背景信息的解法。悬停只把安静压暗的牌恢复不透明，不改牌面的 alpha——那是滑杆决定的。

**折叠 / 展开要有反馈。** 单组时切完连窗口尺寸都不变，没反馈就等于「点了没反应」。给一次性 opacity 脉冲 —— **不能用 transform**：本文件 §4.5 对常驻窗口有一条硬约束是「动画只动 opacity」，动 transform 会让它每帧重排。

**牌面（可辨识性）。** 灯球现在是一块**深色圆角牌**：彩点 + 组名 + 状态 + 已持续，有消息时多一行。深色牌面是刻意和**应用图标**同一套语言（深色圆角方块 + 彩点），这样悬浮灯和图标看起来是一个东西。

这一步替换掉了上一版的「外壳」（一圈中性细环）：外壳是给「孤立圆点不够像灯」打的补丁，而牌本身就是那个框，再在牌里套一圈纯属多余。**要的是结构（外框、底色、文字位），不是装饰（阴影、发光、渐变）**——朴素简约仍然成立。

**牌面按「在等我」分两档。** 灯上同时有好几块牌，抢的是同一份余光 —— 早先四块同底、同点径、同字重，「等你授权」和「刚跑完」读起来一样响，只能逐块读字才知道该先看谁。判据是 `lampStyle.ts::toneOf`（有单测），只有两档：`need`（授权 / 关注 / 出错）点径 `0.72×size`、牌底不动；`calm`（其余七个）点径 `0.55×size`、牌底 ×0.72、组名 400 字重。**`done` 刻意归 calm** —— 它值得看一眼但不需要你动手；算进 need 的话，一个上午跑完十件事，整叠牌全是「要你」的分量，分层就白做了。三样都不参与布局（点径是 CSS 变量、牌底是 `background`、字重是 `font-weight`），牌宽高仍由 `config.rs` 与 CSS 共享那两个值。**占位牌不参与**：它不是某一块组牌，是整盏灯的自述，那句「没有智能体在上报 / 刚完成 · N 分钟前」正是回来时最该读的一句话。**只有一块牌时也不分层** —— 分层是在多块之间分先后，一块牌没有比较对象，压淡只换来「整盏灯退一档」；而 `group_by` 默认是 `none`（所有上报归一组，也就是一块牌），不能让最常见的那种用法无故变淡。

**状态词用两字短词。** 牌宽固定（22px 档 154px），长词（「需要授权」「出错 / 阻塞」）光状态就吃掉 40–53px，组名常被截成五六个字符。灯上用 `Messages::shortSignal`（「授权」「出错」），长词留给 tooltip、收件箱和设置面板。**也不能干脆不显示**：`working` 和 `done` 默认同色，只靠「慢闪 / 常亮」区分，静态一瞥分不出来。

**跃迁闪的是描边，不是整块牌。** 状态一变，那块牌的边框从状态色淡回常态色（420ms，`edge-flash`）。早先是整块 `opacity: 0.35 → 1`：在透明窗口上读起来像「这块牌消失了一下」，而且在低透明度设置下会有一段明显更淡、几乎读不出字的中间态。要拿到状态色，`.sign` 自己也得挂 `data-state`（`state.css` 的 `[data-state] { --state }` 才在牌这一层生效）。上面 §3.6 那条「折叠 / 展开要有反馈」仍然只动 opacity —— 那个要的是「整块牌应了一声」，不是「这一格更新了」。

### 3.6.1 用户可以调的外观

| 外观预设 | 单灯 / 紧凑 / 标准 / 醒目 | 一次设好下面几项，见下 |
| 形态 | 展开牌面 / 一颗灯 | 展开是默认（灯的本职是一眼看到状态），折叠是「让出地方」 |
| 大小 | 小 / 中 / 大 | 整块牌的尺度（牌宽、牌高、字号、灯的大小都由它派生） |
| 形状 | 圆 / 圆角方 / 环 | 全局默认；**环**在桌面上几乎没有别的东西会撞脸 |
| 配色 | 默认 / 色盲友好 / 高饱和 | 全局默认（起点） |
| 背景透明度 | 65–100（`--sign-alpha`） | 调低能看见桌面；**下限 65%**，再淡浅字就落在桌面上（见上）。更隐形请用安静模式 |
| 牌宽 / 牌高倍率 | 0.8–2.5（1.0 = 原样） | 只放大 / 缩小展开态的牌本身，窗口跟着内容走 |
| 牌间距 | 紧凑 / 标准 / 宽松（0.5× / 1× / 2×） | **唯一影响窗口高度的一项**：牌竖着叠，间距大了窗口就变高。所以只有三档，且两处真值（`SignGap::px` ↔ `lamp.css` 的 `gap`） |
| 字体 | 系统无衬线 / 整块等宽 | 等宽把组名、状态、消息一起换掉，读起来像一段终端日志；不碰几何 |
| 闪烁节奏 | 50–200（100 = 原始） | 全局默认倍率；闪得太快会分心，太慢又看不出在动 |
| 牌上显示 | 圆点 / 组名 / 状态 / 已持续 / 消息，各自可关 | 有人只要一眼颜色，有人要看清「卡在哪一步」，也有人只想要一块纯文字卡 |
| 边灯 | 不亮 / 顶边 / 四边 / 辉光 | 把状态色**铺到面积上**；牌宽就那么大，字已经排到第四行，再多信息只能往「不写字」的方向走。见 §3.35 |
| 角灯 | 四角各自：空 / 状态色 / 置顶 / 静音 / 将过期 | 四个角是四个独立的是 / 否位，回答的正是那几件「只想知道有没有」的事。见 §3.35 |
| 安静模式 | 开 / 关 | 在「行为」页 —— 它和贴边吸附、点击穿透同属「灯怎么动」，见 §3.16 |
| 每个状态的外观 | 颜色 + 形状 + 节奏，逐个覆盖 | 「外观」页末尾那张**折叠**的表（见 §3.16） |
| 每个状态的停留时长 | 30 秒 – 24 小时，逐个覆盖 | 「智能体不出声之后这块牌还留多久」，见下 |

**外观预设**（`src/lib/presets.ts` 的 `presets()`）一次设好大小、形态、牌上显示、背景透明度、闪烁节奏，以及质感里的圆角 / 描边 / 字号 / 字体 —— 它们互相牵制（牌面调透了就得把字调少、字多了就得把牌调大），让用户一个个试很难试出一套协调的组合。预设**刻意不含形状和配色**：那两项是语义性的（形状承载色盲区分、配色承载「红 = 危险」），混进同一个预设里会让人以为换个风格就会顺手把配色改掉。同理**也不含牌底（`sign_tint`）、分层（`sign_emphasis`）和间距（`sign_gap`）**：前两个是材质与语义，间距则是唯一会改窗口高度的一项 —— 而预设的承诺是「换风格不改窗口大小」。预设**只在前端**，不进 `Settings` —— 它不是一个状态，只是「一次把几个字段设成一组值」。

**牌间距是外观里唯一会改窗口几何的一项。** 牌竖着叠，间距直接进窗口总高，所以它不能像圆角、字号那样「随便调」—— 取值只能是三个离散档（`config::SignGap` 的 `px()` 与 `lampStyle.ts::SIGN_GAP_MULT` 是同一个倍率的两份声明，`lamp.css` 的 `.lamp-signs { gap }` 也从它取）。默认档 1.0 **逐字等于旧公式** `size / 2`，且 Rust 侧是先取整再乘、乘完向上取整 —— 方向和 `sign_width` 一致（只许多留，不许裁）。这也是它不进外观预设的原因：预设承诺「换风格不改窗口大小」。

**字体只改字形，不改几何。** `data-sign-font="mono"` 把整块牌换成 `ui-monospace` 一族，组名 / 状态 / 消息 / 时长一起换 —— 代价是等宽字形更宽，长组名会早一点出现省略号。这是这个开关唯一的代价，也是它为什么只做两个选项：再多的字体档位在这个字号下分不出「好看」，只分得出「塞不下」。

**关掉圆点（`show.dot`）不影响几何。** 圆点本来就在牌的 flex 行里，关掉它只是让文字往左挪 —— 牌宽高仍由 `sign_width` / `sign_height` 算，所以这个 chip 和另外四段一样可以随便关。

**闪烁节奏**是一个倍率（数字越大闪得越快）。但它**只作用于用户没单独设节奏的状态** —— 见下面「逐个状态」那一层。

**停留时长（`styles.<状态>.ttl_ms`）不是外观，但和外观放在同一张表里。** 它管的是「智能体不出声之后，这块牌还在灯上待多久」—— 调它的场景永远是「我盯着**某一个**状态觉得它消失得太早 / 太晚」，而那时人已经在看这张表了。三级优先写在 `state::state_ttl` 一处：**上报方显式给的 `ttl_ms`**（CLI 的 `--ttl`、HTTP 字段、包装器心跳、测试上报）> **用户设的** > **内置默认**（`Signal::default_ttl`）。显式排在最前，是因为它来自**那一次调用**，比「我一般想让工作态活多久」更具体 —— 反过来就是「设置里改过之后 `--ttl` 再也不生效」，而那种坑只有等一条长任务被误杀时才会被发现。

**刻意没有「永不过期」这一档**（`config::MIN_STATE_TTL_MS` / `MAX_STATE_TTL_MS`，1 秒 – 24 小时）。一盏不会自己熄灭的灯等于一条永远不撤的告警：智能体被强杀（`SessionEnd` 没触发）之后它会一直亮着，用户拿它没办法。这个仓库已经踩过一次 —— `idle` 早先没有 TTL，一个忘关的会话能在灯上挂半小时。

**它只在「上报进来的那一刻」算一次，不追溯**：`expires_at` 是上报时写死的，所以改了设置要等下一次上报。追溯会让「刚才还亮着的牌突然消失」，而它消失的理由（你改了配置）在灯上根本看不见 —— 那种「东西自己没了」比「改完要等一会儿」难解释得多。

**「跟随」那一档要标出内置默认（`跟随 5m`）。** 这一列问的恰恰是「到底多久」，只写「跟随」两个字等于没答；而那个数的真值在 Rust（`Signal::default_ttl`），所以由 `state_ttl_defaults` 命令推给前端（`lib/useStateTtls.ts`），前端不存第二份 —— 存了的话，改了 Rust 这边不会报错，只会**悄悄显示错的**。拿不到（不在 Tauri 里）就退回纯「跟随」，功能不受影响。

**`off` / `offline` / `stale` 三行这一格是空的。** 前两个永远不会成为会话状态（`off` 在 `apply` 里等价于清除会话，`offline` 是汇总产物），`stale` 是**静默超时之后**的派生状态、那一段宽限期是固定的（`STALE_GRACE`），而且细环画的就是那一段的剩余比例 —— 让它可调就得连那个环的算法一起改。

**`show.message` 不是纯外观。** 牌有没有消息那一行决定了窗口高度：`lib.rs` 的 `visible_groups` / `sign_heights` 必须和前端 `data-has-message` 算出**同一个**布尔值（消息存在**且**用户没关掉那一段），否则窗口会裁掉最后一块牌。

**设置行有一套通用件，不只服务外观。** 三条，都是「同一件事别散在四处」的推论：

- **说明跟着它解释的那一行走**（`Row` 的 `hint`，写在该行名字下面）。原先一页五六条 `.hint` 全堆在页尾，和它解释的那一行隔了十几行 —— 读的时候根本连不上。「形状只影响灯珠」这句话不写在「形状」那一行底下，就等于没写。
- **每行一个「恢复默认」**（`Row` 的 `onReset` + `resetFor`）。判据是 `lib/useSettings.ts::DEFAULTS` —— 导出 / 导入、Rust 的 `Default::default()` 用的都是它，所以**不存在第二个默认值**。因此只有「背后是 `Settings` 字段」的行才有 ↺：点击穿透 / 开机自启 / 通知权限背后是运行期状态，没得可恢复；预设那行一次改五个字段，给它挂 ↺ 会被读成「撤销上一个预设」。↺ **只在当前值偏离默认时出现**，于是它顺带成了一个「这一行被我改过」的记号。位置在名字右边、不在控件右边：否则右边那个控件会随着「这行改过没有」左右跳。
- **一张实时预览**（`LampPreview`，在「外观」页顶部）。改外观的时候你不一定看得见那盏灯 —— 它可能被别的窗口挡住、收成了一排点、或者在你正看着的这块屏之外。预览用的是**灯自己那套变量和类名**（`lampVars` + `.lamp-root` / `.sign` / `.dot`），所以大小、形态、形状、配色、透明度、节奏、牌宽高倍率全都跟着变，一个都不用在这里重算；代价是那份标记是照着 `SignalLamp` 写的，那边改了结构这边要手动跟上（后果止于观感，不会出错）。为此 `--sign-alpha` 从 `SignalLamp` 的内联样式里挪进了 `lampVars()` —— 两处各写一遍的话，预览显示的透明度和真正的灯迟早对不上，而**「预览和灯不一样」比没有预览更糟**。

**而这一行以前对 hook 用户永远是空的** —— 值得记一笔，因为它是「一个功能做完了但没接上」的典型。`hook` 模式组装请求体时只发 `state` / `session` / `agent` / `cwd`，从来不填 `message`；唯一能填的是命令行上的 `--message`，而装出来的 hook 命令是 `{program} hook {agent}`，一个选项都不带。于是：`show.message` 默认开着、窗口高度也为它留了第二档，**而走 hook 接入的人（绝大多数）永远看不到那一行**。`tool_name` / `tool_input` 却一直躺在 payload 里没人用。

现在由 CLI 从工具事件压成一句话（`tool_summary`，见 api.md §4.14）。三条设计约束写在那儿了，其中两条是这个仓库反复踩过的坑：**绝不把整条命令打出去**（它会进灯的状态、通知正文和消息流，而 `command` 可能带密钥），以及**认不出来就显示工具原名、不猜动词**（`TodoWrite` 里有 "write"，关键字匹配会一路认错）。第三约束是形态上的：服务端**每次上报整体替换** `message`，所以 `PreToolUse` 和 `PostToolUse` 都得带 —— 只带一个的话，牌上那行会在两步之间闪一下空。

**`show.age`（已持续）反过来不碰几何，但有一个别处没有的依赖。** 它是同一行里靠右的一段（`flex: none`），不占额外的行，所以 `sign_heights` 不管它。但这个数字是**算出来的**（`now - since`），而灯球只在状态变化时重绘、`sweep` 也只在会话真的过期时才推事件 —— 于是没有任何东西会让它随时间重绘，它会永远停在状态刚变化那一刻算出的 **0s**（`formatAge` 里的 `Date.now()` 只在重绘那一刻被求值，而那一刻的答案恰好就是 0）。所以灯球里挂了一个 `useNow`（`src/lib/useNow.ts`），每秒推一次「现在」。**加任何「算出来的时间显示」之前，先想清楚谁让它重绘。**

**逐个状态：颜色 + 形状 + 节奏。** 全局的 `palette` / `shape` / `blink_speed` 是**默认值**，「灯效」页可以逐个状态覆盖，存在 `Settings.styles: BTreeMap<String, StateStyle>` 里：

```rust
pub struct StateStyle {
    pub color: Option<String>,   // #rrggbb
    pub shape: Option<Shape>,
    pub blink_ms: Option<u16>,   // 0 = 常亮
}
```

**三样都是可选的，没写 = 跟随全局**（颜色跟随 `palette`、形状跟随 `shape`、节奏跟随 `blink_speed`）。为什么是「可选的字段」而不是「填满的表格」：默认值会随版本演进（新增状态、调整默认节奏、改配色），如果用户配置文件里存着一份填满的表，那些改进就永远到不了他那儿。空着 = 跟随，是唯一能让默认值继续演进的表达。这和 §3.13 的 `#[serde(default)]` 是同一个道理。

旧的扁平 `colors` 表会被 `migrate_legacy_colors` 搬进 `styles` 的 `color` 字段，字段本身标了 `skip_serializing` **永不写回** —— 和 §3.10 的旧 `webhook_url` 同一个套路。不搬的话，用户已经调好的颜色会在升级后静默变回默认。

`clamped()` 的清理规则（手改配置文件属于系统边界）：`blink_ms` **恰好为 0 是合法的**（常亮），其余夹回 120–4000ms；颜色格式不合法就丢掉那个颜色，但**同一状态上别的覆盖要留着**；三样都没写的条目**整条丢掉**（它没有任何作用，留着只会让「当前是哪套预设」的判断无谓地失败）；不认识的键名**刻意保留** —— 静默删掉用户写的东西是数据丢失，键名合法性是 `validate_settings` 的职责（它会明确报错）。

**解析在 `src/lib/lampStyle.ts`（前端）**，`resolveShapes` / `resolveAnimations` / `lampVars` 三个函数。两条有实据的规则：

1. **全局 `blink_speed` 倍率只作用于用户没单独设 `blink_ms` 的状态。** 否则「我把 error 调成 300ms」会在全局滑杆一动之后就变得不是 300ms 了 —— 用户给某个状态定的节奏是他明确的意图，不该被一个全局旋钮悄悄改掉。用户显式设的 `blink_ms > 0` 一律变成一个朴素的 `pulse`（于是 `done` 那个一次性的 `pop`，只要用户给它设了节奏，也会变成一个真的会闪的灯）；`0` 变成 `none`。
2. **色盲的形状区分从 CSS 挪到了 TS。** 全局形状是「圆」时，`permission` / `error` 解析成 `rounded`。原来这条写在 CSS 里（`[data-shape="circle"] .dot[data-state=…]`），现在形状是**逐元素**的（一个窗口里多块牌可以是不同形状），根上挂一个值不够用，只能挪到 TS 里算。它只属于**跟随全局**的那部分 —— 用户显式给某个状态指定了形状就照用户说的来（他要给 `permission` 画圆环，那是有理由的）。

**CSS 也随之调整**：`data-shape` 从窗口根挪到**每个灯珠**上（形状是逐元素的了）；每个状态的 `animation` 由 `--anim-<状态名>` 变量驱动，兜底值就是原来写死的那条，所以样式表单独也能用（和 `state.css` 的 `var(--c-idle, 兜底)` 一个思路）。`--blink-speed` 变量去掉了 —— 倍率现在在 TS 里做除法。

**灯效预设**（`STYLE_PRESETS`）与外观预设是**两组不同的问题**：外观预设管「整块牌多大、多透、显示哪几段」，灯效预设管「红灯和绿灯怎么区分开」。混在一起会变成一套谁也说不清的组合，所以分开。四套 —— 跟随全局 / 形状区分 / 节奏分级 / 只在需要时闪 —— 每套给的是**完整的一份 `styles` 表**，应用就是整份替换，所以「当前是哪一套」可以靠逐字段相等判断出来；用户改掉任意一格，高亮就消失（它已经不是那一套了）。

**配色仍然是两层：预设 + 逐个覆盖。** 配色方案（默认 / 色盲友好 / 高饱和）是起点，用户的逐个覆盖优先 —— 可以先选「色盲友好」，再单独把 `error` 调成更醒目的红。只给预设是不够的：不同桌面背景、不同显示器、不同人对颜色的判断差很多，最终得让用户自己调；但一上手就让人从空白开始配，很容易配出一套自己都认不出的灯，所以预设仍然保留。

**颜色在 TS 里解析，不在 CSS 里。** 「预设 + 逐个覆盖」需要一层解析逻辑；写在 CSS 里会变成 10 状态 × 3 套配色的规则矩阵。所以 `lib/palettes.ts` 算出每个状态最终的颜色，转成一组 `--c-<状态名>` 变量挂在窗口根元素上，`state.css` 只负责消费（`var(--c-idle, 兜底)`，兜底值就是默认配色，让 CSS 单独也能用）。

挂在**根**元素而不是每个圆点上：一个窗口里可能同时有多个状态点（折叠态的几颗灯、设置面板里每个会话一颗），挂一次全都生效。

**描边和细环由填充色派生**（`color-mix(in srgb, var(--state) 74%, #000)`），所以用户只挑一个颜色，不用分别调描边——否则每加一个自定义颜色都得再算一遍。`color-mix` 万一不可用（很老的 WebKitGTK），自定义属性会退化成「保证无效」，`border: 1px solid var(--edge, var(--state))` 于是取兜底值（描边和填充同色、看不见），布局不受影响。

**键名包含派生状态。** `styles` 的键可以是 `stale` / `offline` —— `Signal::parse` 刻意不接受它们（派生状态不能被上报），但用户要能改它们长什么样，所以这里单独用 `Signal::ALL_NAMES` 校验。校验必须在 `clamped()` **之前**：`clamped()` 会静默丢掉不合法的项（那是给手改配置文件用的兜底），先 clamp 再校验用户就永远收不到「你写的颜色不合法」这条反馈。

**一个已知的取舍**：色盲的形状区分（`permission` / `error` 圆角方）只在**跟随全局、且全局形状是「圆」**时生效——用户把全局形状改成圆角方或环，或者显式给这两个状态指定了别的形状，这个区分就没了。没有偷偷保留它，因为「形状设置在某些状态下失效」比「设置被明确覆盖」更难理解。设置面板里写明了这一点，并建议此时配合色盲友好配色。

### 3.7 多组：几块牌

**分组**由上报方决定：请求里带一个可选的 `group`（不传就是 `default`）。灯球上每组一块牌，各组自己聚合。于是「一路在等授权、另一路在跑测试」不再是两个点挤在一起，而是两块各有名字、各有状态、各有消息的牌。

四件事：

1. **全局聚合 = 各组里最高的那个**。通知、钩子、托盘都用它，与分组无关——你不必为了「要不要弹通知」去理解分组。
2. **牌的排序由服务端定**（最紧急在最前，平局按组名），客户端**不再排**。原因不是省事：灯球窗口的高度取决于「哪几块牌可见」，两边必须算出同一批牌，排序只能有一个判断点。
3. **组是临时的**：组里最后一个会话消失（TTL 过期或 `DELETE`），牌就消失。没有「建组」这一步，也就没有需要清理的孤儿组。
4. **组名重复即合并**：同一组的会话一起聚合。别把不同项目的会话塞进同一个组。
5. **藏起来 ≠ 当它不存在**：右键可以把一组从灯上藏掉（`Settings::hidden_groups`），藏掉的组不再占牌的位置，但**仍然参与聚合、通知和钩子**。聚合是全局概念（「有事找你」），藏一块牌不该让应用悄悄不再提醒你。想彻底忽略一组，应该让它的上报方别再报。恢复在设置面板的「状态」页（按组点「显示」，或「全部显示」）。
6. **显示偏好不影响语义**：`Settings::group_meta` 给每组存一个显示名和置顶权重。组名是上报方给的标识（`build-1`），用户想让它读起来像人话、或者想让它永远排在最前面。这两样**只改灯上怎么显示** —— `/v1/state` 返回的组名、隐藏 / 静音的匹配、聚合、通知、钩子全都仍然按原始组名。

   **置顶只把置顶的组拎到前面，其余仍按紧急程度排。** 让用户把顺序整个接管过来的话，一盏红灯就可能被排在绿灯下面 —— 而「瞥一眼先看到该看的那块」正是这盏灯存在的理由。所以这是个 pin，不是「自定义排序」。置顶组之间用权重排（`Option<i16>`），权重由界面按「先钉的先看」分配，省掉一个拖拽界面。

   **顺序在 `visible_groups` 里算，不在 `Store` 里。** `snapshot.groups` 的顺序是**紧急度**，那是状态语义（`/v1/state` 也按它返回）；置顶是**显示偏好**。混进 `Store` 就得让 `Store` 知道 `Settings`，而它们是分开的两块状态。代价是排序规则在 Rust 和前端各有一份 —— 和隐藏、`MAX_SIGNS` 截断一样，两边必须算出同一批牌，否则窗口高度会对不上。
   **改名只有一个入口：设置 →「分组」→「各组的显示」。** 0.6.2 之前牌上的组名点一下就能就地改，撤掉的理由是**牌面不该是可交互的** —— 那盏灯的职责是「一眼看到状态」，而名字上挂一个隐形输入框，代价是每次想拖窗口、点右键都可能先落进一个编辑态。右键菜单留了一个「重命名…」，但它不就地改，只是把设置窗翻到那一页（`menu.rs` 的 `RENAME` → `lib.rs::reveal_settings_tab` → 前端 `listen` 收到 `signalhub://settings-tab` 翻页），落笔仍然只有一处：`lib/groupMeta.ts::withGroupName`。
   翻页这件事有**两条通道，都不能互相替代**：localStorage 那张「纸条」只在**前端窗口之间**传（灯窗 → 设置窗），而命令是从 **Rust** 发出的，那边碰不到 localStorage，只能走 Tauri 事件。反过来事件也走不了灯窗到设置窗那条路 —— 灯窗自己不开设置窗。所以两条并存，`settingsIntent.ts` 里都写着。
   顺带一处必须记住的：提交时 `set_settings` 必须收到**整份** `Settings`（它是整份替换），只传 `group_meta` 会把其它字段回落到默认值。

7. **静音 ≠ 隐藏**：右键（或设置面板）可以把一组**静音**（`Settings::muted_groups`）。静音只让这一组**不再触发通知和提示音**，其余一律不变——灯上照常显示、聚合照常算、钩子照常触发、`/v1/state` 照常返回。它和「隐藏」是两件事，可以各自独立：一组可以「看得见但不打扰」（只静音），也可以「看不见但照常提醒」（只隐藏）。最容易读混的就是这一条，所以单独列出来，细节见 §3.17。

8. **兜底分组由服务端推导**（`Settings::group_by`）。上报自带 `group` 时它优先；没带时才看 `group_by`：

   | 取值 | 一个组是什么 | 什么时候用 |
   |---|---|---|
   | `none`（默认） | 所有上报归 `default` | 单会话 / 单智能体，只要一眼状态 |
   | `cwd` | 一个工作目录 | 几个项目并行，各占一行 |
   | `session` | **一个会话** | 同一个智能体并行开了几个窗口 / worktree，状态各不相同 |

   **`session` 是补的第三种**，起因也是个真实反馈：同一个智能体开两个会话时，只按目录分组会把它们挤在同一块牌上，只能看到最紧急的那一个 —— 而它们的进度往往是两码事。按会话分就把每个会话摊成自己的一块，多个智能体自然也分开了（它们的会话必定不同）。

   **会话分组出来的组，牌上不画会话 id。** 组名仍然是一个 UUID（它同时是隐藏、静音、通知动作目标的匹配键，不能改），但 `GroupView` 多带一个 `default_label = 「目录末段 · 智能体」`，前端按 `用户改的名字 > default_label > 原始组名` 三级取名（`lampSort.ts` 的 `labelOf`）。**判据只有一条**：`Settings::resolve_group` 只在按会话分组时拿会话 id 当组名，所以「组名 == 组内某个会话的 id」等价于「这是会话分组出来的」—— 显式给的 `group` 和按目录分的路径名都不会恰好等于一个会话 id，因此不需要额外的标志位。这条判据和取名规则都在 `state.rs` 的 `session_label` 里，有单测。

9. **手动设的状态在这一组的牌面上说了算**（0.5.1 之后）。从灯上右键「手动状态」设的、以及托盘那三个「我 / Me」状态，仍然是**一条普通会话**（统计、历史、只读面板、钩子照旧认它），只是 `Store::apply_manual` 会把它的会话 id 记进 `manual_sessions`，`winner_in` 先取它、再取真实会话。**为什么必须这样**：0.5.1 之前它就是普通上报，组里只要有个 `working` / `permission` / `error` 的会话，按优先级一对就把用户设的 `idle` 压住，牌上一个像素都不变 —— 表现正是「点了没反应」。

   **边界划得很窄**：只覆盖这一组的牌面。全局 `aggregate()` 仍按普通优先级在所有会话里取最大值（托盘、物理灯、今日统计不骗人）；告警判定也不看牌面、按会话取最大值（`GroupView::alert_state`），所以把一盏灯画成绿不会把底下「等授权」的提醒吞掉；「打开项目目录」取真实会话的 `cwd`（手动那条没有目录，照旧写法菜单会无故置灰）。手动会话到期**直接删**、不转 `stale` —— 一条 stale 的手动状态会压着真实会话整整 30 分钟宽限期。收掉走右键现有的「清除该组的状态」，`settle` 会顺手把标记一起清走，不会留下悬空的 id。

**去掉目录前缀、并且把项目放在前面，都是同一件事逼出来的：牌宽固定。** 名字那一行还要跟状态文字分，所以这个词**一定会被截断**，能看见的只有前几个字。于是两条：取路径的**末段**而不是整条路径（末段才是有区分度的那个词），以及项目排在智能体前面 —— 按会话分组的典型情形是「同一个智能体开了好几个窗口」，那时智能体名是重复的噪音，只有项目名能把它们区分开，把项目放前面，截断切掉的就是那截重复的尾巴。这两条都不是审美，是「截断之后还剩什么」这个问题的答案。

   顺带一处去重：取目录末段的 `config::project_name` 原本只有 `alerts.rs` 里一份（通知正文要用），现在两处共用它 —— 各写一遍「最后一段怎么切」迟早会分叉。

   **这一步做在 `server.rs` 的 `apply()`，不在 CLI、也不在钩子命令里。** 钩子命令是写死的字符串，而按目录 / 按会话分组要的是**每次调用各自的值**，写进命令行就只能是个常量，根本表达不了；而且改服务端顺带覆盖了 `curl` / CI / 手写脚本，不用去动用户的智能体配置文件。代价是上报路径也要读设置，所以 `SharedSettings` 和 `SharedStore` 一样是 `Arc` 共享的同一份，不是启动时的快照 —— 否则用户在面板里一改开关，得重启才生效。

   **默认必须是 `none`**，这条比看着重要：一旦默认分组，所有现有用户的灯会从一块牌变成若干块、窗口尺寸跟着变、没配过的组显示名还是原始路径 —— 属于无声改变既有行为。

窗口尺寸：展开时牌竖着叠（宽度不随牌数变），高度按每块牌累加；折叠时一组一颗点，横着排，`+N` 角标另占点位：

```
展开：牌宽   = size × 7
      牌高   = size × 3/2（一行）/ size × 5/2（带消息两行）
      牌间距 = size / 2
      牌尾只剩 `+N` 角标，flex: none，不另占高度
      暂停 / 穿透角标绝对定位在牌的右上角外侧，不吃牌身宽度
折叠：宽 = (dots + badges) × size + (dots + badges − 1) × (size / 3)
      高 = size + 28
      dots   = min(可见组数, MAX_DOTS)，且至少 1
      badges = 有组被藏起来（0/1，即 `+N`）
留白 = 28（LAMP_MARGIN，两侧各 14）
```

**有消息的牌会变高** —— 那是刻意的：牌子长出一行本身就是「有东西可读」的提示。但用户把「消息」那一段关掉之后牌永远是单行，窗口高度也得跟着少一行（见 §3.6.1）。

最多同时显示 `MAX_SIGNS`（4）块，超出的截断（服务端已按优先级排好，所以留下的恰好是最紧急的）。折叠态的上限 `MAX_DOTS` **刻意等于 `MAX_SIGNS`**：折叠只是换个外形，不该顺带少显示几个组——那会让人以为一折叠就把状态弄丢了。宽度**固定、超出用省略号截断**：让宽度跟着文字走会让窗口每次消息变化都跳一下。

**折叠态的点数是「组数 + `+N` 角标数」。** 只有 `+N` 在折叠态占一个点的位置（展开态寄住在牌尾，不占额外高度）；暂停 / 穿透那枚是 `lamp.css` 的 `.lamp-flag` —— 绝对定位在**牌的右上角外侧**（`top: 1px`、`right: var(--lamp-inset)`，右边缘与牌右边缘齐平，12×12 圆角方块 + 9px 线性图标），两种形态共用同一枚 DOM，既不挤牌身也不占点位，所以切换穿透 / 暂停不会让窗口尺寸变化。它原来既是牌里的 flex 子项（挤掉 `.sign-body` 的组名）、又在折叠态多占一个点距，表现就是一开穿透整排灯珠被重新居中、像被箭头挤出去。**位置挪了三回**：窗口左上角 (1,1) → 顶部留白正中（9px 小圆点）→ 牌的右上角（12px）。前两种都在 14px 的留白里勉强塞下一枚 9px 的圆点，小到像渲染残留，而且里面的 `⇥` 在 7px 下只是一团墨；现在换成 `Icon` 的线性图标（穿透 = `ban` 圆环加斜杠，暂停 = 两道竖线），形状本身就能分辨，不靠颜色。**它必须待在牌外**：牌的右端是时长（`12s` 那一列），叠在牌角上就会压住它，所以留白从 10 加到 14（`LAMP_MARGIN` 20 → 28）专门给它腾地方。`collapsed_window_size(size, dots, badges)` 的 `badges` 现在只数 `+N`，`MAX_BADGES` 也降到 1。**两个上限仍然分别封**：组数按 `MAX_DOTS`，角标按 `MAX_BADGES` —— 封住它们的和会让「多一枚角标」被当成「少一个组」，那正是截断要避免的那种谎。前端画几枚，这里就得算几枚：两边是同一个条件（`SignalLamp.tsx` 的 `hidden.length > 0` ↔ `config::more_badge`），少算一枚那枚角标就会被 `#root` 的 `overflow: hidden` 从右边切掉。

顺带一个量级问题：Rust 的点距是**整除**（`size / 3` = 7），CSS 的 `calc(var(--size) / 3)` 是 7.33 —— 一行点排下来 CSS 比 Rust 宽出 ~1.6px。这点差被两侧各 14px 的留白吃得下（`.lamp-root` 自己 `overflow: visible`，只是往 padding 里溢一点），所以不会裁切；但**留白不能再小了**，那点余量就是它兜的（角标也靠这 14px 容身）。

几何在 Rust（`config::sign_width` / `sign_height` / `collapsed_window_size`）和 CSS（`.sign` / `.lamp-dot` 的 `calc()`）各写了一份，**必须严格对齐**——差了 1px 就会被 `overflow: hidden` 切掉最后一块牌。这是本项目里反复出现的一类耦合（折叠点距、设置窗高度也是），所以每个几何常量旁边都写了「CSS 里对应哪条规则」。

**「哪几块牌可见」只有一个判断点**：`lib.rs` 的 `visible_groups`（先滤掉隐藏的，再截断到 `MAX_SIGNS`）和 `sign_heights`（每块多高）。前端照着同一条规则渲染。两边算出不同的组，窗口要么裁掉最后一块牌，要么底下空一条。

**多灯布局（`Settings::lamp_layout = per-group`）的建窗必须离开 IPC 的栈。** 每个可见组一盏真窗口（上限 `MAX_LAMPS` = 8，超过就回落单灯），主灯退成一颗全局灯。麻烦在于「谁来建这个窗口」：

- **不能在 IPC 命令里就地建。** Windows 上 IPC 走 WebView2 的消息回调、**就在主线程**，而 `WebviewWindowBuilder::build()` 在 Windows 上会调 `webview2_com::wait_with_pump` —— 一个**嵌套的 Windows 消息泵**，用来等 WebView2 自己的创建回调。两者一叠：在回调内部又泵起一层消息循环，去等一个必须等外层回调返回才可能被投递的回调。**互等，界面冻死**，而且建第一盏就卡，和几盏灯无关。macOS 上不会现形：那里的 IPC 不在主线程，`build()` 走「投递给事件循环 + 阻塞等回执」，事件循环是空闲的 —— 所以这条只在 Windows 上被用户撞到（0.4.2 修，见 `lamp_worker`）。
- **也不能抱着 lamps 锁建**（issue #4：主线程上的 `set_peek` 要来抢同一把锁）。
- **关窗要排在同一条队列里。** 记账是乐观的（`plan` 就把新组算作已开），「切过去」和「切回来」两份计划可以紧挨着算出来；乱序执行会留下一个谁也不认的孤儿灯窗（关的时候窗还没建出来，建完就没人记得它了）。投递发生在 lamps 锁内，所以队列顺序 = 计划顺序。

于是固定成：锁内 `plan` → **在锁内投给 `lamp_worker`** → 那条线程按顺序做「关 → 改尺寸 → 建 → 记账」。**只有改尺寸仍就地做**：折叠态悬停临时展开（`set_peek`）是热路径，晚一帧就能看见窗口跟不上鼠标。副作用是设置面板的 IPC 立刻返回 —— 切「每组分灯」时界面不会跟着等 8 个 webview 建完。

### 3.8 通知：把「被动」补成「主动」

灯是**被动**的：你不盯着屏幕它就白搭，而「不用看终端」恰恰意味着你可能根本没在看灯。所以聚合**新变成** `permission` / `attention` / `error` 时弹一条系统通知。

两个不显然的设计点：

1. **只在跃迁时弹一次，不是每次状态变化都弹。** 一轮工具调用会触发几十次状态推送，每次都弹就成了骚扰。核心判断就是 `previous != Some(current)`。
2. **权限在启动时申请，不在第一次要发通知时申请。** 弹权限框和发通知没法同时发生——放在第一次要发通知时，那条通知必然丢掉，而它往往正是最要紧的一条。

通知正文取「胜出会话的项目名 + 智能体自己写的说明」，例如 `proj · 需要批准: rm -rf build`。`Signal::label()` 在 Rust 侧也有一份中文名（界面上的文案在前端的 `signals.ts`）——重复一份是因为通知由 Rust 发，比前端可靠（webview 出问题也照发）；那个 `match` 是穷尽的，所以新增状态时编译器会强制补上标签。

> **dev 模式的限制**：`tauri dev` 跑的是未打包的裸二进制，而 macOS 的 `UNUserNotificationCenter` 需要 bundle identifier。所以通知在 dev 下可能**不显示**（调用本身会成功、不报错）。要确认真的能弹，得 `npm run tauri build` 出真正的 .app。这一点没在 dev 下验证过，不要当成已验证。

**出站钩子**见 §3.10 —— 它和系统通知共用「只在聚合跃迁时触发」这个语义，但钩子自带过滤条件（`when`），所以不受「只在需要注意的状态」限制：用户可以配「done 时跑个脚本」。

**提示音**（`Settings::sound`，默认开）挂在通知上。**声音名没有三平台通吃的写法**，只能逐平台取值：macOS 认 `NSUserNotificationDefaultSoundName` 这个哨兵；Windows 的 toast 只接受 `Default` / `IM` / `Mail` / `Reminder` / `SMS` / `Alarm*`，喂它 macOS 那个哨兵会**静默无声**；Linux 走 XDG 的 `sound-name` 提示，而 dunst / GNOME 这些常见的通知守护进程根本不理会它——所以那一栏的常量是 `None`，设置等于没接。`alerts.rs` 里用 `#[cfg]` 分平台选常量，并在注释里写明了每个平台的实情。

声音**只有在通知发得出去时才存在**：关掉通知，这条路径根本不会被调用，声音自然一并没了。这是刻意的——不为一个提示音再单开一条音频通路和它的跨平台麻烦。

**「该不该吵你」还叠了三道闸门** —— 按组静音、持续多久才提醒、勿扰时段，见 §3.17。它们都只影响通知（和声音），不影响灯怎么显示、聚合怎么算。

`ureq` 因此**必须带 rustls**（钩子目标都是 HTTPS）。选 rustls 而不是 native-tls，是因为后者在 Linux 上要系统 libssl，跨平台构建会多一道坎。

### 3.9 一个把三个功能同时静默废掉的接线 bug

这一条值得单独记，因为它的形态很典型。

现象：webhook 配好了、地址正确，但从不发出；系统通知也从没弹过。

根因：**通知器有两个构造方式**。`notify::to_lamp_window(app)` 只负责把事件推给前端窗口；而 lib.rs 在 setup 里组合了一个「推事件 + 核对窗口尺寸 + 记统计 + 发通知 + 转发」的闭包，把它 `manage` 进 Tauri state。但 `server::spawn` 自己又调了一次 `notify::to_lamp_window(app)` —— 于是**所有走 HTTP 上报的状态变化全部绕过了那一整套逻辑**。而智能体的 hook 恰好全走 HTTP。

更糟的是它**不报错**：`alerts::send` 和 `alerts::forward` 根本没被调用，所以既没有通知、也没有失败日志。我早先「通知没有报错」的验证是个**假阴性**——它验证的是「没有错误」，而真相是「没有尝试」。

**修法不是补一处调用，而是去掉另一种构造方式**：把组合逻辑收进 `notify::compose(app)`，让它成为唯一入口，`to_lamp_window` 降级为模块私有的 `emit`。这样「某个路径用错通知器」在结构上就不可能发生。

教训：**当一个功能有多条入口路径（HTTP / sweep / 命令 / 托盘）时，共享的那层逻辑必须只有一个构造点**。否则漏掉一条路径的表现不是报错，而是「功能静默不生效」。

### 3.10 出站钩子：让 SignalHub 成为信号中枢

入口本来就是通用的（HTTP + CLI，任何程序都能报，8 个状态词是共享词汇表），但出口最初只有**一条 webhook**，而且只转发「需要注意」的三种状态。要做成信号中枢，出口必须是**多条带过滤的钩子**：

```json
{ "when": ["permission", "error"], "type": "http", "url": "https://ntfy.sh/x", "preset": "ntfy" }
{ "when": ["permission"],          "type": "http", "url": "https://ntfy.sh/y", "preset": "slack", "headers": { "X-Token": "…" } }
{ "when": ["done"],                "type": "command", "command": "say 完成" }
{ "when": [],                      "type": "http", "url": "http://localhost:9000/ingest" }
```

`preset` 省略时是 `raw`（原样发 SignalHub 自己的 JSON 快照），`headers` 省略时是空 —— 两者都靠 `#[serde(default)]`，所以老的 `{"type":"http","url":…}` 一个字节都不用改。

`when` 空数组 = 任何变化都触发。模型和触发在 `outbound.rs`（注意和 `hooks.rs` 方向相反：那个是入站，把智能体的 hook 装进它们的配置文件）。

**四条设计约束：**

1. **必须异步。** 触发点在状态变更路径上（HTTP 上报和 sweep 都会走到），同步发网络请求或等命令结束会把状态机卡住。每条钩子丢进 `spawn_blocking`，互不影响。
2. **命令必须带超时。** 走 `sh -c`（Windows 上 `cmd /C`），用户因此能写管道和重定向 —— 这正是钩子有用的地方。但挂死的命令会把 tokio 的阻塞线程池占满，所以轮询 `try_wait` 到 10 秒就杀掉。输出全部丢弃：钩子是用来触发副作用的。
3. **只在聚合跃迁时触发**，不是每次快照变化。同一个状态内的变化（某个会话的说明文本改了）不算。语义和系统通知一致。
4. **空目标不算错。** 目标留空的钩子不触发也不报错 —— 编辑时必然要经过「刚点添加、还没填目标」这个中间态，那时候报错就没法编辑了。面板上会标「未填目标」，所以它不会静默失效。

**安全性：`type: "command"` 会执行本地命令，没有额外开关。** 信任模型和 git hooks / npm scripts 一样——配置文件在用户自己的主目录里，能改它就能执行任何东西。加一个开关只会给人一种「关掉就安全」的错觉，而文件本来就在用户手里。文档里写明了这一点，并提醒不要把别人的 `config.json` 直接拿来用。

**一次迁移：** 旧的单条 `webhook_url` 在启动时会被搬成一条 `when = [permission, attention, error]` 的 HTTP 钩子，字段本身标了 `skip_serializing` 永不写回。不搬的话，用户已经配好的转发会在升级后静默失效——而那正是最难发现的一类回归。出口只保留一种表达，不让「单条 webhook」和「钩子列表」并存。

**R4：从「能做」到「好用」。** 一条真实反馈是「转发疑似不可用」。查下来**通路是好的**（本轮补的端到端测试证明 `post` 真的把请求发出去了、非 2xx 也真的带着状态码回来），坏的是它发出去的东西和它周围的体验。四条一起补：

1. **服务预设（`HttpPreset`）。** body 一直是 SignalHub 自己的 JSON 快照，而做通知的那些服务（ntfy / Bark / Slack / Discord / Telegram / 飞书 / 企业微信 / 钉钉）要的是「一个 URL + 一段文字」—— 用户照着 ntfy 的占位符填一条，手机收到一坨看不懂的 JSON。于是 `outbound::compose()` 按预设组装请求：**纯函数**，输入 (预设, 摘要, url, 头)，输出最终要发的 URL / 头 / content-type / body。每个服务的形状都只有这一处实现，也都测在这一处。默认 `raw`（原样发 JSON），老配置靠 `#[serde(default)]` 落到它，行为一个字不变。

   **Telegram 那一格要解释一下：`chat_id` 按官方文档是查询参数**，所以用户填的地址必然是 `…/sendMessage?chat_id=123`，而 sendMessage 只认表单体 —— 于是整条查询串要**搬进 body**，URL 上不留。裸的 `…/sendMessage` 也允许：Telegram 会回 400，而那条状态码正好通过「非 2xx 带码回来」显示给用户。

2. **一行摘要（`summarize`）**：`[SignalHub] 需要授权 · 构建 — 等你批准 (2m)`。组名用**用户看到的那个**（`Settings::display_label`，三级规则同前端 `labelOf`）—— 用户在灯上把 `build-1` 改成了「构建」，转发里却还是 `build-1`，那就是两处真值打架。**不加 emoji**：Rust 这边没有状态 emoji 表，新加一份就是第三处「状态长什么样」的真值，而这类漂移最难自查；收件人读的是文字。

3. **自定义请求头（`Http::headers`）。** 任何要鉴权的地址（`Authorization: Bearer …`、ntfy 的 `X-Token`）原先根本配不了。`clamped()` 里规整：去空白、丢空键、上限 16 条（按键的字典序截断，所以丢哪几条是确定的）。**不做「只差大小写」的去重**：HTTP 头名大小写不敏感，但要判断 `Authorization` 和 `authorization` 哪个是后写的，得知道用户写下的顺序，而 `BTreeMap` 已经把顺序排掉了 —— 任何胜者都是任意挑的。宁可两条都发（服务器会用状态码告诉我们它不接受），也不要悄悄丢掉一条用户明确写下的鉴权头；编辑界面在输入那一层挡重复的键，那里顺序还在。

4. **发送测试（`test_hooks` → `outbound::test_all`）。** 忽略 `when` / 组过滤 / 跃迁判据，把已配置的每条各发一遍。没有它，用户配完只能等下一次真实跃迁 —— 而「等不到」和「发失败」从外面看一模一样，这就是「疑似」的来源。它和真实触发走**同一条路**（同一个 `compose`、同一个 `post`、同一份日志），只有前缀不同（`SignalHub 测试`）—— 测试消息必须看起来就像测试，否则用户会以为真出事了。摘要写的是**当前最紧急的那一组**，这样一条测试消息能当样本看（「真出事时手机上大概长这样」）。

**PushDeer 与「200 也会撒谎」（`verdict`）。** PushDeer 是第一个把「只看状态码」这件事戳破的服务：**一个失效的 key 回的是 `200 {"code":80501,"error":"错误的Key"}`**（实测）。`post` 原来只把状态码带回来，于是一个填错的 key 在面板上是绿色的「✓ 200」，而手机一声不响 —— 那正是「转发疑似不可用」里最难查的一类：界面上写着成功。所以 `post` 之后多了一步 `verdict(preset, status, body)`：对**出错也回 200** 的那几家（PushDeer `code`、飞书 `code`、企业微信/钉钉 `errcode`、Slack `ok`）读一眼响应体里的信封，在 200 里说了失败就按失败记，并把服务自己给的那句原话带回来（界面上是「错误的Key」而不是「失败」两个字）。

两条边界写在这里，免得以后有人「顺手」改掉：**认不出形状就不当失败**（单测里专门有 `{"hello":"world"}` 和纯文本 `ok` 这两种）—— 我们只是多看一眼，不该因为解析不出形状就把一次真发出去的推送判成失败，那会变成一种新的「疑似」；**只读前 8KB**（`ENVELOPE_LIMIT`）—— 那个地址是用户填的，不该由它决定我们往内存里读多少。`Request` 因此带上了 `preset`：不知道是哪一家，就不知道信封的键叫什么。

PushDeer 的形状本身也只有两处**实测**结论：`pushkey` 留在 URL 的查询串上（Laravel 把查询串和表单体合起来读，所以不动用户填的东西），**只填服务器地址**（自架版 README 给的就是 `host:8800`）时补上官方的 `/message/push`（POST 到根路径回 405）；正文固定 `type=text`（它默认按 markdown 渲染，摘要里的 `·`/`—` 会被吃成标记）。

**出站日志落盘（`~/.signalhub/outbound.json`）。** 日志原来是纯内存的环形缓冲，重启一次界面就显示「从未触发」—— 用户重启一次就会以为转发坏了。和 `lamp-positions.json` 一个路子：内存里留一份（界面要立刻读到），`record` 时顺手写一份。**落盘失败只打 stderr**：记不住一条历史结果不该影响转发本身。读回来时文件不在 / 格式坏了都当空的（它只是历史记录），但坏文件会留一行 stderr —— 静默吞掉的话，「转发结果一直是空的」会变成一个查不出来的现象。

### 3.11 今日状态时长统计

按「前端给的本地日期」分桶——**本地日期只有前端知道**（Rust 这边没有时区数据，`SystemTime` 只给 UTC），所以由前端推过来（`new Date().toLocaleDateString("sv")` 给的就是本地时区的 ISO 日期）；日期一变就重置。这样不必引入时区依赖。

**日期跟着那个每分钟一次的时钟心跳走，而不是只在查询时带过来。** 这条一开始做错了：跨天只在 `report`（也就是有人在查统计）时才判，而那个查询只在设置面板开着时发生 —— 灯球是常驻应用，整天不开面板是常态，于是「今日时长」会横跨多天一路累加。现在 `Stats::rollover` 被摘成独立方法，`set_local_clock` 每分钟调一次它（`useLocalClock.ts`），跨天在分钟级就能被发现。**注意 `useLocalClock` 和 `useStats` 必须用同一个日期写法**，否则两边字符串不等，会白白触发一次跨天把统计清掉。

四个不显然的点：

1. **第一次拿到日期只记下来，不清空。** 否则从启动到第一次拿到日期之间累计的时间会被白扔。
2. **跨天时当前这段也重新起算**，否则会把昨天那段算进今天。
3. **查询会把「正在进行的那一段」也算进去**，所以不必等状态变化就能看到当前进度；结算完立刻把这段重新打开，否则反复查询会漏时间。
4. **`rollover` 只认日期字符串变了没有**，不自己算日期 —— 它没有时区数据，算出来的「今天」可能是错的时区。

时长平局时按优先级排——否则顺序取决于 `HashMap` 的迭代顺序，界面每次刷新都可能换个次序。

**每日合计会落盘**（`~/.signalhub/stats.json`）。灯球是常驻应用，但「常驻」不等于「永不重启」：改设置、升级、崩了重来，而用户对「今天等了多久」的期待是跨重启的。

落盘里有四个不显然的地方：

- **内存用 `Instant`、文件用日期。** `Instant` 是单调钟（不受系统时钟调整影响），但它存不下来、跨重启也没有意义 —— 所以文件里只有「某天某状态多少秒」，当前这一段是**存的时候现折算**的。
- **今天只存一处。** `history` 放**过完的日子**，`totals` 放今天。读盘时全部进 `history`；等前端第一次推来日期，把那一天从 `history` **取出来**（`remove`）放进 `totals`。不取走的话，落盘时「history + 今天的 totals」会把今天写两遍。
- **跨天归档前必须先把当前这段结算掉。** 不清的话，一天里最后那一段（从上次状态变化到跨天，可能几小时）整个丢掉 —— 它在 `segment_start` 里、还没进 `totals`。这条有单测盯着。
- **文件的键是状态名的字符串，不是 `Signal`。** `Signal` 的 `Deserialize` 是给**外部上报**用的，刻意拒绝 `stale` / `offline`；而统计里那两个恰恰要有。所以走 `Signal::from_name`（接受全部名字），绕开那个属于上报的约束。

**「历史」页把这些天摆出来**（`Stats::recent_days` → `get_history` → `useHistory`）：一天一行，条子的宽度就是那天各状态占用的时间。三个不显然的地方：

- **今天从 `report()` 走、更早的从 `history` 字段拿。** 这两处本来就是同一份账的两半（见上面「今天只存一处」），所以这里只是把两半摆成「一天一行」，不重算任何东西。名字叫 `recent_days` 而不是 `history`：后者会和同名字段撞在一起，`stats.history(...)` 和 `stats.history` 摆着谁也读不出哪个是哪个。
- **所有天共用一个尺度**（要显示的那几天里最忙的那天占满整条），不是各画各的。各归一化的话，只用了 10 分钟的那天会和用了 8 小时的那天一样满 —— 而「哪几天真的忙」正是这一屏要回答的事。做法是给每条补一段**透明**的尾巴（`.history-rest`）撑到那个尺度，所以条子其实是一条轨道。
- **没有记录的日子不补一行零。** `history` 里只有真的记过的日期。补零会读成「那天灯开着但什么都没干」，而真相多半是应用没跑。

**刻意只做 7 天，也不做趋势线、不做同比。** 这一屏回答的是「我这几天都在忙什么」。往分析工具那个方向走，尽头是另一个应用，而这个应用是一盏灯 —— 定位这条线比多加一个图表重要。

落盘挂在**时钟心跳**上（`set_local_clock`，前端每分钟推一次）—— 那是「应用还活着」的现成节拍，不必再起一个定时器。代价是崩掉最多丢一分钟，对一个「今天等了多久」的数字完全够用。

**近 30 分钟的时间线**是同一份数据回答的另一个问题。`Stats` 本来就收到每一次聚合变化，现在多留最近 `TIMELINE_CAPACITY`（512）次**状态转换**——只在状态真的变了时才记一笔，同一个状态反复上报不刷屏。

`timeline(now, window)` 返回首尾相接的 `Segment { state, ms }`，覆盖 `[now − window, now]`，从旧到新：第一段在窗口边界处截断，最后一段截到 `now`。它取 `&self`——不像 `report`，它**不能**改自己（查询时间线不该影响统计）。第一个样本之前没有已知状态，所以覆盖区间从 `max(now − window, 第一个样本的时刻)` 起算：宁可短一点，也不假装知道应用启动前是什么状态。

设置面板的「状态」页把它画成一条色带，**每一段的宽度就是它的时长**。今日统计回答「一共多久」，这条回答「什么时候」——两个问题不一样，所以两条都留着。`Segment` 直接给时长而不是给时间戳：`Instant` 换成墙上时钟要处理时区和时钟回拨，而前端只需要「这一段占多宽」。

### 3.12 窗口位置记忆

用 `tauri-plugin-window-state`，但**只让它记位置，不记尺寸**：

```rust
.with_state_flags(StateFlags::POSITION)   // 默认是 all()，会把尺寸也一起恢复
```

尺寸由设置和会话数决定、是程序自己管的（`apply_window_size`），让插件跟着恢复会和它打架。这是这个插件最容易被误用的地方——默认值 `all()` 会连尺寸、最大化、可见性一起恢复。

插件的默认存储位置是 app 配置目录下的 `.window-state.json`（macOS 上是 `~/Library/Application Support/<identifier>/`）。它在**正常退出**时写入，所以 dev 下反复重建期间看不到这个文件是正常的。

**位置记住 + 尺寸由内容决定，这两件事凑在一起会咬人。** 组一多、或者从旧版本升上来（默认从一颗灯变成一叠牌），窗口就会长大 —— 一个原本贴着屏幕右下角的点会长到屏幕外面去，用户看到的是一块被裁掉一半的牌子，而且多半想不到是尺寸变了。

所以 `apply_window_size` 在**尺寸真的变了**之后会调一次 `keep_on_screen`，把窗口夹回工作区（`work_area`，不是整屏 —— 任务栏 / Dock 占掉的那一条不算可用空间）。三个细节：

1. **只在尺寸变了的分支里调**，所以不会和用户拖动打架：用户把窗口拖到哪就是哪，只要没越界就一个像素都不动。
2. **用刚设下去的逻辑尺寸换算，不读 `outer_size()`** —— `set_size` 是往事件循环投一条消息，紧接着读回来拿到的还是旧值，用它算会把窗口夹到错的位置。
3. **窗口比工作区还大时 `clamp` 会 panic**（min > max），所以先取 max 保证区间非空。夹紧的数学抽成了纯函数 `clamp_to_area`，边界情况（比屏幕还大的窗口、副屏在左侧时的负坐标）都有单测 —— 那些在真机上很难复现。

**而「屏没了」的时候，上面这条兜底原来恰好失效。** `keep_on_screen` 原来要求 `current_monitor()` 给得出屏 —— 可是**窗口整个落在一块已经不在了的屏幕上时，它正好给 `None`**（拔掉外接屏、改分辨率、换布局都会这样）。于是最需要夹的那一刻直接 `return`，灯永远留在屏幕外：它没有 Dock 图标、托盘也只能打开设置，**用户再也点不到它**，最后只能去删配置文件。现在屏拿不到时退回「点到矩形的距离」最近的那块屏（`nearest_screen`），照样夹得回来，并往 `hooks.log` 记一行 —— 「我的灯怎么跑到这边来了」得有个地方查。

组灯（多灯布局下每个组一盏）走的是同一个 `clamp_to_area` + `nearest_screen`：它们的位置不在插件里，而是自己存的 `lamp-positions.json`（见 §3.7 的多灯布局），拔掉外接屏之后那个坐标同样会失效。这一条真机验过：把某组的位置写成 `(9000, 9000)`（一块不存在的屏上），重启后那盏灯落在最近那块屏的右下角、完整可见。

### 3.13 设置文件的向前兼容

`Settings` 带 `#[serde(default)]`。这是用户可手改、也会跨版本留存的文件，缺字段时应该退回**该字段**的默认值，而不是整份解析失败——否则每新增一个设置项，都会把用户已经调好的其他设置一起重置。

这个坑是真实踩到的：加 `notify` 字段之后，已有的 `config.json`（里面存着用户调过的 `size: 32`）直接解析失败，圆点尺寸会被静默重置回 22。日志里那行 `config.json 无法解析（missing field notify），使用默认设置` 就是它。

### 3.14 两种形态，以及拖拽与点击的冲突

灯有两种形态，左键在两者之间切换：

- **展开（默认）** —— 一叠交通牌，每组一块（§3.7）。默认展开是刻意的：灯的本职就是让人一眼看到状态，折叠是用户主动要的例外。
- **折叠** —— 每组一颗裸灯，横着排，没有牌面。

选择存在 `Settings::collapsed` 里，所以重启后还是用户上次选的那个。三条路径都能切（灯上左键、灯上右键菜单、托盘），它们**共用 `lib.rs` 的同一个 `set_collapsed`**——写两份行为迟早分叉。

窗口尺寸仍由 Rust 算（见 §3.7 的几何），前端只负责「点了一下」。

> 上一版这里是另一种设计：点圆点把窗口放大成一张**会话列表**（`Settings::panel_size` / `PANEL_CHROME` / `PANEL_ROW`）。那一套连同 `.lamp-panel` 的 CSS 和 `set_lamp_expanded` 命令一起删掉了——会话级明细现在只存在于设置面板的「状态」页，灯上不再有第二套列表。

**这里踩到一个真实的冲突：同一个元素不能既用 `data-tauri-drag-region` 又响应点击。**

`data-tauri-drag-region` 让系统在 `mousedown` 时接管鼠标、进入原生拖拽循环，之后的 `click` 就不再可靠地送到 webview —— 表现是「点一下折叠」时灵时不灵。而把拖拽区域去掉又会丢掉拖窗口的能力，那是这个工具的基本操作。

解法是自己在 JS 里区分：按下时记下坐标，移动超过 4px 才认为用户在拖窗口（此时才调 `getCurrentWindow().startDragging()` 交给系统），否则在 `mouseup` 时当作点击。于是灯上**没有 `onClick`**，点击是从 `mouseup` 里判出来的。

**两个推论，都还在生效：**

1. **两种形态都仍然可拖拽**。上一版为了「点击收不起来」而让展开态不可拖，现在不需要了——点击是从 `mouseup` 判的，和拖拽不冲突。
2. **右键能穿透到 `contextmenu`**，因为只有主键会记下拖拽起点（`if event.button !== 0) return`）。所以右键菜单和「左键拖拽 / 左键点击」可以共存于同一个元素上。

空白处（牌之间、留白）也 `preventDefault` 掉右键，否则会冒出 webview 自己的菜单。

### 3.14.1 每组右键菜单（`menu.rs`）

右键一块牌（或折叠态的一颗点）弹出：隐藏该组 / 静音该组（或取消静音该组）/ 清除该组的状态 / 折叠成一颗灯（或展开牌面）/ 打开设置…。

**为什么是原生菜单而不是 HTML。** 灯球窗口是按内容**精确**尺寸的（§3.7），而且 `overflow: hidden`——一个 HTML 菜单画在窗口里必然被裁掉。原生菜单由系统绘制，不受窗口边界约束，位置也由系统避开屏幕边缘。这是这个项目里「窗口尺寸即内容尺寸」这条约束的又一个后果。

**两个实现点值得记：**

1. **运行时构造的 `Menu` 没有自己的事件回调。** `TrayIconBuilder` 有 `on_menu_event`，但 `Menu` 没有——只能挂在 `AppHandle::on_menu_event` 上。关键在于那是往 `global_event_listeners` 这个 `Vec` 里 **push** 而不是替换（tauri 2.12.2 的 `manager/menu.rs` 与 `tray/mod.rs::register` 都往同一个 vec 里推），所以**托盘自己的回调照常工作**，两者共存。为了让这一点成立，菜单 id 用 `group:` 前缀和托盘的 id（`quit` / `toggle` / `pause` / …）隔开，收到不认识的 id 直接放行。
2. **组名没有编进菜单 id。** 组名是任意用户字符串（`ci`、`我的构建`），编进 id 要转义、还可能和别的 id 撞上。所以 id 只用固定的几个动作名，被点的组名存在 `menu::Target(Mutex<Option<String>>)` 里，处理事件时再取。

**菜单上有三个关于「这一组」的动作，别混：** **隐藏**只是不让它占灯上的位置（`hidden_groups`，见 §3.7 第 5 条）；**静音**只是不再为这一组弹通知 / 出声（`muted_groups`，见 §3.17）；**清除**是把这一组的会话全部删掉（`Store::clear_group`）。清除是「这个组的状态卡住了」的解药——上报方崩了或者没发收尾事件时，灯会一直停在最后一个状态上等 TTL 到期，而清除是立刻的。

### 3.14.2 清除状态的入口（只剩会话行尾的 `×`）

「状态卡住了」这条路上，原生右键菜单有两个够不着的地方：**看不出来能删**（能力藏在右键里），
以及**粒度太粗**（只有「清整组」，一组里跑着三个会话、卡住一个时只能全清）。所以当时补了两条
入口：牌右上角悬停露出的 `×`（一组）、设置 →「状态」页会话行尾的 `×`（一个会话）。

**牌上那枚已于 2026-11-10 撤掉。** 两条理由，都不是「不好看」：

1. 常驻窗口上的一枚 ×，形状说的是「关掉这块牌」，而它做的事只是清一个状态 —— 需要靠 tooltip
   纠正形状，说明形状本身就说错了话；而误点的代价是「一组状态忽然没了」。
2. 那个角落正是四角小灯 `tr` 的落点（§3.35）。悬停浮出的按钮会盖住读者刚配好的一盏灯，
   角灯又是余光级信息 —— 被遮一下，等于把它刚刚表达的东西抵消掉。

现在只剩一条：

| 入口 | 粒度 | 命令 |
|---|---|---|
| 设置 →「状态」页会话行尾的 `×`（悬停露出） | 一个会话 | `clear_session` → `Store::remove_session` |

**整组清除回到右键菜单**（「清除该组的状态」→ `menu.rs::CLEAR` → `lib.rs::clear_group`），
`clear_group` 仍以 `pub(crate)` 留在 `lib.rs` 给菜单用。命令 `clear_group_state` 随之删除 ——
留着它就是一个没有调用方、却看起来像「还有第二条路」的入口。

HTTP 的 `DELETE /v1/sessions/{id}` 用的是同一个 `Store::remove_session`，
清一个**不存在**的会话在那里是静默幂等的，命令这边也不能改成报错。

**不做二次确认**：这是低频、幂等的操作（智能体下次上报就回来了），而且它本来就是「卡住了，
赶紧清掉」这条路上的动作 —— 加个确认框只会让紧急的事变慢。剩下那枚 `×` 仍用 `title` 把后果说清楚。

**这枚 `×` 不许改变窗口尺寸**（红线 1 的免死金牌是「不参与布局」）：它是设置窗里的普通流式按钮，
不牵涉灯的几何。显隐**只动 `opacity`**（红线 2），藏着时 `pointer-events: none` —— 否则盲点会
清掉一个会话。

**措辞跟着当前状态走。** 静音那项在已静音时显示「取消静音该组」，切形态那项在折叠时显示「展开牌面」——写「切换」的话，得先看一眼设置或灯才知道会切成什么。

### 3.15 单实例、穿透、自启

**单实例**（`tauri-plugin-single-instance`）要**最先注册**。多开会让两个进程抢同一个端口文件、互相覆盖状态，表现出来是「灯球偶尔不动」这类极难排查的现象。第二个实例起来时把灯球亮出来——用户多半是没找到它才又点了一次图标。

**点击穿透是这里唯一有危险的功能**：开启后整个窗口忽略指针事件，鼠标再也点不到、拖不动它。所以：

1. **全局快捷键必须先注册成功**，它才是键盘上的出路（另一条是托盘菜单）。注册失败只记日志、不阻断启动，因为托盘那条路还在。
2. **开启时发一条通知说明怎么退出**——一个没有逃生通道的穿透模式就是个陷阱。
3. **不替用户改外形。** 上一版会在开启穿透时顺手把展开的面板收起来，理由是「否则留下一个点不动的大窗口」。现在外形是用户自己选的、存在设置里的，而穿透下窗口本来就点不动——替用户改掉反而是越权，所以这一步删了。
4. **不落盘**。它是瞬态开关，重启后必须回到可点击状态；否则用户一开机就面对一个点不动的圆点，还不知道为什么。这也是它没进 `Settings` 而是单独放在 `UiFlags` 里的原因。

托盘里的「切换点击穿透」刻意**不显示开关状态**：快捷键也能切换它，菜单里的状态会漂移。准确状态在设置面板里（`get_toggles`），并且 Rust 在每次变更后都会发 `signalhub://toggles` 事件——不发的话面板会一直显示过时的状态。

### 3.16 设置面板的组织：左栏三组 + 沉底的「系统」

设置面板拆成三组页签，左栏底下单独沉一个「系统」，见 `SettingsPanel.tsx::tabGroups`：

```
看        状态 · 历史
灯        外观 · 行为 · 分组
通知      提醒 · 转发
开始用    接入 · 指南
────────
系统      （左栏底部，用一道细线隔开）
```

**分组是为了修「轴不一致」，不是为了好看。** 最早那次改版（见下面的来历）把内容分成了七个平铺的页签，但没人规定过「一个概念该放哪一页」—— 于是「安静模式」「贴边吸附」在【外观】、同层概念的「点击穿透」在【系统】，「语言」也在【系统】。三次改版是三个人在不同时间加的功能，谁都不是故意；而**用户的代价**是「改这个去哪儿」取决于它当初进了哪个文件，只能一页一页找。现在这一根轴是**这一页在回答什么问题**：只读的观察（看）、它长什么样和怎么动（灯）、怎么告诉你（通知）、怎么把它接上（开始用）。

| 组 | 页 | 内容 |
|---|---|---|
| 看 | 状态 | 近 30 分钟时间线 + 按组列出的会话（一行一个会话：状态点 + 项目名 + 状态 + 说明）。**只读**：这一页回答的就是「现在发生了什么」。底部是最近消息流 |
| 看 | 历史 | 近 7 天，一天一行（横条宽度 = 那天各状态占用的时长，右侧合计）。数据每天落盘，保留 30 天 |
| 灯 | 外观 | 全局那层：**顶部的实时预览**、预设、形态、大小、形状、配色、背景透明度、牌宽 / 牌高倍率、牌间距、闪烁节奏、牌上显示哪几段（含圆点）。子页「质感」：圆角 / 描边 / **边灯** / 牌底 / 字号 / 字体 / 分层，末尾是**可折叠的角灯**（四个角各一个下拉，默认收起）。**再末尾是可折叠的「逐个状态覆盖」**（10 行的颜色 / 形状 / 节奏表，默认收起） |
| 灯 | 行为 | 安静模式、贴边吸附、点击穿透、保持在最前、托盘跟随状态 —— 全是「它怎么动」，一个像素的外观都没有 |
| 灯 | 分组 | **怎么分组**（不分组 / 按目录 / 按会话）+ **摆成几盏灯**（一盏灯 / 每组分灯），下面接各组的显示：显示名 / 置顶 / 隐藏 / 静音 |
| 通知 | 提醒 | 需要时弹通知、通知带提示音、**系统通知权限状态**、持续多久才提醒、勿扰时段 |
| 通知 | 转发 | 出站钩子列表（多条、可过滤、支持本地命令），每条可选**服务预设**（决定 body 形状）与**自定义请求头**（鉴权）；**发送测试**一个按钮把已配置的各发一遍 |
| 开始用 | 接入 | 把智能体接上（检测 + 一键接入 / 卸载）→ 只用命令行的那几家 → 一键诊断 → **试一下** → 局域网访问 |
| 开始用 | 指南 | 手册：这是什么、三步接上、接口速查、不工作了怎么办 |
| | 系统（底） | 开机自启、界面语言、**配置导出 / 导入** |

标题区（当前聚合 + 组数与会话数 + 今日时长）、左栏底部的「暂停监控」和面板底部的退出按钮**固定在内容区之外**——它们是「为什么我打开这个面板」和「怎么关掉」，任何时候都该看得到。

**「各组的显示」从「外观」搬出来独立成页。** 它是整个面板里**唯一会随会话数变长**的一节（按会话分组时一个会话一行），而「灯长什么样」是固定的九行 —— 留在同一页，后者会被前者一点点推走。同理，「逐个状态覆盖」在「外观」页里**默认收起**，标题右侧挂一行摘要（`3 个状态单独设过` / `未单独设置`）：十行表和上面那九行不是一个量级，而它回答的其实是「外观」的一个子问题。摘要和表格用的是同一个判据 `stateOverridden`（`lib/lampStyle.ts`）—— 两边不一致就会出现「摘要说 3 个、表里只有 2 行彩色」这种最难查的对不上。

**「状态」页和「外观」页的分工是「读」与「写」。** 改名、置顶、隐藏、静音原先散在「状态」页的组卡上：那一页因此成了全窗最长的一页，而且把只读的实时会话和写进去的偏好混在一起 —— 前者跟着上报每秒在变，后者是你设完就不动的。现在四样全部搬进「分组」页，并且「隐藏」「静音」各自收敛成一个开关（原先是一个「点一下恢复」的徽标加一个「静音」按钮，三种控件表达两个布尔量）。

**「分组方式」和「灯的数量」也从「接入」页搬进了「分组」页。** 它们原先挂在「接入」，理由是「管的是上报进来之后怎么解读」。但导航里明明有一页就叫「分组」，而这两项一个决定**有哪些组**、一个决定**这些组摆成几盏灯**，正是那一页的主题；「接入」页该回答的只是「别人怎么报给我」（端点、token、局域网、智能体）。两项挨着放、又都在说「分组」，很容易被读成同一个设置 —— 所以两句提示各写了半句分界（上面那项定「有哪些组」，下面那项定「它们摆成几盏灯」），这一条比放在哪一页更重要。

**两次改版是为了同一件事：让每一页只回答一个问题。** 最早那次（见上面的来历）是分页；第二次是**把「灯效」并进「外观」** —— 它们是同一件事的两层（全局默认 + 逐状态覆盖），分成两个页签只会让人在两个之间来回找「改颜色到底在哪」，所以现在合并成了「外观」页里那一段可折叠的小节。第三次（本轮）是把**轴**统一：拉出「行为」页，见上面那段。

**控件只有两种「选法」。** `seg`（带外框的分段按钮）管一组里选一个，`chip` 管选几个（筛选条件、牌上显示哪几段）。两者的选中态是同一套：浅灰底 + 正文字色 + 中等字重 —— 曾经 chip 是 accent 整块实心加白字，成了全窗最重的元素，而它表达的只是「这个筛选项开着」。两组「预设」（外观页的整块牌预设、逐状态页的风格预设）都是单选，所以都是 `seg` 而不是 chip。逐状态表里那两列因为列宽受限用 `select`，是**唯一记录在案的例外**。

**左栏的分组标题是标题，不是按钮。** 点它不该有任何反应（点一下「灯」却跳到某一页，会让人以为漏了一层）。样式抄 `.section-title`，但不加 `text-transform: uppercase` —— 中文没有大小写，套上去只是白设。

**左栏页签的选中态不是一个盒子。** 它曾经是 6px 圆角浅灰块加一条 2px 的 accent 竖线：在 140px 的窄栏里，每一行都像一枚待点的卡片，整列比右栏内容还抢眼，而它要说的只是「你现在在这一页」。现在与 `seg` / `chip` 统一成浅灰底 + 正文字色 + 中等字重，方角、无边框；hover 与选中同底不同重，靠字重就能分开「指针临时经过」和「当前所在页」，不必再叠颜色、竖线或圆角框。沉底的「系统」也用 flex 撑满整行，否则它的选中底只有文字那么宽。

**`.hint` 是次级文字，不是一个盒子。** 它曾经有边框、有内边距，一页三到六个，比正文还抢眼 —— 和「靠字号与灰度分层」这条自述原则直接冲突。现在它只是一段灰色说明；真需要重样式的是 `.error` 那类。

**「接入」页瘦下来的办法是把接口速查搬去「指南」。** 那一页曾经有 1013px 的内容、而可视区只有 433px —— 两倍多的内容墙。根因是它同时在干两件事：「点哪个按钮把智能体接上」（动作）和「端点表、状态词表、curl 示例」（查细节）。前者是第一次用的人要的，后者是已经接好的人要的，混在一起就把按钮淹没了。现在「接入」只剩智能体列表，「指南」是一份可以滚的手册 —— 并且「状态」页的空态里挂了一个入口，因为那是第一次用的人最可能撞上的地方。

**内容区改成「左栏导航 + 右内容」两栏，右栏高度交给 flex（窗口 720×690）。** 之前是顶部一行七个页签加一块**固定 495px** 的内容区：固定高是为了「切页签不会跳」，代价是短页留一大片空白、长页还得在里面滚。改成左栏之后，窗口高度固定，`.page` 用 `flex: 1` 吃掉标题区和底部之间的全部空间 —— **「切页签不会跳」从「写死一个够大的数」变成了结构性成立**，不必再为英文比中文多折一行预留余量。**「外观」和「指南」仍然允许滚**：前者的长度由那九行加可展开的十行表决定，后者本来就是一份手册。

**页签从顶部一行挪进左栏，同时把窗口从 560 加宽到 720。** 左栏不能白占地方 —— 720 − 140（栏宽）− 16（栏与内容间距）− 40（面板左右内边距）= 524 的内容区，比原来的 520 还宽一点。栏宽按最长的英文页签名（`Forwarding` / `Guide`）量出来，再宽就是从内容区身上刮肉。本轮加的分组标题（`Overview` / `Getting started`）比它短，放得下。

> **附带删掉了「按内容自动定高」。** 上一版为了让那一列不再被裁切，写过一个 `fit_settings_window`：前端量出内容高度、Rust 把窗口设成那么高。改成固定内容区之后，`.settings` 的高度恒等于窗口高度，`scrollHeight` 也就恒等于 `clientHeight` —— 那个测量变成了空转，留着是死代码。**它是被新设计取代的，不是被推翻的**：分页之前它确实解决了真问题。

**改设置的路径有三条**（设置面板、托盘、灯上右键菜单），而两个窗口都得跟着变。所以写设置的逻辑收在 `lib.rs` 的 `persist_settings` 一处：夹紧 → 存盘 → 改内存 → 应用（窗口尺寸 / 置顶）→ 广播 `signalhub://settings`。

**「打开设置并翻到某一页」靠一张一次性纸条**（`lib/settingsIntent.ts`）。`open_settings` 不带参数 —— 设置窗在启动时就以 `visible: false` 建好，命令只负责 `show()` —— 所以「翻到哪页」只能走同源 localStorage：写的一方在 `invoke` 之前写，设置面板读到就翻页并删掉。**读的时机有两处，缺一不可**：初始化一次（启动时就有纸条的情况），以及窗口每次 `focus` 再读一次 —— 设置面板的组件整个应用生命周期只挂载一次，只在初始化读的话，用户点「接入」时写的纸条永远不会被看到（`reveal_settings` 是 `show()` + `set_focus()`，所以 `focus` 就是「显形」的判据，和 `useVisibleRefresh` 同一个口径）。页面 id 用 `tabIds(m)` 校验，认不出来就退回「上次那页」，不会翻到一个不存在的页导致整页空白。

这是 §3.9 那条教训的同一个形状：**当一个功能有多条入口路径时，共享的那层逻辑必须只有一个入口**。三条路径各写一遍的话，漏掉「广播」那一步**不会报错**——只是设置窗里的开关偶尔显示过时的状态，最难查。

**演示页按「场景」切，而不是一条长剧本。** 原来是 7 步线性走一遍「一天里的状态流转」，但新用户点进演示往往只为看一件具体的事——「折叠成一颗灯长什么样」「智能体断线时灯怎么显示」。一条 20 秒的线性剧本要求他先等完不相干的前六步。现在 `demo.ts` 的 `DEMO_SCENARIOS` 分成四段：`day`（原来的七步，一步没改）、`asking`（黄灯、红黄同屏、出错与授权的区别）、`silence`（静默转灰、圆环形状下的剩余时间、牌消失后那句「没有智能体上报」）、`tucked`（安静模式、折叠态）。**每段自己循环**——`nextDemoStep` 到段尾回到段首而不是绕进下一段，否则画面会从一颗灯突然变回一张牌，像跳帧。数据仍然只有一份：场景摊平成 `DEMO_STEPS`，`demoSnapshot()` 是唯一出口，`aggregate` 由测试逐个盯着。折叠与安静走的是设置里真有的 `collapsed` / `quiet` 开关，静默环用的是 `state.rs` 的真实比例——**没有一个是只为演示编出来的字段**，否则这份演示会变成一份会骗人的说明书。

### 3.17 通知的三道闸门：静音 / 持续阈值 / 勿扰时段

**这三道闸门都只影响「要不要打扰你」，不影响「世界是什么样」。** 灯照常显示、聚合照常算、钩子照常触发、`/v1/state` 照常返回——它们只决定系统通知（和挂在通知上的提示音）发不发。

**按组静音（`muted_groups`）。** 静音掉的组不参与告警：`alerts::alerting_aggregate(snapshot, muted)` 在**没被静音**的组里取最高优先级的 `GroupView::alert_state()`（组里真实会话的最高优先级，不是被手动覆盖过的牌面），通知的**标题和正文都用它**。和 `snapshot.aggregate` 分开是刻意的——那个是全局的（托盘、钩子、`/v1/state` 都用它），静音一组不该让托盘变色、也不该让钩子不触发。全被静音时返回 `Offline`（不是紧急状态，闸门直接放行成「不弹」）；正文也按静音过滤，否则静音组的消息还是会出现在通知里。

> 这里踩到过一个不一致：标题原来用**全局**聚合，而正文过滤了静音组。当一个被静音的组恰好处于全局最高优先级时，通知的标题写着那一组的状态、正文却是另一组的会话——一条自己跟自己打架的通知。两处都改用 `alerting_aggregate` 就好了。

**持续多久才提醒（`alert_after_secs`，默认 5 秒，0 = 立刻）。** 智能体经常在一秒内进出 `permission`（先问再自己答，或者弹一下就被自动批准），立刻弹的话，用户被叫过去看到的是一个已经解决的问题。所以「需要你注意」的状态要**持续**够久才弹。

它替掉了原来那个 `should_alert(previous, current)`（那个只能表达「跃迁时弹一次」），换成 `alerts::Gate`：

```rust
pub enum Decision { Now, Later, None }
impl Gate {
    pub fn observe(&mut self, alerting: Signal, threshold: Duration, quiet: bool) -> Decision;
    pub fn confirm(&mut self, alerting: Signal) -> bool;
}
```

三个设计点：

- **`Gate` 是纯逻辑，不碰 `AppHandle`**，所以「阈值 + 静音 + 勿扰」三者怎么交互是被单测覆盖的，不是只靠跑起来看。它用两个标志接过了老逻辑：`notified` 实现「这个 episode 只弹一次」（一轮工具调用推几十次同样的状态，每次都弹就是骚扰），`pending` 保证一轮里只排一次延迟检查（否则几十次推送就是几十个定时器）。
- **延迟到点后重新从快照判断，不信排任务时捕获的值。** 到点时先重读 `alerting_aggregate`，再问 `sustained()`——后者读 `GroupView::since_ms`（「这一组进入当前状态的时刻」）。状态离开又回来是一个**新的 episode、新的计时**，只看捕获的 `Signal` 值会让一个过期的定时器提前开火。`sustained` 读 store 而不是自己记一份时钟，也是这个道理：store 是唯一的事实来源，自己记一份恰恰在那种情况下会说谎。判定用「任一组已持续够久」而不是「最早的那组」——几组同时处于同一紧急状态时，只要有一组卡了很久，这个状态就该算数。
- **`confirm` 顺手把 `notified` 置上**，于是重复到点的定时器不会再弹第二次。

**勿扰时段（`quiet_hours`）。**

```rust
pub struct QuietHours { pub enabled: bool, pub start: u8, pub end: u8 }
```

**只有小时、没有分钟**：分钟级精度只会让配置变麻烦，而「晚上十点到早上八点别吵我」本来就不需要分钟。起止都按**本地时间**，`covers(hour)` 处理跨午夜（22–8 读作 `[22,24) ∪ [0,8)`）；`start == end` 读作**空窗口**而不是「全天」，所以一个手滑调成一样，后果是「没生效」，而不是「从此再也不提醒我」。

**判断留在 Rust，前端只提供「现在几点 + 今天几号」这个事实。** Rust 这边没有时区数据（只有 UTC，仓库刻意不引 `dirs` / `chrono`），所以当前本地时钟只能由前端推——`src/lib/useLocalClock.ts` 每 60 秒调一次 `set_local_clock`，两个窗口谁活着谁推（值一样，多推一次没有代价）。而「在不在窗口内」的判断留在 Rust，因为跨午夜那种边界逻辑只有一处实现才敢信，而且那边能单测。**前端还没推过第一帧时，Rust 当作「不勿扰」**——宁可多弹一条，也不要因为一个尚未建立的事实把通知永久静掉，那会表现为「通知功能坏了」，最难归因。日期顺带推过去，是为了让**今日统计**也能跨天结算（见 §3.11）。

**勿扰期间彻底不弹，而且不补发。** 这一轮会被标记成「已通知」，之前排下的延迟定时器到点也会被 `confirm` 判成 false。刻意不做「延后补发」：补发意味着早上醒来面对一整夜攒下的通知，而那正是勿扰想避免的事。灯照常显示状态，所以什么信息都没丢。

### 3.17.1 卡住了就一直提醒

`Gate` 的 `notified` 实现的是「一个 episode 只弹一次」。那对「一轮工具调用推几十次同样的状态」是对的，但对**真正卡住**的情形不够：智能体卡在等授权上时是**真的什么都不做**，没人去管它就永远停在那儿。第一次通知弹的时候你正好在开会，回来只看到一盏红灯，完全不知道它已经卡了一小时。

所以通知之后会排一条**重复提醒链**：5 分钟、15 分钟、30 分钟各再提一次，然后停（`alerts::REMIND_GAPS`）。50 分钟后还没人管，再响多半也没用，而一直响就成了骚扰。

三个设计点：

- **正文不是把第一次那条重发一遍，而是明说等了多久**（`alerts::send_reminder` → `lang::stuck_for`）。「还没解决」和「已经卡了 20 分钟」是两条不同的信息，**后者才推得动人**。时长读 `GroupView::since_ms`，和 `sustained()` 同一个事实来源 —— 各算一份的话，两处迟早会对「到底卡了多久」给出不同的答案。
- **`Gate` 多了一个 `episode` 计数。** 状态离开又回到同一个值时是一轮新的（`alerting` 变过，只是恰好变了回来），上一轮排下的提醒必须认得出并失效 —— 否则它会替新一轮发一条「已等待 20 分钟」，而新一轮才刚开始。同样地，`Decision::Later` 那条延迟检查也补上了轮次判断：原来只看 `confirm(alerting)`，那对「离开又回来」是认不出来的，会拿旧一轮的检查替新的一轮开火、跳过它自己的阈值。
- **链上每一步都重判，不一路睡到底。** 这中间状态可能已经过去了、用户可能把通知关了、也可能进了勿扰时段 —— 任何一步发现不该提就整条停掉。判据全部现读（快照、设置、本地时间），不看排链时捕获的值。进了勿扰是**停掉**而不是延后补发，和第一次通知同一条理由：早上醒来面对一夜攒下的通知，正是勿扰想避免的。

### 3.18 托盘图标跟随状态

`Settings.tray_follows_state`（默认开）让托盘图标画一颗**实心圆点**、颜色取当前聚合状态的颜色，而不是那个单色的三点模板字形——不看悬浮灯也能知道现在什么情况。关掉（或某个状态没有可用颜色）就退回单色模板字形，跟着菜单栏明暗自动反色。

**宽高比换了一套。** 三点模板字形刻意压扁到 2.16:1（见 `tray.rs` 的注释：三颗点排成一行本来约 3.7:1，菜单栏放不下），而跟随状态的单点没有「排成一行」的问题，套用 2.16:1 会被拉成一个椭圆——所以单点另取**方形**边长，宽等于高。

**颜色表不在 Rust 里复制一份。** 颜色是「配色方案 + 用户逐个覆盖」解析出来的结果，只存在于前端的 `lib/palettes.ts`；前端用 `usePalettePush`（在 `App.tsx` 里调用）把算好的 `状态名 → #rrggbb` 表通过 `set_palette_colors` 推给 Rust。在 Rust 里复制一份就意味着两处会漂移，而「用户改了颜色但托盘不变」是最难注意到的那种 bug。`set_palette_colors` 收到后立刻重画一次托盘，否则用户改完颜色要等下一次状态变化才在托盘上看到。

**重画托盘有三条路径**（状态变了、颜色表变了、`tray_follows_state` 开关变了），都走 `lib.rs` 的 `refresh_tray`——少走一条的表现是「托盘图标偶尔不更新」，很难归因。这是 §3.9 那条教训的又一面。

**一个实现点：** 更新图标用 `set_icon_with_as_template`，而不是先 `set_icon` 再 `set_icon_as_template`——tauri 2.12.2 的源码注释里写明两步会在 macOS 上渲染两次、肉眼可见地闪一下。非 macOS 平台它会退化成 `set_icon`，模板标志本来也只有 macOS 认。

### 3.19 通知上的动作按钮

通知带两个按钮：**打开项目目录** / **静音该组**。目的是把「知道有事」变成「能动手」——原来的通知只告诉你哪个项目卡住了，剩下的还得自己回终端里找。

**按钮属于一个「动作类型」，而动作类型必须先注册。** 这是 macOS 的 `UNNotificationCategory` 那一套，插件在三个桌面上抹平了：`Notification::register_action_types` 注册一组按钮，通知再用 `action_type_id` 引用它。**注册类型和挂处理函数必须一起做**——插件在「没有处理函数」时会干脆不显示按钮（否则点下去没人接），而只做一半的表现是「按钮从来没见过」，且不报错。所以这两件事绑在 `alerts::wire_actions` 一个函数里。

**目标在发通知时记下来，不在回调时重算。** 按钮是用户点的时候才回调的，而那时状态可能早就变了：从当前快照重新算「优先级最高的会话」会指向另一个会话，用户点的按钮就作用到了别处。所以 `alerts::LastAlert` 存住这条通知说的是哪一组、哪个目录。只存最后一条——告警本身有节流（一个 episode 只弹一次），同时存在两条待处理通知实际上不会发生。

**目标会话和标题、正文用的是同一个**：`alerting_session` 算一次，三处都用它。各算一遍的话，一旦算得不一致就会出现「正文说 ci 要授权、点『静音该组』却静音了 work」这种自相矛盾的通知。

**「打开项目目录」把路径作为独立的 argv 传，绝不过 shell。** 那个路径来自智能体上报的 `cwd`，是不可信输入；拼进 `sh -c` 就是一个命令注入。（`outbound.rs` 的钩子走 shell 是因为那里用户就是要写管道和重定向，这里没有那个需求。）目录不存在时什么都不做——弹一个「找不到」的报错框比不动更烦人。三个平台各一条命令（macOS `open -R`、Windows `explorer /select,`、Linux `xdg-open`），子进程起完在一条后台线程上回收，免得留下僵尸进程。

**两个平台细节：**

- macOS 上**两个及以上的动作会收进「选项」菜单**，而点「选项」本身会上报**第一个**动作。所以第一个动作是「打开项目目录」——点了也无害的那个。
- 一旦挂上处理函数，插件对**所有**通知都会起一条线程等用户交互（它要靠这个才知道用户点了什么）。告警有节流，所以挂着的线程最多就是「今天弹过几条通知」那么多，不值得为它绕路。

> **未验证**：这一条同样受 §3.8 那条限制——`tauri dev` 跑的是未打包的裸二进制，macOS 的 `UNUserNotificationCenter` 需要 bundle identifier，所以按钮在 dev 下看不到。要确认得 `npm run tauri build` 出真正的 .app。菜单构造、回调分派、目标记录这几层都有单测，但「按钮真的出现在通知上、点了真的触发」没有实证。

### 3.20 界面语言

界面可以切成英文。**代码注释和 `docs/` 保持中文** —— 它们是给维护者的，这个仓库的行文（为什么这么决定、踩过什么坑）本身就是它的核心资产，翻译一遍既稀释了它，又让每次改动都要维护两份。

**分工和时区那条一模一样**：Rust 不知道系统语言（就像它不知道时区），所以 `Settings::locale` 存的是用户的**偏好**（`auto` / `zh` / `en`），由**前端**把它解析成具体语言（`navigator.language` 以 `zh` 开头就是中文），再调 `set_lang` 推给 Rust。前端提供事实，Rust 用它挑文案。

因此有两个「语言」类型，别混：

| 类型 | 在哪 | 取值 | 谁用 |
|---|---|---|---|
| `config::Locale` | `config.rs` | `auto` / `zh` / `en` | 用户的**偏好**，落盘 |
| `config::Lang` | `config.rs` | `zh` / `en` | **解析后**的语言，瞬态 |

**两个都在 `config.rs`**，而不是 `lang.rs`：`Settings` 要被 CLI 通过 `#[path]` 共用，而 `lang.rs` 是 app 侧的模块。`Lang` 一开始在 `lang.rs`（只有 app 用得上），CLI 也要挑自己的文案之后跟着搬了过去 —— 顺带避免了「把整个 `lang.rs` 拖进 CLI 换来一片 dead_code」的麻烦（CI 是 `-D warnings`）。同理，`Signal::label()` 从 `state.rs` 搬到了 `lang.rs` —— 它现在要分语言，而 `state.rs` 也在 CLI 的共用名单里。

#### CLI 怎么知道该说哪种语言

**CLI 是独立进程，`--help` 和报错也得跟着界面语言走**，否则用户在英文界面上敲 `signalhub --help` 看到中文会以为装错了版本。但它拿不到 `navigator.language`，所以按可靠性排了三个来源（`config::resolve_lang`）：

1. `config.json` 里的 `locale` 是**显式**的 `zh` / `en` → 直接用。用户明确选过，最权威，而且手改配置文件立刻生效。
2. 是 `auto` → 读 app 写下的 `~/.signalhub/lang`。那是界面**实际**在显示的语言（`set_lang` 时落一次）。
3. 还没有（app 从没跑过）→ 猜环境变量 `LC_ALL` / `LC_MESSAGES` / `LANG`。
4. 连环境变量都没有 → `Lang::default()`（中文）。

`lang` 文件是必需的，不是锦上添花：Windows 上根本没有 `LANG`，而第 2 条正好补上那个洞 —— 它是 app 写、CLI 读的运行时事实，和 `port` 是同一类东西。

**环境变量要做一次归一。** POSIX 写的是 `en_US.UTF-8`，而 `Lang::parse` 认的是 `navigator.language` 那一套（`en-US`）—— 少了 `normalize_posix_locale` 这一步，CLI 在几乎所有 Unix 上都会退回中文（实测踩到过）。

**文案在 `cli_text.rs`**，由 CLI 用 `#[path]` 包含，**故意不挂进 `lib.rs` 的模块树** —— 只有 CLI 用它，挂到 app 那侧换来的是一片 dead_code。

里面是两张并排的表（`ZH` / `EN`），占位符写成 `{}` 由 `fill` 从左往右替换。用运行时模板而不是 `format!`，是为了让两种语言能在同一个结构体里并排（`format!` 要求格式串是字面量）；代价是占位符写错编译器看不住，所以 `fill` 里有一句 `debug_assert` 逐个对数，而 CI 跑的是 debug 测试。

同样有两条防漏译的测试：一条逐字段比「两边都非空、占位符个数相同、英文那份里没有 CJK」，一条把 `--help` 在两种语言下都过一遍，检查子命令和选项一个不漏。

**原生界面必须单独处理。** 托盘菜单、灯上的右键菜单、通知的动作按钮、设置窗的标题都不经过 webview，前端换不了，所以语言一变就得重建。这几件事收在 `lib.rs` 的 `apply_lang` 一个函数里 —— 漏掉一处的表现是界面上混着两种语言，而那只有肉眼能发现。两个细节：

- 托盘菜单是启动时建好就一直挂着的，换语言只能整个换掉（`TrayIcon::set_menu`）。菜单项的 **id 不变**，所以事件分派不用动。
- 通知的动作类型重新注册一次即可（同 id 覆盖）。顺带一提，插件在「没有注册处理函数」时会干脆不显示按钮，所以 `wire_actions` 必须整体再走一遍，不能只改文案。

**文案表用「对象」而不是「字符串键」。** 前端是 `MESSAGES: Record<Lang, Messages>`，`Messages` 是一个接口 —— 加一条文案就得两种语言都加，TypeScript 会盯着。`t("look")` 那种键查找没有这个保障，漏一条就是界面上冒出一句另一种语言。Rust 那边同理：`NativeText` 结构体的每个字段都是 `&'static str`，两种语言各一份静态实例，`text(lang)` 挑一份。

**有一条测试专门盯「英文里还有没有中文」**（`lang.rs` 和前端各自一份）：把英文那份的每一条文案过一遍，看有没有 CJK 字符。漏译是这类改动里最容易发生、又最难自查的问题 —— 它不会报错，只会让用户看见一句中文。

### 3.21 配置导出 / 导入

整份 `Settings` 序列化成 JSON 存到用户选的文件里，「系统」页两个按钮。换机器、重装、或者想手工看一眼自己配了什么的时候用。

**职责切在最要紧的那一刀上：前端只用 dialog 插件拿一个路径，读写和校验全在 Rust。** 前端自己读文件再塞进 `set_settings` 就绕过了校验 —— 而导入这条路上校验是必须的。

导入走的是**和设置面板改设置完全同一条路**（`validate_settings` → `persist_settings`），所以：

- **不认识的状态名、非 `#rrggbb` 的颜色 → 明确报错。** 这两种是手改配置文件最常犯的错，而它们的兜底（`clamped` 是静默丢掉）只在「启动时读配置」那条路上合适 —— 那条路上总得起得来，这条路上用户是主动点的，静默什么都等于骗他。
- **超范围的值（尺寸填了 500）→ 夹回合法区间**，不拒绝整份文件。对「从别处拷来的配置」而言，因为一个数字越界就把其余全部退掉太苛刻了。

**坏文件报错，不静默套默认值。** 这一条和 `load_settings` 的兜底**刻意相反**：启动时读不出来必须继续启动（否则一个手滑的文件就让应用起不来），而导入读不出来必须说 —— 用户以为导进去了、其实什么都没变，是最糟的结果。

**导出用的是原子写**：导出的文件用户多半会留着当备份，而写了一半的备份比没有更糟。

有一条单测把每一项都设成非默认值再往返一遍（`Settings` 派生了 `PartialEq`，所以是精确比较）：漏一个字段、类型对不上，都会在那里露馅 —— 而不是等到用户换机器导入时才发现。

### 3.22 局域网访问：一个显式放宽安全模型的开关

默认只绑 `127.0.0.1`。跑在别的机器、容器或 WSL 里的智能体连不进来 —— 那正是「本机服务」这个安全模型的代价，也是它的价值。想跨机上报的人可以打开「允许局域网访问」，服务改绑 `0.0.0.0`。

**打开之后唯一的防线只剩 token。** 那道「带 `Origin` 头一律拒绝」的中间件挡的是「你正在浏览的某个网页偷偷去打本机端口」——它是**针对浏览器**的，对 `curl` 这类客户端完全无效（人家不发 `Origin` 就行了）。所以开了之后，同一网段里任何人拿到 token 就能上报。这不是实现缺陷，是这个功能本身的代价，所以：**默认关、要显式打开、界面上把代价写清楚**（说明分两段，代价那一段单独成句，不藏在操作说明的尾巴上）。

**改完要重启应用才生效。** 监听地址只在启动时绑一次；运行中重绑会让端口变化（首选端口可能已被占用，于是退到系统分配），CLI 的自动发现跟着断一下 —— 出错时表现为「灯突然收不到上报」这种极难归因的现象。与其在运行中做这件事，不如写明「下次启动生效」。

界面靠**两个值**判断要不要提示那句话：设置里的 `lan_access`（用户想要什么）和服务**实际**绑到哪了的 `bound_lan`（`server::spawn` 在真的 `bind` 成功之后回填）。两者不一致时才提示 —— 无条件挂一句会让人以为一直没生效。

**唯一真正决定安全模型的那一行被抽成了纯函数**（`server::bind_host(lan)`），配了单测钉住两个分支和「默认必须是关的」。写成内联的三元表达式就只能靠跑起来看，而这一行值得比那更硬的保障。

`local_ip()` 用「连一个 UDP socket 再看自己的 `local_addr`」这个经典办法拿本机在局域网里的地址：UDP 的 `connect` **不发任何包**，只做一次路由查找，所以不引入依赖、也不产生流量。取不到就返回 `None`，界面上不显示 —— 它只是给人看一眼，不该因此报错。

### 3.23 降级通道：app 没在跑的时候不丢事件

hook 上报是「一次 HTTP」。app 没在运行时（重启电脑、退出 app、刚装还没启动）**那些事件会静默消失** —— 而 hook 在后台跑，用户根本不会发现灯少了什么。`docs/api.md` §5 此前一直写着这条「还没做」。

现在：CLI 在**连不上**时把这一条追加到 `~/.signalhub/spool.jsonl`（`spool.rs`），app 启动时按原顺序补进状态机，然后删掉这个文件。

**只攒「连不上」，不攒别的失败。** 4xx/5xx 是这次请求本身不对（或服务端明确拒绝），重放只会再错一次；超时也不攒 —— 超时的那个请求**可能已经被处理过了**，重放会造成重复，而重复的一条会把已经前进的状态倒回去（一次迟到的 `done` 能让 `working` 复活）。判据就是 `classify` 给出的 `not_running`（连接被拒 / 连不上），那正是「app 没开」这件事本身。

**`read_response!` 里的那个 `?` 曾经把最常见的那种失败整条吞掉。** `?` 是把失败从**当前函数**抛出去的，而它原本长在 `hook()` 里：于是「连不上 app」这条最该被记下来的故障绕过了日志（更不用说攒盘），直接抛到 `main`，只印一行 stderr。修法是把「真的发出去」这一步挪进 `send_action()` —— 失败在那儿是一个返回值，由 `hook()` 决定怎么记、要不要攒。日志里那句「失败: SignalHub 没有在运行（已存下，app 启动后自动补上）」就是它的落点。

**有界，而且满了从最老的丢**（`spool::MAX_BYTES` 256 KiB / `MAX_LINES` 200）。hook 是每次工具调用都跑一遍的，没有上限的话，一次「app 忘了开」的周末就能堆出几百 MB，第二天一起来就要解析它。留下的必须是最新的那一段活动 —— 三小时前的记录重放时本来就会被 TTL 判过期，保它等于白占位置。写盘失败一律吞掉：hook 是用来监控别人的，自己不能变成故障点。

**补进来的记录按「原本那一刻」起算。** 这是重放的语义核心：一条四分钟前的 `working`（TTL 五分钟）补进来之后应该**只剩一分钟**，而不是又拿到完整五分钟 —— 后者会让一块本该消失的牌在灯上多待四分钟。做法是拿记录里的 `at_ms` 算出「过去了多久」，再从 TTL 里减掉；**减到零或负的直接丢**。所以「一条三小时前的 `working`」不会补出来 —— 它确实过期了，补出来只会是一块「沉默」的牌（而且还会再挂 30 分钟宽限期）。判据和正常上报共用 `state_ttl`，重放只是多给一个「剩余时长」而已。

**重放走和 HTTP 上报同一条路**（`server::ingest_core`，分组解析 + 状态机 + TTL 规则都在那一份里）。只有推送不同：HTTP 是每条都推，重放是**攒完推一次**。逐条推的话，一次退出期间攒下的事件会让灯闪一阵子，而且每一条都会过一遍通知 / 出站钩子的判断；攒完推一次拿到的是**最终**状态，那才是用户真正该看到的。

**时机在 `axum::serve` 之前**（端口文件已经写好，但一条连接都还没被处理）：这样「先补旧的、再收新的」这个顺序是被保证的，不会出现「新的先进状态机、旧的后进来」把状态往回跳。判据是**文件里有没有东西**，不是「端口文件在不在」—— 进程崩过之后端口文件还在，那是常见的假阳性。

补了什么、丢了多少，都在 `hooks.log` 里留一行（`[spool] 重放 N 条，丢弃 M 条（过期）/ K 条（读不出）`）—— 那是用户唯一能查的地方。已知的取舍：重放**不追溯「已持续」**（牌上的时长从补进来的那一刻重新算起）—— 严格起来要把上报时刻一路带进状态机，而那个数只影响一个显示值。

### 3.24 自动更新：检查可以自动，装必须由用户点

常驻应用悄悄换掉自己的二进制是用户不该遭遇的事 —— 所以这里只把**检查**自动化：启动 15 秒后查一次，之后每 24 小时一次（`update::FIRST_CHECK_DELAY` / `CHECK_INTERVAL`），查到有新版本就在【系统】页摆出来，等用户点。

**自动那条路的失败是静默的。** 不能因为 GitHub 抽风就给一个常驻应用弹错误。自动检查的失败只写 `hooks.log`（`[update] 检查更新失败: …`），**不写进**给界面看的状态里 —— 用户没点过「检查更新」，就不该在我们的界面上看到一条他没法解释的失败。反过来，用户主动点的那次失败会如实摆出来（`state.error`）：**「点了没反应」和「明确说失败」是两件事，前者是 bug。**

**验签用的是 Tauri 自己的密钥对**（minisign）：公钥在 `tauri.conf.json` 的 `plugins.updater.pubkey`，私钥只在 GitHub Secret 里，构建时由 `tauri-action` 那一步的 env 传进去。它和 Apple / Windows 的代码签名证书是**两套完全独立的东西** —— 校验的是「这个包确实是我们发的」，不是「Apple 认识我们」，所以没有证书也能做自动更新。

**只有 macOS 真的能用，另外两个平台如实说「请手动下载」。** 理由要分两半说，别把话说错：

- **Windows 是上游卡住的**：插件的 `zip` feature 要求 `zip = "^4"`，而 2026-08 的 RUSTSEC-2025-0168（解包时路径规范化不当 → 任意写文件）之后，crates.io 上**所有 zip ≤ 9.0.2 都被 yank 了**，`^4` 无解 —— 带着这个 feature 连依赖都解析不出来。Windows 的更新包就是 `zip` 那种，所以那条路技术上做不了。
- **Linux 是「做得通但没验过」**：查过 v0.2.4 的实际产物，`latest.json` 里 `linux-x86_64-appimage` 指的是**没压缩的 ELF AppImage**，不吃 `zip` feature，那条路其实走得通；但 deb 装的那份要靠 `dpkg -i` 提权（普通用户跑不动，会变成一个「点了报权限错」的按钮），而两条路都没在真机验过。**在能动真机验收之前不打开。**

macOS 的 `.app.tar.gz` 只用 `flate2` + `tar`（插件里的**非可选**依赖），和那个 feature 无关，所以那条路完整可用。`Cargo.toml` 里因此写的是 `default-features = false`，判据是 `update::SUPPORTED`（只有 macOS）；**上游把 zip 提到 ^9 之后**把那行收回去，**Linux 要打开**则是改 `SUPPORTED` 一行（先把两条装法在真机上跑通）。界面按 `supported` 分流：不支持的平台不给「下载并安装」，只给一个「打开发布页」（`open_releases`）—— 说清楚之后总得给个去处。

**点「下载并安装」时会重新查一次**，而不是装「十分钟前看到的那一版」。代价是多一次网络往返，换来的是「装的一定是此刻的最新版」，也省掉了把插件的 `Update` 对象跨命令存起来（那东西带着 HTTP 客户端和一堆内部状态）。装完走 `app.restart()`：不重启的话跑着的还是旧二进制，用户点了「安装并重启」却什么都没变。

**界面上的版本号是「运行时事实」，不是检查结果**（`update::stamp`）：非 macOS 上永远不会走到网络那一步，只靠检查去填的话那边会一直空着。

还有一条**只能真机验**的：未签名的 macOS 应用被更新替换之后，Gatekeeper 会不会拦。验过之前不要对外说 macOS 上自动更新可用（见 `docs/plan-round3.md` 的 R5）。

### 3.25 收件箱与跳转（0.4）

灯解决的是「抬头看一眼」，但真正要花时间的是**接下来那一步**：找到是哪个窗口、点允许、切过去。收件箱把这一步做成一个贴着灯出现的小窗口，而不是设置面板里的又一页 —— 设置是低频配置，收件箱是高频操作。

**窗口**：独立的 `inbox` webview（初始 420×560、最小 360×320、可拉伸，深色 HUD、无边框、始终置顶）。开在灯**左侧**、底边对齐；左边放不下就放右边，两边都放不下才居中（`inbox::place` 用 `outer_size()` 读实际尺寸，是带负坐标工作区单测的纯函数）。无边框窗口没有系统给的 resize 边缘，右下角一枚 14px 的把手调 `startResizeDragging("SouthEast")`。失焦 / Esc / × 都只隐藏不销毁 —— 和设置窗同一个理由；隐藏时如果设置窗也没开，把激活策略退回 Accessory。

**关窗只隐藏的代价要记住**：前端组件整个应用生命周期只挂载一次，所以「每次打开都要做的事」不能写在 `useEffect(() => …, [])` 里。`inbox.rs` 在 `show()` 广播 `signalhub://inbox-shown`，在**三条隐藏路径**（`hide()`、`Focused(false)`、`CloseRequested`）上各广播一次 `signalhub://inbox-hidden`，前端据此重算离开摘要、推进「上次看过」的基准。早先靠挂载算一次的写法，第二次打开就再也没有摘要了。

**数据**：仍然只有两个来源 —— `useSignal` 的快照（会话）和 `useApprovals` 的登记表（待审批）。`inboxRows.ts` 把两者摊成「需要你 / 运行中 / 刚刚完成 / 空闲」四段，**一个会话最多一行**（同时有审批时合并，否则同一窗口会出现两次，一次能点允许、一次不能）。排序规则：需要你里 `error > permission > attention`，同类里等得最久的在前；审批的等待时间取审批自己的 `age_ms`。

**一行两段信息**（2026-11 重排）。第一行只有项目名和右对齐的等待时长：名字 `flex: 1` 独占剩余宽度（`min-width: 0` + ellipsis），才不会被多机徽章和状态挤成「Signal…」；等待时长右对齐后在几行之间形成一列可扫的读数 —— 那正是这个窗口要回答的第一个问题。第二行是灰字元信息：机器徽章 / 智能体 / 目录末段（`inboxRows.dirName`，整条路径在 `title` 里）/ 状态文字。**状态保留文字，不只靠颜色**：红点在「授权」和「出错」之间是同一个颜色，而读屏器读不出颜色。

**主次动作分层靠显式展开，不靠 hover。** 允许 / 拒绝（含理由 ▾）/ 跳转常驻；盯住 / 静音 / 清除收进行尾的 ⋯，点开才出现在第二排（同时只开一行）。早先的做法是 hover 或键盘选中时让它们直接显形，结果指针一划过按钮墙就冒出来、行被撑成两排、整列下移 —— 正要点的「允许」正好被推走。「清除」因此多了一步，这也是刻意的：它是唯一不可撤销的动作，本来就不该和「允许」并排。

**空态给两条出路**：「接入智能体」（设置 → 接入页）和「看演示」（设置 → 演示页），都走 §3.16 那张一次性纸条。第一次打开收件箱的人拿到的如果只是一句「现在没有需要你处理的事」，等于不给下一步 —— 而那一刻正是他最可能什么都不懂的时候。

**「需要你」那一段只把底板和标题各抬一档**（`--row-bg` 0.035 → 0.055），不加左边框、不加色条：那是设置面板里被否掉过的强调语言，而这里要的只是「先看这段」。

**审批**：允许 / 拒绝走的是灯上气泡同一个 `Registry::decide`，「看不全不给放行」在 Rust 登记表里挡着，收件箱只是一个新入口。审批的 `detail` 仍然只进本机窗口，不进 `/v1/state`、通知和出站钩子。

**跳转**（`jump.rs`，macOS 优先）：会话的 `pid` → `ps -o tty=` → `ttys003` → tmux pane（`list-panes` 按 `pane_tty` 匹配，选中后按 client tty 找外层终端标签页）或 Terminal.app / iTerm2 的标签页（AppleScript，按 tty 精确匹配；第一次会请求「控制终端」的自动化权限）。找不到精确标签页时按父进程链认出终端 / IDE，激活应用；再不行才在 Finder 里打开项目目录。**每一层都在返回值里说清楚做到了哪一步**，不猜、不假装。所有外部命令走 argv、不过 shell；tty 只放行 `[A-Za-z0-9/._-]` 且拒绝 `..`。

**入口**：`⌃⌥I`（`Ctrl+Alt+I`）、托盘菜单第一项、灯上长按 480ms 呼出的圆环菜单第一项、第二次启动应用（单实例回调打开收件箱）。**v0.5.0 的手势重做之后，左键单击是折叠 / 展开，双击已取消** —— 单击因此不再需要 280ms 的双击判定窗口，拖拽优先并取消待执行的单击，见 `SignalLamp.tsx::useDragOrClick` 与 `plan-round5.md:84-85`。这段历史写过「左键开收件箱」，那是重做之前的方案。

**限制**：精确定位终端目前只在 macOS 上；Windows / Linux 先做到「打开项目目录」。IDE 内置终端没有能精确定位标签页的公开接口，只能激活编辑器。ad-hoc 签名的版本更新后，「控制终端」的自动化授权可能需要重给 —— 和这个应用没有 Apple 证书这件事是同一个根因。

#### 3.25.1 「你离开的这段时间」

收件箱回答的是「**现在**谁在等我」，但真实场景常常是**离开一阵子再回来**：这期间完成了几个、失败了几个、有没有人一直在等。摘要就一句话，放在列表上方、可以关掉。

**两份数据各管一半**。`awaySummary.ts` v2 对快照仍用老判据：每条会话当前状态的起点（`now - age_ms`）晚于「上次看过收件箱的时刻」——也就是「这条在我离开之后才变成现在这样」；`age_ms` 服务端已经算好了，收件箱本来就要用它显示「等了 3 分钟」。另一半来自 [§3.25.2](#3252-事件流水本周洞察与跑完叫我) 的事件流水：窗口内的 `end` 事件里，那些此刻已经不在快照中的会话，单独报成「另有 N 个跑完就结束了」。两份按 session 去重，不会重复计数；事件读不到就退回只看快照。

**「上次看过」存在 localStorage**（`signalhub.inbox.lastSeen`），不进设置文件：它是运行时的观察记录，不是用户偏好，进「配置导出」没有意义。收到 `inbox-shown` 时用当前基准算一次摘要，收到 `inbox-hidden` 时把基准推进到当下；组件卸载（退出应用）再补写一次。少了隐藏那一次，收件箱开着一小时后关掉，下次打开会把这一小时也算成「你不在」。没有基准时 `buildAwaySummary` 直接返回 `null` —— 不猜「离开期间」。

**离开不足 10 分钟不出摘要**（`AWAY_MIN_MS`）。短于这个数回来，那些行本来就是刚看过的，再顶一条摘要只是噪音。从没打开过收件箱（没有基准）时也不出 —— 没有基准就没有「离开期间」。

**两件它做不到的事**（写在 `awaySummary.ts` 的注释里，免得以后被当成 bug）：

1. 离开期间状态变过好几次、最后又回到原样的，只按「最后一次变化」算一次；事件那一半也按 session 去重，不按「几次变化」说话。
2. 只统计四档（完成 / 失败 / 在等 / 在跑），`idle` / `stale` / `offline` 不计 —— 它们说的是「没在干活」，不是「发生了什么」。

### 3.25.2 事件流水、本周洞察与「跑完叫我」（0.5.1 之后）

`plan-round5.md` 定的三步走是「发现谁需要你 → 当场处理 → 回到工作时给摘要」，并写明「这一版先做前两步」。第三步的第一版摘要只有基于快照的计数，出现过又消失的会话一个都看不到。这一节补的就是那段记忆。

**唯一出口，不是第二套状态机。** `events::tap` 包在 `notify::compose` 的 `coalesce` **外层**：`crate::mutate`（HTTP / CLI / hook / 手动状态 / 远程会话）和 `sweep::spawn`（探活、TTL 到期）都汇到 `Notifier`，所以在这一处把每帧快照和上一帧对比就够了。`Observer` 只记 `HashMap<session id, 上次摘要>`，diff 出 `start`（新增）/ `change`（状态变了）/ `end`（消失，带最后已知状态）。挂在合帧外层是刻意的：`coalesce` 只送 100ms 里最后一帧，而一轮里「出现 → 完成」的中间态正是流水要保住的。只认**状态**变化、不认 `message` —— 一轮工具调用会改几十次说明，全记下来会把真正的跃迁淹掉。

**落盘沿用 `approval_log.rs` 的形状**：`~/.signalhub/events/YYYY-MM-DD.jsonl`、append-only、目录 `0700` / 文件 `0600`、坏一行只丢一条、留 30 天（`events::prune` 启动时跑一次）。日期换算和「按时间下界读」都复用 `approval_log` 的 `day_key` / `read_since_in` —— 两份日志的文件名约定一样，各写一份历法迟早在跨零点那天对不上。盘上只有「谁在什么时候变成了什么」和截到 200 字的短说明，**不存命令原文**；写盘失败只记一行日志，绝不挡住灯（流水是增强，不是状态机的依赖）。

**三个消费者，都只做加法**：

- 收件箱摘要 v2（§3.25.1）：补上已经从快照里删掉的那些。
- 历史页「本周洞察」（`insights.ts`）：近 7 天事件 + 审批日志，按会话去重后回答「哪个项目最闹、哪个智能体最活跃、最常被拒绝的工具是什么」，以及审批等待的总和与中位数。两份日志各最多读 5000 条、取最新的，界面如实写出上限，**真的撞到上限时再补一句「数字可能偏小」** —— 截断后的数据不能当全量结论；读盘失败走 `Result` 让 IPC reject，卡片显示「读不到」，**不画成「没有记录」**。活跃日按所有事件的 `session × day` 去重，不只数 `start`：跨天的长会话第二天没有 `start`，但它那天确实还在跑。
- 「跑完叫我」（`watches.rs`）：收件箱按 session 订阅，`done` / `error` / `end` 时发一条通告并立刻移除订阅。**远程会话的 `end` 例外**：它靠几秒一次的拉取维持，TTL 一抖就整批消失、下一拍整批回来，把它当「跑完」既误报又会把订阅提前用掉；真完成时远程也会先送 `change: done`，那条照样触发。它补的是告警看不到的那一类事件 —— 一个跑了二十分钟的构建全程绿 `working`，全局聚合一次都没跃迁，永远不会通知你「它好了」。订阅只活在内存、触发即移除、不落盘；通知走 `alerts::send_message`（固定不带声音），**不受勿扰时段影响**是刻意的：勿扰是「全局别打扰我」，而这是用户针对单个任务点名要的那一条，也不补发。触发后 Rust 广播 `watches-changed`、前端重拉 `get_watches` —— 收件箱窗口常驻只是隐藏，不广播的话通知都响了，按钮还停在「取消盯」。

**两个只在运行时才炸的坑**（都写回代码注释里了）：

1. `watches::fire` 取语言 state 必须用 `crate::SharedLang`（`build()` 注册的是 `Arc<LocalLang>`）。Tauri 按 `TypeId` 取 state，写错类型**编译期不报错**，运行时才 `state() called before manage()` panic；release 下 `panic = "abort"`，表现是每帧一有事件应用就退出。所有取 state 的地方一律用注册时的那一个类型，`try_state` 兜住启动期。
2. 系统时钟回拨到 epoch 之前时 `now_ms()` 给 0，会写出一个 `1970-01-01.jsonl` —— 而 `read_since_in` 用 `ts_of >= since_ms` 永远读不回它。`append_in` 直接拒写 `ts_ms == 0`。

**今日复盘刻意不变**：它按聚合状态计时，同一时刻只记一个状态，各项可以直接相加；逐会话的事交给旁边那张洞察卡。两张卡问的不是同一个问题，不要合并。

### 3.26 多机中枢：远程会话就是普通会话（0.4.2）

灯答的是「本机上谁在忙」，而 agent 越来越多地跑在别的机器上 —— 服务器、另一台笔记本、
WSL 里。多机中枢让一台机器（hub）把其他机器（对端）的看板拉过来，合并进**同一盏灯、
同一个收件箱、同一块只读看板**。完整方案见 [plan-multi-machine.md](./plan-multi-machine.md)。

**方向是拉，不是推。** hub 每 2 秒对每台对端 `GET /v1/state`，也就是普通的状态查询
接口，没有任何新端点。决定性理由是**对端不用升级**：那个接口从 0.1 就有，所以一台
0.4.x 的机器立刻能当对端，只要它开了「允许局域网访问」并把 token 抄过来。推的方案
要求两台机器都升到同一个新版本，而「让用户把两台机器都升级」是真实的摩擦。

**远程会话不另立数据结构，直接喂进同一个 `Store`。** 这是整个设计里最重要的一个决定：
下游有七个消费者（灯、收件箱、托盘、通知、统计、物理灯、只读面板），它们全都只认
`Snapshot`。另立一套就要在七处各写一次「本地 + 远程」的合并，而那七份迟早会漂移。
喂进去之后，隐藏 / 静音某个组、30 天统计、WLED 聚合色、手机看板**全部零改动**生效。

代价写在这里：远程会话会进统计、会触发通知。前者是对的（hub 的统计本来就该是全局的），
后者由既有的「静音某个组」兜住 —— 不为它加第八个开关。

**命名空间**：会话 id 是 `m:{机器名}:{对端会话 id}`，组名是 `{机器名}/{对端组名}`，
牌上通过 `default_label` 读作 `{机器名} · {组名}`。`m:` 前缀同时是**循环防护** ——
拉取时跳过对端快照里以它开头的会话，于是 hub A 拉 hub B、B 又拉了 A 时不会无限套娃。
它还是 UI 的判据：收件箱据此把「跳转到终端」关掉，因为那个 `cwd` 在对端机器上。

**失联由 TTL 兜底**：每个远程会话按 `max(3 × 轮询间隔, 6 秒)` 上报，对端一掉线就
自然过期 —— 不需要另做一套心跳超时。连续 3 次失败后额外造一条 `error` 会话
（`{机器名} · 连不上 · {原因}`），因为「机器挂了」和「机器上没有 agent」在灯上是
同一个样子（没有牌），而前者恰恰是最需要知道的那一条。

**锁序**：网络 I/O 一律在 `Store` 的锁外。对端可能超时 3 秒，握着状态锁等它等于让
整个灯的刷新停 3 秒。健康状态表在合并前先整份拷出来，避免「持 store 锁去拿 registry
锁」这对嵌套 —— 死锁的唯一来源。

**不做的事**：远程跳转（SSH 过去开终端）、远程审批（要先解决「谁有权点」）、中继 /
公网穿透。三条都写在方案的 §6 里。

### 3.27 Call Me：让外面的智能体来找你（0.6）

灯和收件箱答的是「我的智能体在干什么」。Call Me 答的是另一个方向的问题：**我写的东西
被别人读了，读的人想给点意见，怎么送到我这里来？** 做法是把一条链接贴进文章，读到的
AI 智能体通过用户自己的服务器发一条留言；桌面端定时拉回来，在设置面板的「留言」页
阅读（0.6.0 起阅读独立成页，配置在「连接 → Call Me」，见 §3.28），并能一键打开出处回去改。

**它不进 `Store`，也不进收件箱。** 这是本节最重要的一条分叉，和多机中枢的做法刚好相反
（§3.26 说「远程会话就是普通会话」，这里刻意不复用）：留言不是状态信号 —— 它没有 TTL、
不参与优先级聚合、不该让灯变色。收件箱回答的是「哪个智能体卡住了，要不要授权」，那里
每一行都有可执行的动作（跳到终端、允许 / 拒绝）；留言是**要读的文字**，读完只需要回去
改文章，没有即时动作可做。两者混在一起，收件箱会变成两种东西的拼盘，而「需要你」那一段
会被「有人夸了你」淹没。所以它有自己的数据（`CallMeState`）、自己的事件
（`signalhub://callme`）、自己的页面。

**拉，不是推。** 桌面端在 NAT 后面，公网服务器推不进来 —— 与多机中枢同一个判断。客户端
每 `callme.poll_ms`（默认 15 秒）`GET /v1/callme/messages` 与 `/v1/callme/sources`，用
`after=<最大 seq>` 增量拉取；重启后首跳不带游标，取最近 200 条，让页面一打开就有东西读。
合并按 `seq` 去重（首拉和后续增量会重叠），内存留最新 500 条。

**每处一条链接，而不是全局一条。** 链接里带的是**每条链接各自的令牌**（32 位 hex，
128 位熵），服务器据此知道「这条留言来自哪篇文章」，于是可以单独配额、单独吊销；客户端
拼上自己配的域名就是完整 URL，服务器不需要知道自己被哪个域名访问（反代 / 多域名都成立）。
来源标识靠链接本身而不是智能体自报的 `source` 字段 —— 后者可伪造，前者不能。

**服务器是独立 crate（`server/`），不进 src-tauri。** Tauri 会链接 webkit2gtk 等一整套
系统库，而服务器要跑在裸 VPS / 容器里；把它放进 src-tauri 等于要求服务器也有桌面环境。
也没有建根 workspace：那会把 target 目录从 `src-tauri/target` 挪到仓库根，破坏
`scripts/stage-cli.mjs` 找 sidecar 产物的路径，以及 CI 的缓存键。代价只是多一份
`Cargo.lock` 和一个 CI job，换来的是部署镜像里没有任何 GUI 依赖。

**存储用 JSONL，不引 SQLite。** 写入量极低（每链接封顶 50 条/24h），消息 append-only，
查询只有「按游标顺序拉」「按来源过滤」「数窗口内的条数」三种；SQLite 要带 C 编译，Docker
构建和交叉编译都多一道坎。`messages.jsonl` 一行一条，出问题在服务器上 `cat` 就能排障。
`seq` 全局单调、启动时续接最大值，同时充当客户端游标。

**防滥用是三道闸门**：每 IP 每小时 10 条（内存固定窗口，重启清零可接受 —— 这是限速不是
账本）、每链接滚动 24 小时 50 条（直接数内存消息表，单一事实来源，且不依赖时区）、正文
4000 字符（按字符数不按字节）。另外两个细节：带 `Origin` 头的请求一律 403（这个端点只给
智能体 / curl 用，挡掉「你正在浏览的网页偷偷 POST」那一类）；吊销和不存在返回同一个 404，
不给探测者区分。`CALLME_ADMIN_TOKEN` 为空时服务器**拒绝启动** —— 公网服务不能裸奔；
比较用常数时间，不因前缀匹配泄露。

**已读状态存本地**（`~/.signalhub/callme_read.json`，`source_id → last_read_seq`）：
已读是界面状态，服务器可能迁走 / 重装，它不该跟着数据走；这也让服务器保持纯 append-only，
不需要「已读」这种会被并发改写的字段。

**MVP 不做系统通知，只做页面红点。** `Notifier` 的六件事（布局、统计、托盘、出站钩子、
系统通知、推事件）全部键在 `Signal` / 组名语义上，为留言单开一条通知通路要绕过勿扰时段
和静音组两道闸门，而这两道闸门正是「什么时候打扰你」的全部约定 —— 绕过去等于多一套
没人维护的规则。红点已经满足「知道有新留言」，留作后续增强。

**TLS 交给反向代理。** 服务器只监听明文 HTTP；Caddy 两行配置就能自动签 Let's Encrypt，
而自己在 Rust 里接 ACME 会把部署复杂度翻倍，收益为零。客户端走 ureq + rustls，`https`
开箱即用。

**链接自己带着用法（0.6.0 之后补的一块）。** 第一版把请求体写在 `docs/api.md` 里，
默认智能体读过文档 —— 实际上它只拿到一条贴进文章的短链接，既不知道要 POST，也不知道
该带哪些字段；让用户把说明一起贴进文章又会把链接变长，正是这个功能最不该做的事。现在的
解法是**同一条路径按方法分叉**：`GET /c/{token}` 返回纯文本用法（方法、`Content-Type`、
四个字段、curl 示例、限额、错误码），`POST` 仍收信。链接一个字符都没多，智能体先 GET
就会了；人在浏览器打开也读得懂。GET 对不存在 / 已吊销的令牌同样 404，不额外泄露
「这条链接还活着」。

**来源信息由第一条留言回填。** 用户建链接时要填「名称 / 放在哪个文件」是同一类错误：
这两样只有智能体知道。现在 `create_source` 接受空 `label`，生成 `link-<id>` 并标记
`auto_label`；第一条带 `title` 的留言把名字换成文章标题，第一条带 `context` 的留言把出处
填进 `note`，各只回填一次 —— 名字不会随每条留言变，用户手填过的名字不被覆盖。写回
`sources.json` 失败只记日志、不让留言失败：那是显示信息，正文已经落盘了。

### 3.28 设置面板重排与本机 Call Me 服务（0.6.0）

到 0.6 为止设置面板已经有十几个页签，而问题不是「页签太多」，是**三类任务混在同一层**：
看内容（状态 / 历史 / 留言）、配功能（灯 / 通知 / 连接 / 服务器 / 系统）、找帮助（指南 /
演示）。最刺眼的是 Call Me —— 服务器配置、链接管理、留言阅读纵向堆在一页，而配置是低频
动作、阅读是高频动作，每次看留言都得先经过服务器地址和 token。

**现在的轴是「这一页在回答什么问题」**，五组 + 一个沉底的「系统」：

```text
工作台  状态 / 历史 / 留言
灯      外观 / 行为 / 分组
通知    提醒 / 转发
连接    接入 / 多机 / Call Me
帮助    指南 / 演示
系统    通用 / 更新与诊断 / 数据     ← 由左栏单独渲染在最下面（齿轮位）
```

**只给三个复杂页面加页内子页，不再加全局页签。** 接入（智能体 / 其他来源 / 网络与诊断）、
Call Me（链接 / 服务器）、系统（通用 / 更新与诊断 / 数据）这三页各自都有两倍于可视区的内容，
把它们拆成页内子页比继续往左栏塞更划算：左栏只有 140px，每多一页就从正文那里拿一像素；
而页签数一旦超过一屏，「翻页」就变成了「先搜索」。

**「留言」独立成页是这一轮的核心决定。** 阅读和配置不是同一种任务：读留言要的是未读、
筛选、展开、打开出处；配服务器要的是地址、token、端口、部署命令。挤在一页的后果是未读点
只能挂在配置页上 —— 提醒指向了用户并不想读的那一页。现在红点挂在「留言」上，Call Me 只剩
链接与服务器两个子页。两页共享同一个 `useCallMe` 实例（在面板壳里创建一次），所以事件监听
仍然只有一份，未读数不会因为分页而不同步。

**页签结构搬进 `lib/settingsNavigation.ts`。** 原来它写在 5000 行的 `SettingsPanel.tsx` 里，
加一页要同时改 `type Tab`、别名表、分组函数、`tabIds()` 和 switch —— 漏掉其中一处，表现是
「搜索搜不到」或「纸条指向一个不存在的页，整页空白」，都不会报错。现在结构、别名、`tabIds()`
是同一份数据，`settingsNavigation.test.ts` 守着三件事：页签不重名、「系统」只在最末、
**历史上出现过的页签 id 仍然认得**（旧版本把当前页存进了 localStorage，删 id 等于把回来的
人送到错误的页）。

**每页统一页头，今日时长搬去「历史」。** 顶部原来在**每一页**都重复显示聚合状态和今日各状态
时长 —— 后者是回顾数据，不该占每一页的一行。现在全局顶部只留聚合状态，今日时长进「历史」
页顶，页头负责回答「我在哪儿、这页能做什么」，主操作（全部已读、管理链接）放右侧。

**本机 Call Me 服务：应用内起一个只监听回环的 HTTP 服务。** 用户问过「为什么不能自己部署」。
答案是不能替用户决定部署到哪，但本机能做的部分可以做到位：`callme_local.rs` 直接复用
`server/` crate 的 `router()` / `Store` / 限流，用 `tokio::spawn` 起在 `127.0.0.1:43877`
（可改），应用退出即结束，不留孤儿进程；token 首次生成后存 `~/.signalhub/callme-local.json`
（0600），数据在 `~/.signalhub/callme-server/`。启动成功才把 url + token 写进设置 —— 端口
被占用时不能把一份连不上的配置落盘。

**为什么不是「一键部署到 VPS」。** 两条看似更省事的路都被否掉了：**检测并调用 Docker** 要求
用户机器上装了 Docker（多数人不装，装了也多半没启动），把一个「填地址」的问题换成一个
「装运行时」的问题；**让用户输入 SSH 密码 / 私钥由应用去远程执行** 则是在应用里长期保管主机
凭据，一旦有漏洞就是服务器被接管 —— 这种事不该由一个灯球应用来做。所以：本机跑服务，
公网仍走 `server/` 的独立部署（Docker / 二进制 + 反代），界面给一段可复制的命令和三条注意事项，
并**明确区分「本机测试地址」与「外部智能体可访问的地址」** —— 本机地址写进文章是收不到留言的，
这一点必须说在前面，否则「部署成功了但一条都没收到」会是最难自查的故障。

**配置页默认只剩一个开关。** 实测下来最劝退的不是「要部署」，而是一屏里同时摆着地址、
token、端口、检查间隔、测试按钮、部署命令 —— 可这个功能的日常动作只有「启动服务 →
新建链接」两步，其余都是低频例外。所以服务器子页把地址 / token / 端口 / 检查间隔收进一个
`<details>`，VPS 命令收进另一个；折叠用原生 `<details>` 的三角，不加圆角色块（沿用
`settings.css` 文件头那套）。启动成功后若还一条链接都没有，面板用刚生成的地址自动建第一条
并切回「链接」子页 —— 配置动作从「开服务 + 建链接」收敛成一次点击；已有链接时不重复建。
设置窗同时从 720×690 放大到 **1000×720**（下限 820×560，
见 §4.1）：重排之后每页多了页头和一层子页，宽一点才不用让高低频控件抢同一屏。多出来的
宽度全给正文，左栏仍是 140px。

### 3.29 折叠导航、图标与「吊销不等于删除」

**左栏默认折叠，只展开当前页那一组。** 0.6.0 重排之后左栏是 5 组 14 页 —— 分组解决了
「轴不一致」，但没有解决「一眼看过去还是十几行」。现在组标题变成可点的折叠开关（仍是
开关，**不是导航**：点它不跳页），`SettingsPanel` 里的 `expanded` 默认只含
`groupForTab(tab)` 那一组；切页时自动归位，手动展开过别的组也在下一次切页收回。不持久化
展开状态 —— 每次打开设置按当前页展开最自然，记一堆状态反而要用户自己收拾。两个容易漏的
细节：**搜索时强制全展开**（否则命中的页签藏在折叠里，搜索白做）；**折叠组的未读点提到
组标题上**（收起「工作台」不该把留言提醒一起收走）。`TAB_GROUP` 是归属的唯一真值，
`settingsNavigation.test.ts` 盯着「每页都登记了、组内归属一致」，加页签忘了写会测试失败。

**图标是纯数据，不参与选中态。** `lib/icons.ts` 存 16×16 的 path 名字表，`components/Icon.tsx`
只统一尺寸、`currentColor` 和 1.5 线宽。把数据放 lib 是为了让导航表也能引用 `IconName`，
不形成 lib → components 的反向依赖；`ICONS` 每个名字都必须有笔画由 vitest 盯住（漏配时
渲染出来是一枚空白 svg，不报错、不留痕，只能靠肉眼在真窗口里发现）。图标跟着所在按钮的
文字色走，于是 hover / 选中 / 禁用都不需要第二套配色 —— 这条正好接上 §3.16 里「选中态
只用浅灰底 + 字重」的纪律：**图标帮助扫读，不表达状态**，所以不做彩色、不做圆角色块、
不做 accent 竖线。次要动作（打开用法 / 吊销 / 删除 / 恢复）用统一的 `IconButton`，
最高频的「复制链接」仍是文字按钮。

**吊销与删除现在是两件事。** 原来只有 `revoke`：链接立刻失效，但那条记录永远留在列表里
占位，用户既改不了名字也清不掉。现在 `Store` 多了 `rename` / `delete` / `restore`：
- `delete` 把记录从 `sources.json` 移走，位置让出来（`MAX_SOURCES` 只数未吊销的），
  幂等；**不删留言** —— `messages.jsonl` 是 append-only，删来源不该顺手毁掉别人写的内容，
  客户端找不到名字时显示「已删除的链接」。
- `restore` 撤销误吊销，但受同一条上限约束，否则「吊销 → 恢复」能一直堆对外可写的入口。
- `rename` 清掉 `auto_label`，用户手改过的名字不再被第一条留言的标题覆盖。备注不给手工
  编辑入口：那是智能体通过 `context` 回填的东西。
- 界面上**有效链接才占位置**，吊销过的收进默认折叠的「已吊销 (n)」区，那里可以恢复或
  彻底删除；删除有二次确认。

三个新端点都是 `POST /v1/callme/sources/{id}/{rename,delete,restore}` 而不是 `DELETE` /
`PATCH`：桌面端只有一套 `http_post` 封装，且部分反代对 `DELETE` 的默认策略不一致；它们
语义上是命令而非资源 CRUD。`revoke` 保持原有 404 语义，旧客户端认这个。

### 3.30 Windows portable 版的系统通知身份（issue #25）

**症状**：macOS `.dmg` 装的版本通知正常；Windows 用 `_x64_portable.zip` 解压即用，
点「发一条测试通知」什么都不弹，界面上却写着「已允许」和「已发出」。

**根因不在通知代码，在 Windows 的应用身份。** `tauri-plugin-notification` 在非
dev 的 Windows 上把 toast 的 `app_id` 固定设成 `tauri.conf.json` 的 `identifier`
（`app.signalhub.desktop`）；`ToastNotificationManager::CreateToastNotifierWithId(id)`
要求这个 AppUserModelID 由**开始菜单里带 `System.AppUserModel.ID` 属性的快捷方式**
注册过，否则系统直接丢掉 toast。Tauri 的 NSIS 安装器会给它建的快捷方式盖章，所以
`-setup.exe` 能弹；portable zip 没有安装器，缺的正是这一步。

之所以「完全没报错」，是三层叠在一起：

1. 插件在 Windows 的 `permission_state()` **恒返回 Granted** —— Windows 没有 macOS
   那种 per-app 授权弹窗，这个值只说明「不存在需要申请的权限」。
2. 我们注册了通知动作按钮，插件因此走 `show_tracked` 后台线程，而那条路径是
   `let Ok(handle) = notification.show() else { return; }` —— **底层错误被吞掉**，
   `builder.show()` 照样返回 `Ok`。
3. GUI 子系统没有控制台，`alerts::show` 打的那行 stderr 等于没打。

于是 `src-tauri/src/win_toast.rs` 在 `setup` 里、第一条通知之前补上这套身份：
`SetCurrentProcessExplicitAppUserModelID`、写 `HKCU\Software\Classes\AppUserModelId\
<identifier>` 的 `DisplayName` / `IconUri` / `IconBackgroundColor`（决定通知来源的名字与
图标），再用 COM 的 `IShellLinkW` + `IPropertyStore` 在 `%APPDATA%\Microsoft\Windows\
Start Menu\Programs\SignalHub.lnk` 写入 `System.AppUserModel.ID`，最后 `SHChangeNotify
(SHCNE_ASSOCCHANGED)` 让 shell 立刻认到。

几个刻意的选择：

- **只写注册表不够。** 微软 `WindowsAppSDK#6821` 里「注册成功、权限 Enabled、就是没有
  横幅」正是这种情形，决定性的因素是快捷方式上的属性。上游
  `tauri-winrt-notification/examples/unpackaged_app.rs` 那份只写注册表的示例不能当
  通用解。
- **`IconUri` 必须指向图片文件，不能指向 exe。** 0.6.2 那一版把它填成了 exe 路径，
  结果通知照常弹、来源那一栏却只有名字没有图标 —— Windows 只认 png / jpg，给 exe
  等于没给。现在 `icons/128x128.png` 用 `include_bytes!` 带进二进制，注册时落到
  `~/.signalhub/toast-icon.png`，注册表里写的是那个文件的路径。选内嵌而不是
  `bundle.resources`：portable 的 zip 只有一个 exe，解压到哪都没有「资源目录」这回事，
  内嵌到哪都能解出同一张图。`Microsoft.Toolkit.Uwp.Notifications` 对 unpackaged 应用
  也是这个做法（把图标解成 `Icon.png` 再写路径）。
- **不用 PowerShell 的 AUMID 兜底。** 那条路能弹，但通知来源会写成「Windows
  PowerShell」，插件的动作按钮 / 点击回调也全都不走我们这套了。宁可花一次启动把
  身份注册对。
- **COM 放在单独的 STA 线程。** Tauri 主线程可能已经用 MTA 初始化过 COM，在那里再
  `CoInitializeEx(STA)` 会拿到 `RPC_E_CHANGED_MODE`。
- **幂等判据是「上次记的 exe 路径」而不是「快捷方式存在吗」。** `~/.signalhub/
  toast-shortcut.txt` 存着路径；portable 目录被搬走、快捷方式被删、注册表键被清、
  图标文件被清，任一种都会触发重建。写成功了才记标记，中途失败下次启动自动重试。
  **标记里带格式版本**（`MARKER_VERSION`）：0.6.2 写的是裸路径，只改 `IconUri` 的取值
  对老用户无效（标记命中就直接返回），所以格式一变就让旧标记失配、强制重注册一次。
- **和 NSIS 用同一个快捷方式路径**（没配 `startMenuFolder` 时就是
  `$SMPROGRAMS\<productName>.lnk`），安装版不会被多塞一个重复的开始菜单项。

代价要说清楚：portable 版首次启动会写一个 `HKCU` 键 + 一个当前用户的开始菜单项。
仍然不需要安装器、不需要管理员、不写 Program Files。凡是写着「不写注册表、不建
快捷方式」的文档/注释都得跟着改，别留失效的真值。

**失败要可见。** 注册失败只记进 `ToastBackend`，不阻断启动；`get_notify_permission`
在这种情况返回 `unavailable`（界面显示「未注册」而不是假的「已允许」），旁边给
「重新注册」按钮，具体错误原样显示并进一键诊断报告。测试通知的结果文案也不再说
「已发出」—— 应用只能确认把通知交给了系统，看不到系统是否真的显示了它（上面第
2 条决定了这一点在本项目里无法从返回值判断）。

真机验收（Windows 10/11）见 issue #25 的清单：快捷方式属性、测试通知、真实告警的
动作按钮、搬动 portable 目录、NSIS 安装版不重复、写入被策略拦截时的提示。

修复随 **v0.6.1** 发布；0.6.0 的 portable 包不含它，那个版本的用户要么改用
`-setup.exe`，要么直接换 0.6.1 的 zip。issue #25 在上面这份真机清单跑完之前保持
OPEN —— CI 的 windows-latest 只证明这段代码编得过，不证明 Toast 真的弹了。

### 3.31 设置窗口的手动亮 / 深色主题（2026-11-10）

**原本就有一套。** `theme.css` 定义 8 个变量（bg / fg / muted / line / hover /
accent / danger / danger-line），靠 `@media (prefers-color-scheme: dark)` 整套换值；
`settings.css` 2273 行里 177 处 `var(--…)`，只剩 5 个硬编码颜色（开关旋钮的白、
两个状态色兜底、警告黄的深浅两值）。所以这次不是「补一套深色」，而是把一个
**只能跟随系统**的机制改成「跟随系统 / 强制亮 / 强制深」三选一。

**边界先划清。** 灯球和收件箱是透明窗口上的固定深色 HUD，`theme.css` 和
`inbox.css` 的文件头都写了「刻意不用这套变量」；只有设置窗和演示页是普通页面，
跟着主题走。设置界面里那行 hint 不是凑字数的：不写清楚，用户切了开关发现灯没
变色只会以为开关坏了。状态色 `--state` 来自 TS 的 palette（`state.css`），也与
主题无关。

**偏好照 `Locale` 抄。** Rust `config.rs` 加 `Theme { Auto, Light, Dark }`，
`Settings` 带容器级 `#[serde(default)]` —— 旧配置缺字段读成 Auto，升级不改观感，
单测锁住三种值的线上名字与缺字段回退。Rust **只存偏好、不解析系统外观**：它连
`prefers-color-scheme` 都看不到，这和 `Locale::Auto` 由前端 `navigator.language`
解析完全同构。前端 `lib/theme.ts` 的 `resolveTheme(mode, systemDark)` 是唯一一份
语义。

**CSS 只读结果。** 深色块从 `@media` 改成 `:root[data-theme="dark"]`，
`settings.css` 那枚警告黄也跟着换选择器。理由不是写法好看：若 CSS 保留媒体查询、
JS 又写一个强制值，两条路会各自得出答案（系统深色 + 用户强制亮色时必然打架），
那就是两处真值。

**两个时序坑，都是这轮才发现的。**

1. **首屏闪白。** 生产构建把 CSS 提成 `<head>` 里的 `<link>`，浏览器在 module
   script / React 挂载之前就应用了。改成 JS 驱动之后，等 `useTheme` 的 effect 再
   设 `data-theme` 已经晚了。`index.html` 里放一段**同步内联脚本**（不是 module，
   必须在 CSS 之前执行），读 `localStorage` 里的解析结果缓存
   (`signalhub-theme-resolved`)，第一帧就定好外观。缓存不是第二份配置，
   `theme.test.ts` 有一条测试锁住「HTML 里的 key 和 TS 常量一致」。
2. **React 首屏只有 DEFAULTS。** `useSettings()` 的初始值是 `DEFAULTS`
   (`theme: auto`)，IPC 回来之前拿它去 `applyTheme` 会用系统外观盖掉首屏按缓存
   设好的深色 —— 强制深色的用户照样白一帧。所以新增 `useSettingsState()` 带上
   `loaded`，`useTheme(mode, ready)` 在 `get_settings` 回来前什么都不做。浏览器
   里的 demo 页没有 IPC，`loaded` 一开始就是 true。

**`color-scheme` 单独收窄。** 原来挂在全局 `:root` 上。若把它写进
`:root[data-theme="dark"]`，特异性 (0,2,0) 会压过 `inbox.css` 的
`html[data-window="inbox"]` (0,1,1)，把收件箱的原生控件一起带亮。现在全局兜底
仍是 light，深色只给 `html[data-window="settings"][data-theme="dark"]` 和
`html[data-window="demo"][data-theme="dark"]`。

**没做的**：灯球 / 收件箱的主题化（那等于重做两套 HUD 配色并在透明窗口上验
可读性）；主题不推给 Rust（Rust 不需要知道）；`prefers-reduced-motion` 与主题
无关，保持原样。真窗口的亮 / 深观感要在 `tauri dev` 里切系统外观验收，Agent
环境看不了。

### 3.32 通知也能挑状态了（2026-11-10）

**原来写死三个。** `alerts::is_urgent()` 只认 `permission / attention / error`，
其余状态一到 `Gate::observe` 就直接 `None`。而「转发」那边 `Hook.when` 早就是
一张可选状态表 —— 所以「提醒」页现在也有一排同样的 chip，存进
`Settings.notify_when`。

**默认值不能是「空 = 全部」。** `hooks[].when` 的空表示「不过滤」，照搬到通知
上等于给每个状态都弹 —— 从旧版本升级上来的用户会突然在每次 `working` / `done`
时被弹一下，而他们什么都没改。所以 `notify_when` 用
`#[serde(default = "default_notify_when")]` 明确落成那三个，**空数组 = 一条都
不弹**。两种语义的差异在字段注释、`i18n` 的 hint 和前端类型注释里各写了一遍：
这三处都在回答同一个容易搞混的问题。

**候选里没有 `offline` / `off`。** 它们不代表「发生了什么」：`offline` 是「一个
组都没有 / 全被静音」时的兜底值，`off` 是「用户自己按了暂停」。勾上只会得到
「你暂停时提醒你暂停了」这种噪音。`stale` 留着 —— 一个会话沉默到快消失，确实
值得知道。Rust `config::NOTIFY_STATES` 与前端 `types.ts` 的 `NOTIFY_STATES`
（由 `SIGNALS` 过滤得来）是同一份集合，两边各有测试钉住「默认值必须可选」。

**闸门只多一个入参。** `Gate::observe` 加了 `wanted: bool`，位置在 `quiet` 之后：

- 它只决定**第一次要不要弹**，`alerting` / `episode` 照旧推进。这样「用户刚把
  某个状态勾上」在下一帧就生效：状态没变，但 `notified` 还是 false（`turning_
  a_state_on_takes_effect_on_the_very_next_push` 钉住这条）。
- 延迟分支（阈值到点后）**现读** `live.notify_wants(alerting)`：等待期间用户可能
  把它取消勾选了，和静音、提示音同一条规矩。
- `is_urgent` 收窄成「只有它决定重复提醒」：提醒说的是「还卡着、已经等了 20 分
  钟」，给 `done` / `idle` / `stale` 排这样一条是胡说。第一次要不要弹由用户的
  列表决定，`spawn_reminders` 因此只对那三个状态开工。

**写坏的配置有两层兜底。** `clamped()` 丢掉认不出来的名字（去空白、统一小写、
去重）；**全丢光时退回默认** —— 留成空表的表现是「通知开着、权限也给了，但永远
不弹」，界面上没有任何线索指向这里。但**显式写 `[]` 是用户的真实意图**，不能被
兜底顶掉，两者靠 `had_states` 区分。`validate_settings` 另有一层：名字不可用时
直接报错并列出可用项（只在导入手改过的配置时才会走到）。

**没做的**：组过滤（`Hook.groups` 那一维）。通知现在看的是**全局聚合**，也就是
最紧急的那一路 —— 两组并行时「ci 完成」会被「work 在执行」盖住。要做的话得连同
`Gate` 的「一次一个 episode」一起改，不是加个字段的事。

### 3.33 牌面的「质感」五档（2026-11-10）

**问题不是旋钮太少，是缺一层「风格」。** 加这一层之前，外观页已经有十来个可调项
（尺寸预设、形态、大小、形状、配色、不透明度、长宽倍率、节奏、灵动、显示字段、
逐状态覆盖），但决定「气质」的四样在 `lamp.css` 里是硬编码：`border-radius:
calc(size * 0.32)`、`border: 1px solid rgba(255,255,255,.14)`、`--sign-rgb: 28,28,32`、
`font-size: calc(size * 0.5)`。所以用户能调「多宽、多透、显示几行」，调不出「另一种
感觉」。微调再多，缺风格层也还是那个印象。

**这五项之所以能安全地做，是因为它们都不参与窗口几何。** 牌宽高只由 `size`、
两个倍率和「有没有消息」决定（`config.rs` 的 `sign_width` / `sign_height`），
圆角、描边、底色、字号、分层全都只改绘制。因此这一层**没有**「改一处必须同步另一处」
那条老约束 —— 这也是当初把它们从「尺寸」那一类里分出来单做的原因。

**用 `data-sign-*` 属性而不是内联 CSS 变量。** 每档对应 CSS 里一条规则，倍数只在
`lamp.css` 一处；换成变量的话 TS 就得拼 `calc()` 或者直接吐像素值，像素值就有了
两个出处。属性名和档位值与 `config.rs` 的同名枚举、`useSettings.ts` 的联合类型
一一对应 —— **三处必须同名**，对不上的表现是「点了没反应」，没有任何报错。

| 属性 | 档位 | 落点 |
|---|---|---|
| `data-sign-radius` | square / soft / **standard** / round | `--sign-radius`（× size） |
| `data-sign-border` | none / **hairline** / strong | `--sign-border-w` / `--sign-border-c` |
| `data-sign-tint` | **graphite** / black / warm / slate | `--sign-rgb` |
| `data-sign-text` | compact / **standard** / large | `--sign-text`（× 字号） |
| `data-sign-emphasis` | **auto** / flat | 覆盖 `data-tone` 那三条压淡规则 |

加粗的是默认档，默认档**在 CSS 里不写规则** —— 否则 `lamp.css` 的兜底值就和
`config.rs` 的 `#[default]` 争同一件事。`lampStyle.ts` 有自己的单测（`presets.test.ts`
里那组），而「CSS 漏一条规则」当时没有测试兜着 —— 后来补了 `src/styles/css.test.ts`
（见 §3.35 末尾），但它只认几条「删了就一定是事故」的规则，逐档覆盖仍然靠上表和对齐注释。

**字号是一个整体乘数（0.9 / 1 / 1.12），不是某一处字号。** 组名、状态词、消息、
时长、`+N` 一起缩放 —— 只放大其中一项会得到「组名比状态词大得离谱」的牌。上限
压在 1.12：牌宽固定 `size × 7`，字再大只会让省略号更早出现，换不来更多信息。

**分层开关有双重作用。** `data-tone` 那套压淡（calm 的牌底 ×0.72、组名降到 400、
灯珠 0.55×）本来在界面上没有任何解释，用户看到某块牌比别的淡，第一反应是「是不是
坏了」。`sign_emphasis` 既是「有人就想要所有牌一样重」的个性化，也是一种说明：
关掉它就能看出差异来自这里。实现上把灯珠点径抽成 `--dot-scale`，关掉时只需把
need 的 0.72 归回 0.55，不必把两个像素式子各写一遍。

**预设只接管圆角 / 描边 / 字号，不碰底色和分层。** 圆角、描边、字号只是形态，
不承载含义；底色要和桌面协调（换预设时突变很突兀），分层是「谁在叫我」的语义
机制。这和既有的「预设不含形状和配色」是同一条理由，`presets.test.ts` 用
`not.toHaveProperty` 钉住。

**刻意不做毛玻璃。** 透明窗口里 `backdrop-filter` 只能模糊 webview 自己的内容，
糊不到桌面 —— 做出来是个假的。同理不加渐变和外发光：这套样式从头到尾是扁平的，
`lamp.css` 头注释和 `settings.css` 都写着这条。

**几何红线没动**：窗口尺寸仍由 `config.rs` 与 `lamp.css` 那两处共享的值算，
这一层连一个像素的宽高都不影响。

### 3.34 不再给低透明度的字描边：改成滑杆下限（2026-11-10）

**撤掉的是一个「补丁」，不是一项功能。** 0.4.4 起，牌面不透明度拉到 50% 以下时
会给牌里的字加一圈四向深色 `text-shadow`（`[data-sign-translucent]`），理由是浅字
落在桌面上会看不见。它确实让字读得出来，但读起来像**空心字**：笔画被边吃掉、小字号
糊成一坨、近白字心配黑边在 2× 屏上尤其脏。用户的原话是「特别丑，观感也不好」——
这类问题调不了参数，只能不进入那个状态。

**第一版的下限 50 抬到了 65，因为 50 仍然看不清。** 50 是按「α = 0.5 是牌面还托得住浅字的临界」推的，但那只考虑了**组名**（近白、加粗）。用户接着报「低透明度下提示字体的颜色是灰色，在浅色程序上根本看不清」——指的正是状态词 / 消息 / 时长这些 `#9b9ba3` 的次要文字。把同一块牌按 50/60/65/70/78/86 排一列、铺在近白窗口（`#fbfbfc`）和浅灰壁纸（`#cfd3da`）上对照：50% 时牌面在白底上合成 `#8b8b8d`，`#9b9ba3` 的对比只有 **1.1:1**，那是消失而不是淡；60% 好转但余量太小；65% 约 3:1，才真的读得住。于是下限定 65。

**同时把次要文字提亮：`#9b9ba3` → `#c2c2cb`。** 这是第二个病因 —— 就算牌面满不透明，`#9b9ba3` 在浅底上也只有 3.9:1，同样偏弱。只抬下限不动字色，等于让灰字配一块更深的灰底。提亮后与组名（`#ececef` + 600 字重）仍差 35 级灰度，层次靠字重和字号继续表达，不必靠压暗字色。

两处同名声明：`config::MIN_SIGN_OPACITY`（`Settings::clamped()` 夹住手改的
config.json 和旧版本存下的 0–64，读一次设置就被抬上来）与
`src/lib/lampStyle.ts::SIGN_OPACITY_MIN`（滑杆的 `min`）。**旧配置里的低值算迁移，
不算数据损坏** —— 表现是升级后灯变清楚了一点。

**更隐形的需求另有出口：安静模式。** 没事时整盏压到 `opacity: 0.15`，那条路上
本来就不指望你读字。两条路分工清楚：滑杆管「看得见」，安静管「别打扰」。也正因为
如此，安静压暗不再触发任何换字逻辑 —— 压暗了还描一圈边，反而比不描更扎眼。

**calm 档的压淡顺手补了个托底。** 分层要乘 0.72（见 §3.4），而 `0.65 × 0.72 = 0.468`
又跌破可读线 —— 「多组 + 低透明度」恰恰是最常撞上、也最难看的组合。现在压淡取
`max(α × 0.72, 0.6)`，低端时层次差被压缩（0.65 vs 0.6，主要靠点径和字重区分），
换来两块牌都还读得出字。**托底必须低于下限**：一度图省事写成 `= 下限 / 100`，
下限抬到 65 之后托底 0.65 就高过了默认档的乘积 0.619 —— 反而把最常见那档的 calm
拉实、分层在默认设置下消失。两个数一个是「乘积的下界」、一个是「滑块的下界」，
不是同一件事。
**乘数搬到了 JS**（`CALM_ALPHA_FACTOR` / `CALM_ALPHA_FLOOR` → `--sign-alpha-calm`）：
不把 `max()` 写进 CSS 的 alpha 位，是因为赌输的表现是整条 `background` 失效、牌底
直接透明 —— 比原来难看十倍，而这个数值得有单测。

**删掉的东西**（别在旧分支里找回它们）：`lamp.css` 的
`.lamp-root[data-sign-translucent]` 两段与 `.approval` 那条覆盖（气泡本来就是实底
深色，不需要钉颜色）、`lampStyle.ts` 的 `SIGN_TRANSLUCENT_BELOW` /
`QUIET_FADE_OPACITY` / `signTextNeedsContrast` / `isQuietDimmed`，以及 `SignalLamp` /
`SettingsPanel` 上的 `data-sign-translucent`。设置页那句 hint 从「会加描边」改成
解释下限（「再淡字就落在桌面上，更隐形请用安静模式」）。

### 3.35 边灯与角灯：不写字也表达更多（2026-11-12）

**这一层是为「装不下」做的，不是为「好看」。** 到 0.6.2，一块牌上最多能出现五段内容
（圆点、组名、状态、已持续、消息），而牌宽固定 `size × 7`、还有一条消息行占着第二行 ——
再加任何一段，代价都是把别的挤成省略号。用户的诉求很具体：想要更多信息，但**不要再
多写字**。于是新开两条通道，都是「用形状和面积说事」：

| 通道 | 配置 | 说什么 |
|---|---|---|
| 边灯 `SignEdge` | off / top / frame / glow | 把状态色铺到牌的轮廓上，离得远也看得见 |
| 角灯 `SignCorners`（四角独立） | empty / state / pinned / muted / stale | 四个独立的是 / 否位 |

**两者都绝不参与窗口几何**，这是能加它们的前提。边灯全在 `.sign::before` 这个绝对定位的
伪元素上（`top` 是一道 1.5px 的亮线加一小截余晖，`frame` / `glow` 是 1px 的 `border` 加
可选外发光），角灯是绝对定位的 `.sign-corner` 子元素 —— 都不是 flex 行里的项。
牌宽高仍只由 `config.rs::sign_width` / `sign_height` 和 `lamp.css` 那两处共享值算。
这和 §3.33 的质感五档是同一条判断：**不碰盒子的才能随便加。**

**「不亮 = 根本不画」，不是画一个暗点。** `lib/lampStyle.ts::cornerLights()` 是个纯函数，
条件不成立的角**根本不返回**，DOM 里也就没有那个元素。这条不是优化，是诚实：一排四个暗点
会让用户以为「这四个位置本来就有东西，只是没亮」，而实际上它们是空的 —— 于是永远不会
去设置里找。判据（`CornerFacts`）三样：`pinned`（`group_meta[组].order != null`）、
`muted`（`muted_groups` 里有这个名字）、`staleProgress`（`stale` 状态那段宽限期的剩余
比例）。只有 `state` 是无条件亮的，它回答「这块牌有状态」本身。

**`--progress` 提到 `.sign` 上了。** 角灯里那个 `stale`（将过期）要画「还剩多少」，
而它和灯珠外那圈细环**必须是同一个数** —— 两处各算一遍的话，细环走完了角灯还没灭，
或者反过来。所以 `progressStyle(group)` 从灯珠挪到牌上，两边都从 `var(--progress)` 取。
`stale` 角灯的 `opacity` 是 `calc(0.2 + 0.7 * var(--progress, 1))`，兜底 1 是因为
`--progress` 只在 `stale` 时才有值，其余状态必须按「满」算，否则角灯会是隐形的。

**顶边那档返工过一次。** 第一版是 `linear-gradient(transparent 62%)` 加 `opacity: 0.42`，
在 22 和 32 两档截图里都像「整块牌变绿了」—— 面积一大，颜色就成了底色而不是提示。
改成 `inset 0 1.5px 0` 的一道亮线 + 到 `size * 0.5` 就透明的短余晖、`opacity: 0.6` 之后
才读成「这条边在发光」。**教训是同类元素的观感只能靠对着真尺寸截图比，不能靠推。**

**角灯的常量在 `.lamp-root` 上，不在每个角上。** `--corner-d`（直径 `size * 0.16`）与
`--corner-inset`（内缩 `size * 0.24`）各一处。0.24 这个数是被**最大圆角**定的：圆角上限
`size * 0.72`，内缩再小角灯就会被裁掉一半 —— 在 16 / 22 / 32 三档、四种圆角、三种桌面底
色下逐一截图核过。

**配置默认全关（`SignEdge::Off` + 四角全 `Empty`）。** 这条是红线：升级后灯不该自己长出
新东西。`SignCorners` 自己带 `#[serde(default)]`，所以手改 `config.json` 只写
`{"br": "muted"}` 也能解析（缺的角退回空），有单测钉着。

**设置页里角灯是折叠的。** 四个下拉摊开要占四行，而绝大多数人不会动它 —— 收起时那行
摘要写「未启用」/「已设 N 个角」，展开才出四个 `select`。用的是既有的 `.disclosure`，
和逐状态覆盖那张表同一套件。

**预览里角灯的判据全给真**（`pinned: true, muted: true, staleProgress: 1`）。预览的职责是
让用户看清「我配的这个角长什么样」，条件按住不成立的话，用户配了 `pinned` 却在预览里
看不见，只会以为没生效。

**撤掉的旧东西**（别在旧分支里找回）：`SignalLamp` 的就地改名（输入框 + `✎` 按钮）、
`lamp.css` 的 `.sign-rename` 及其 `::placeholder`、`i18n.ts` 的 `renameHint`、
`.sign-name` 上的 `cursor: pointer`。改名入口现在只有设置页一处，右键菜单的「重命名…」
只是把设置窗翻到那一页（见 §3.7 第 6 条）。

**顺手补的一道防线：`src/styles/css.test.ts`。** 做这一层的时候我把 `lamp.css` 一段注释的
`*/` 删掉了，于是 `.sign-state` / `.sign-message` / `.sign-age` 三条规则整段被吞进注释 ——
`npm run build` 通过、`npm test` 全绿，只有截图里状态词竖排、消息折两行。这类故障没有任何
现有测试能兜住，所以新增了这个文件：用 `?raw` 读五个样式表，断言注释开闭配平、以及
`lamp.css` 里几条「删了就一定是事故」的规则还在（`white-space: nowrap`、`.sign-corner`、
`[data-sign-edge="frame"]`、`overflow: hidden`）。**`?raw` 要在 `vite.config.ts` 的 `test`
段开 `css: true`** —— 否则 Vite 的 CSS 插件先把它处理掉，导入拿到的是空串，测试会以
「找不到这条规则」的形式误报（我在这上面浪费了一轮排查）。

## 4. 悬浮窗实现

### 4.1 窗口配置

Tauri 2 的配置键是 lowerCamelCase，注意 `skipTaskbar` 的 `b` 是小写（历史遗留）。

```json
{
  "label": "main",
  "url": "index.html?window=light",
  "width": 42, "height": 42,
  "resizable": false,
  "decorations": false,
  "transparent": true,
  "alwaysOnTop": true,
  "skipTaskbar": true,
  "shadow": false,
  "focus": false,
  "visible": false,
  "maximizable": false, "minimizable": false, "closable": false
}
```

- `width`/`height` 只是初值：真实尺寸由设置决定（圆点直径 + 20px 边距），启动时和每次改设置都会由 Rust 侧重设一遍。
- **`transparent: true` 在 Tauri 2.12.1+ 不再需要 `macos-private-api` feature**（旧 2.x 需要）。用 `cargo tree -p tauri` 确认版本。
- **`visible: false` + setup 里先套用设置再 `show()`**：否则会先按配置里的默认尺寸闪一下再跳到设置里的尺寸。
- **`closable: false` + `decorations: false` + `skipTaskbar` + Accessory 激活策略 = 用户没有任何办法退出应用。** 必须提供一个退出入口，见 §4.4。

**第二个窗口：设置面板。** 同一个 Vite 应用、同一份 bundle，靠查询参数分流，比配 Vite MPA 多入口简单得多：

```json
{
  "label": "settings",
  "url": "index.html?window=settings",
  "width": 1000, "height": 720,
  "resizable": true, "minWidth": 820, "minHeight": 560,
  "center": true,
  "visible": false,
  "maximizable": false
}
```

三个非显然的点：

1. **默认 1000×720，可由用户拖大，内容自己滚。** 默认宽度 1000 = 左栏 140 + 间距 16 + 内容区 804 + 左右内边距 40；内容区用 flex 填满余下的空间（见 §3.16），窗口拉大后右栏自然变宽，会话多了仍在内容区里滚，不会把窗口撑高。下限 820×560 是照着「左栏 + 逐状态表还能读」量的。改布局后要在浏览器里量一次再定默认值——把视口固定成 1000×720 再量，才能避开移动端视口模拟的干扰。**0.6.0 从 720×690 放大到 1000×720**：信息架构重排之后每页多了页头和一层子页，窄窗里高频与低频控件得抢同一屏；多出来的宽度全给正文，左栏仍是 140px。**灯窗不能顺手也开 `resizable`**：它的尺寸是 Rust 和 CSS 两处真值按内容算出来的，让用户拖会把牌裁掉。
2. **关闭时只隐藏、不销毁**（`WindowEvent::CloseRequested` + `api.prevent_close()`），这样重开是瞬时的。
3. **Accessory 策略下窗口不会主动到前台**，所以打开设置时临时切回 `ActivationPolicy::Regular`，关闭时切回 `Accessory`。副作用是设置打开期间应用会出现在 Dock 里——这反而是对的，用户正在和它交互。
4. **两个窗口都不是透明的**，但 `lamp.css` 里有一份全局的 `html, body { background: transparent }`（灯球窗口需要）。设置面板靠 `html[data-window="settings"]` 属性选择器压过它，这样覆盖关系是确定性的、不依赖两个 CSS 文件的打包顺序。`main.tsx` 负责把 `data-window` 写到 `<html>` 上。

### 4.2 setup：置顶与 Dock 隐藏

```rust
#[cfg(target_os = "macos")]
app.set_activation_policy(tauri::ActivationPolicy::Accessory);  // 不在 Dock / Cmd-Tab 出现

let win = app.get_webview_window("main").unwrap();   // 需要 use tauri::Manager;
win.set_visible_on_all_workspaces(true)?;            // 所有桌面空间可见
win.set_always_on_top(true)?;
win.show()?;
```

`skipTaskbar` 在 macOS 无效，隐藏 Dock 图标必须用 `ActivationPolicy::Accessory`。

### 4.2.1 崩了会留记录：`panic = "abort"` 与 panic hook

release 打开 `panic = "abort"`（见 `Cargo.toml`），进程直接消失。**这对这个应用是很危险的一条**：灯球没有 Dock 图标、没有窗口，Accessory 策略下连个能报错的地方都没有 —— 用户看到的只是圆点不见了，而「灯自己退了」和「我没注意到」在他那儿分不出来。

所以 `run()` 的第一件事是 `install_panic_hook()`：把 panic 信息和位置写进 `~/.signalhub/hooks.log`，同时打一份到 stderr。`panic = "abort"` 下 hook **照样会跑**（跑完才 abort），所以来得及落盘。

**为什么不干脆去掉 `abort`**：一来那 55 处 `.expect("... poisoned")` 全靠它成立（不展开栈 ⇒ 锁永不中毒，那些分支构造上不可达；改成 unwind 它们会变成活的，而且真走到那一步只会连环 panic，比直接退出更难查）；二来 wry / tao 会从 Objective-C 回调里调回 Rust，让 panic 展开着穿过 C 帧是 UB。这两条都比「一个已经出了错、状态未知的进程继续跑」更值得保住。

hook 里**绝不能再 panic**（双 panic 直接 abort，什么都来不及记），所以全程 `let _ =` / `unwrap_or_else`。

### 4.3 拖拽

`data-tauri-drag-region` 在 v2 仍然有效，并新增了 `"deep"` 值——让任意后代元素的点击也能拖动。因为灯球会盖满整个窗口，必须用 `"deep"`：

```html
<div class="root" data-tauri-drag-region="deep">
  <div class="lamp" />
</div>
```

Tauri 只响应鼠标**主键**的按下事件，所以右键可以正常穿透到 `contextmenu`。`A / BUTTON / INPUT / SELECT / TEXTAREA / LABEL / SUMMARY` 会阻止拖拽——自定义右键菜单时不要用这些标签。备选方案是 JS 调 `appWindow.startDragging()`（需要 `core:window:allow-start-dragging` 权限）。

### 4.4 点击穿透：必须警惕的坑

`set_ignore_cursor_events(true)` 让**整个窗口**忽略指针事件——包括拖拽和右键。一旦开启穿透，鼠标就无法再操作它。

**铁律：永远不要在全局快捷键注册成功之前开启穿透。** 逃生通道顺序必须是：注册快捷键 → 提供托盘菜单项 → 才允许切到穿透模式。UI 上切换时也应提示用户按什么键退出。

因为核心诉求是「可拖拽」，v1 **默认不开穿透**，仅作为托盘菜单/快捷键的可选模式。

**退出入口（v1 必需）**：因为窗口无边框、不可关闭且不在任务栏显示，灯球右键菜单必须提供「退出」，走一个自定义 Tauri command（自定义命令不需要额外 capability）：

```rust
#[tauri::command]
fn quit(app: tauri::AppHandle) { app.exit(0); }
```

### 4.5 动画方案选型

| 方案 | 评价 |
|---|---|
| **CSS keyframes（采用）** | GPU 合成，只动 `opacity`/`transform`，零 JS 开销；换状态只改一个属性；天然支持 `prefers-reduced-motion` |
| Canvas / WebGL | 浮窗只有几十像素，过度设计 |
| 帧序列图 / Lottie | 视觉最好，但 v1 成本过高 |

实现方式是把状态映射成根元素的 `data-state`，配色集中在 `styles/state.css` 一份 `[data-state] { --state: … }` 里（灯球和设置面板的会话小圆点共用），动画则按状态挂在 `.lamp` 上。切换状态 = 改一个 DOM 属性。

```
[data-state="working"]  .lamp { animation: pulse 1600ms ease-in-out infinite; }
[data-state="error"]    .lamp { animation: pulse 340ms steps(2, end) infinite; }
```

`error` 用 `steps()` 硬切做出频闪感，与 `permission` 的平滑闪烁区分开——两者颜色相同，节奏是唯一的区分手段。

`error` 用 `steps()` 硬切做出频闪感，与 `permission` 的平滑闪烁区分开。

无障碍：`@media (prefers-reduced-motion: reduce)` 下禁用所有动画，降级为常亮色块。

**`hooks.rs` 和 `outbound.rs` 名字里都有 hook，但方向相反：** 前者是**入站**（把 SignalHub 的 hook 装进智能体的配置文件，让它们能上报进来），后者是**出站**（状态变化时 SignalHub 主动往外 POST 或执行命令）。两个文件顶部都写了这句区分。

**关于 `hooks.rs` 为什么不是 `integration/{claude_code,codex,cursor}.rs`：** 原计划按智能体拆三个文件，实际写下来发现三者的差异只在「配置路径 + 事件名清单 + handler 形状」这张表里，而**安装逻辑（保留无关键、幂等、备份、解析失败中止、精确摘除自己的 handler）各家完全一样且是最需要谨慎的部分**。拆成多个文件会把这段逻辑抄好几遍，或者抽出一层反而更绕。所以是一个 `hooks.rs`，内部用一个小 `Agent` 枚举和一张事件表区分差异。

这个判断后来被验证了两次：**加 Gemini CLI 和 Goose 各只花了不到一小时**，而且改的确实是那张表 —— 唯一的例外是 Goose，它走插件目录而不是共享配置，安装/卸载各多了一步（写清单、删目录），那也只在 `install`/`uninstall` 两个入口里各加了十来行，`install_at` 那条共用的核心逻辑一行没动。

**Pi Agent 不走这条路，因为它没有能写 hook 的配置文件**（只有命令行上报）。这是那张表装不下的一类，所以它**不进 `Agent` 枚举、也没有 `install`/`uninstall`**：接了也没地方写。它的接入方式就是「在自己的脚本里调一次 `signalhub`」，所以界面上给的是一条可抄的命令而不是一个按钮 —— 「接入」页专门有一节放它。

这一节单独列出来、而不是混进上面那个列表，是因为上面每一行都有「接入 / 卸载」按钮：把一个没有按钮的条目混进去，用户会以为按钮没渲染出来。**同一个列表里的条目形状必须一致**，不一致的东西该另起一节 —— 这比「少一节标题」重要。

顺带一提，这也说明「支持一个智能体」有两种含义：**能自动接线的**（有配置文件可写）和**只能命令行上报的**（要用户自己接线）。前者是一条 `match` 分支，后者只需要文档和一条能抄的命令 —— 后者不该被硬塞进前者的形状里。

**关于两个二进制。** 这个包里有两个 bin：app（`signalhub-app`，源自 `src/main.rs`）和 CLI（`signalhub`，源自 `src/bin/signalhub.rs`）。两者同名会冲突，而 app 的名字用户看不到（通过 .app 启动），CLI 的名字却要写进智能体的 hook 配置里，所以让给 CLI。`[package] default-run = "signalhub-app"` 让 `cargo run`（也就是 `tauri dev`）选 app 那个，`tauri.conf.json` 的 `mainBinaryName` 同步设为 `signalhub-app`。

**Cargo 包名不叫 `signalhub`，叫 `signalhub-desktop`。** 纯粹是为了绕开一条 Tauri 的限制：sidecar 不允许和包同名（「Cannot define a sidecar with the same name as the Cargo package name」）。包名本身没有被任何二进制用上 —— 两个 bin 都是显式命名的，`[lib] name = "signalhub_lib"` 也是显式的。

**CLI 是作为 sidecar 打进应用包的**（`bundle.externalBin`）。这不是锦上添花：装了 `.dmg` 的用户手上没有 `signalhub` 这个命令，而「接入」页一键接入写进智能体配置的恰恰是 `signalhub hook <agent>`。不把它一起装进去，那条命令就是个跑不起来的东西 —— 而且是静默的。`resolve_hook_command` 因此按「PATH 上的裸名字 → 与主二进制同目录的那个 → 裸名字兜底」三级找它，**绝不能用 `current_exe()` 兜底**（原来就是那么写的）：那是 GUI 二进制，它不认 `hook` 参数，而单实例插件会把它变成「把已经开着的窗口叫到前面」，不报状态也不报错。

**这条 sidecar 给 `cargo` 加了一个前置步骤，值得知道。** `tauri-build` 在**构建脚本阶段**就校验 `externalBin` 里的文件在不在，所以 `cargo test` 之前必须先 `npm run stage-cli`（`scripts/stage-cli.mjs`）—— 哪怕测试根本不碰那个文件。脚本内部还有一层蛋生鸡：编译这个包里的任何东西（包括 CLI 自己）都会跑 `build.rs`，于是「编译那个文件」的命令本身要求那个文件已经存在；解法是给那一次 cargo 调用设 `TAURI_CONFIG` 把 `externalBin` 临时置空。`tauri dev` / `tauri build` 会自己先跑这一步，只有直接调 `cargo` 时才需要手动补。

**关于 `notify.rs`：** 状态变化的通知出口被抽成一个 `Notifier = Arc<dyn Fn(&Snapshot)>`，而不是让各处直接持有 `AppHandle`。原因是 `AppHandle` 在单测里造不出来——有了这层间接，`server.rs` 可以用一个只记数的闭包当通知器，起一个真实监听端口跑完整的 HTTP 层测试，覆盖鉴权、路由、状态码、聚合结果。这个抽象不是为未来预留的，它当场就换来了 16 个能跑的集成测试。

**关于 CLI 的 crate 组织**：CLI 用 `#[path = "../config.rs"] mod config;` 直接包含源码，而不是 `use signalhub_lib::config`——后者会把整个 Tauri 拖进这个本该很小的二进制（实测 3.1MB 且不链接 Tauri）。同样的原因，它不校验状态名，只把状态字符串原样转发给服务端，避免出现两张别名表。将来若构建时间或体积成为问题，再抽成 cargo workspace 里的 `crates/signalhub-cli`。

**state.rs 是关键**：它是纯逻辑、无 I/O、时间可注入（`apply(now, …)`），因此可以完整单测而不需要跑起 Tauri 或等待真实时间流逝。整个仓库的单测：`cargo test` 跑出 **lib 231 + CLI 161**，外加前端 `npm test` 的 11 条（CLI 通过 `#[path]` 复用了 config / hooks / state 三个模块，所以两边有一部分是同一批用例）。

> 这个数字**只在写下时准**——每个功能提交都会加几条。看个量级就好，别拿它当断言；要准数就直接跑上面那两条命令。

## 6. 路径约定

```
~/.signalhub/
├─ port          实际监听端口（app 启动时写入）
├─ token         32 字节随机 token，权限 0600
├─ lang          app 解析出来的界面语言，供 CLI 挑自己的文案（见 §3.20）
├─ config.json   用户设置（圆点大小、是否置顶）
├─ stats.json    每日状态时长（按本地日期分桶，保留最近 30 天）
├─ hooks.log     hook 调用日志 + 崩溃记录（每次调用一行，UTC 时间戳，512KB 轮转）
├─ lamp-positions.json  每盏灯窗拖到哪儿了（见 §3.7 的多灯布局）
├─ outbound.json 最近几次出站结果（重启后界面上还看得到「上次发成功没有」）
└─ pending.jsonl 可选：app 未运行时的暂存事件，启动时回放（v1.1）
```

**这里的每个文件都走原子写**（`config::atomic_write`）：先写同目录的临时文件、再 `rename` 过去。理由很直接 —— `load_settings` 的失败兜底是**静默退回全部默认值**，非原子写写到一半崩溃（断电、强杀、磁盘满）留下的残缺 JSON 会让用户调了一小时的颜色、钩子、分组一声不响地全没。智能体自己的配置文件（`~/.claude/settings.json` 之类）也走同一个函数。

三个要点，见那个函数的注释：临时文件**必须和目标同目录**（跨文件系统 `rename` 会 `EXDEV`）；私密文件的权限在**建临时文件时**就设好，不留「已是正式文件但还没收紧权限」的窗口；目标是**符号链接**时写到它指向的地方 —— 用 dotfiles 管配置的人常把 `~/.claude/settings.json` 做成链接，`rename` 会把链接本身替换掉，用户的仓库就此断了还不报错。

主目录只从环境变量解析（`HOME`，Windows 上是 `USERPROFILE`），**不引入 `dirs` 之类的依赖**——CLI 是独立二进制，少一棵依赖树是实打实的收益。代价是两者都缺失时会明确报错而不是静默写到别处，这是可接受的。app 由终端或 launchd 启动时两者必有其一。

## 7. 平台注意事项

**下表的每一条都是查过依赖源码或实测过的**，不是「大概是吧」；真没验证的会明说。

| 事项 | 说明 |
|---|---|
| macOS 全屏 Space 无法覆盖 | `alwaysOnTop` 不能浮在别的应用的全屏 Space 之上，需要更高的 NSWindow level 和私有 API。所有同类工具的共同限制，**不要在 v1 承诺**。 |
| Windows 透明窗口白闪 | 已按官方建议设 `noRedirectionBitmap`（对应 `WS_EX_NOREDIRECTIONBITMAP`）。不设的话，webview 内容渲染出来之前会闪一下白底。 |
| Windows 上 `set_visible_on_all_workspaces` 是**静默 no-op** | `tao` 里那个方法只在 macOS / Linux 上实现，Windows 上返回 `Ok` 但什么都不做。所以 `setup` 里那个 `?` 不会让启动失败 —— 但它也不提供任何效果。 |
| **Windows 不给托盘图标反色** | 模板图（RGB 全 0、只有 alpha）在 macOS 上由系统按菜单栏明暗着色；非 macOS 上 `is_template` 参数是被直接丢掉的（`tray-icon` 里那个方法连图都不收），托盘实现把原始位图交给系统、没有任何主题逻辑。所以那张图在 Windows 上就是**纯黑**，深色任务栏上等于看不见。`tray::monochrome_glyph()` 因此在非 macOS 上把三点图涂成中性灰。 |
| Windows 上 PATH 里的可执行文件带 `.exe` | `Path::is_file()` **不做 PATHEXT 展开**，只找 `signalhub` 会永远找不到 `signalhub.exe`。所以查命令时要把 `.exe` 也试一遍（见 `hooks::candidates`）。 |
| **Windows 只出 NSIS（`-setup.exe`），不出 MSI** | `bundle.targets` 原本是 `"all"`，会同时出 WiX 的 `.msi` 和 NSIS 的 `-setup.exe`。但 `light.exe` 生成 msi 那一步在这套配置上失败了：`failed to bundle project: failed to run light.exe`，而 Tauri **把 light.exe 自己的 stderr 吞了**，看不出原因（candle 那一步是过的，所以不是 `.wxs` 本身解析不了）。`tauri.windows.conf.json` 因此把 targets 收成 `["nsis"]` —— 那份本来就是 Tauri 推荐的 Windows 安装器。**这是绕开，不是修好**：根因没查出来，只是把出问题的那条路关掉了；想要 msi 的话得另做一轮诊断（用 `--verbose` 重跑，或者把生成的 `main.wxs` 打出来手动跑 light）。 |
| Linux/Wayland | 透明窗口与 `shadow` 官方标注不支持。Linux 是硬需求时优先 X11。 |
| `set_shadow` | Linux 不支持；Windows 上对无边框窗口加的是 1px 白边（Win11 上是圆角）。 |
| `set_skip_taskbar` | macOS 不支持（用 Accessory 策略替代）；Windows 上有效。 |
| 首次运行防火墙弹窗 | 绑定 127.0.0.1 通常不弹，但仍可能提示。 |
| **灯球在 Windows 上能不能拖** | **未验证**。窗口配了 `focus: false`（Windows 上走 `SW_SHOWNOACTIVATE`，即不可激活），而拖拽是 JS 调 `startDragging()`（Windows 实现是发 `WM_NCLBUTTONDOWN` / `HTCAPTION`）。理论上可行，但没有真机试过 —— 而拖动是这个工具的基本操作，所以这条值得优先验。 |

### 7.1 跨平台这件事靠 CI 兜着，不靠自觉

平台相关的代码（`#[cfg(windows)]`、`#[cfg(unix)]`）**在开发机上根本编不进去**。macOS 上 `cargo test` 全绿，完全不能说明 Windows 上能编过 —— 上面那张表里的两个 Windows 缺陷（托盘纯黑、`.exe` 没试）都是这么漏掉的，而且第二个是**编译期就该发现**的那一类。

所以 `.github/workflows/ci.yml` 在 macOS / Windows / Linux 三个 runner 上各跑一遍 `cargo test`、`cargo clippy`、前端构建和前端单测。Linux 那个 job 要装 webkit2gtk / gtk，否则连 `cargo test` 都链不过。

**clippy 也用 `-D warnings` 跑，而且必须三平台都跑** —— 理由和 `cargo test` 一字不差。加它之前先清了那 4 处积压的警告（两个手写的 `Default` 改成 `#[default]`、一处文档注释后面多空了一行、一处测试里的字段赋值），所以基线是 0，任何新警告立刻变红。

**这条 CI 已经真的救过一次命**：`shortcut_label` 在非 macOS 上把 Super 写成了 `Alt+Super+S`，而那条测试当初是 `if cfg!(target_os = "macos")` 分叉的 —— 开发机是 macOS，永远走不到出问题的那一支。Linux 和 Windows 两个 job 连红了三次才被发现。修的时候把平台写法抽成了 `KeyStyle` 枚举 + `shortcut_label_for(mods, key, style)`，**两套写法在任何平台上都能被测到**，这个 bug 类别才算关上。

**前端也终于有单测了**（vitest，`npm test`）。目前只覆盖**与 Rust / CSS 有「必须逐字一致」契约**的那几个纯函数：

- `lib/lampSort.ts` —— 置顶排序，和 Rust 的 `visible_groups` 是同一条规则的两份实现。两边算出的可见牌不一致，窗口高度就对不上（多算一块是底下空一条，少算一块是最后一块被切掉）。它原本埋在 `SignalLamp.tsx` 里，摘出来单独放一个文件就是为了让它有地方被测。
- `lib/lampStyle.ts` —— 形状特判（全局是圆时 permission / error 画圆角方）和动画时长。时长是从 `lamp.css` **抄**过来的，所以那组断言同时也是「两份抄本还一致吗」的警报。

这类逻辑**类型系统盯不住**，只能靠断言。测试用的设置来自 `useSettings.ts` 导出的 `DEFAULTS`，不手抄 —— 抄一份会随着真值演进悄悄漂移。

## 9. 依赖清单

```toml
# src-tauri/Cargo.toml —— 已实现部分
[dependencies]
tauri = { version = "2", features = ["tray-icon"] }
axum = "0.8"                  # 0.8 的路径参数写作 /{name}，0.7 是 /:name
serde = { version = "1", features = ["derive"] }
serde_json = "1"
tokio = { version = "1", features = ["time", "net", "io-util", "macros", "rt-multi-thread"] }
getrandom = "0.3"             # 已在 Tauri 依赖树里，复用版本即免一次编译；用于生成 token
ureq = { version = "3", default-features = false, features = ["rustls"] }
#   ↑ CLI 连本机明文端口用不上 TLS，但 app 侧的出站 webhook 目标
#     （ntfy / Slack）都是 HTTPS，所以必须带 rustls
tauri-plugin-window-state = "2"   # 只用来记窗口位置，见 §3.12
tauri-plugin-notification = "2"   # 需要你注意时弹通知，见 §3.8
tauri-plugin-single-instance = "2"  # 多开会抢端口和状态文件，见 §3.15
tauri-plugin-autostart = "2"
tauri-plugin-global-shortcut = "2"  # 点击穿透的逃生通道，见 §3.15
```

几点取舍：

- **锁用 `std::sync::Mutex` 而不是 `tokio::sync::Mutex`。** 所有临界区都是纯内存操作、不跨 `await`，同步锁更简单也让 Tauri 命令能保持同步函数签名。将来若临界区里出现 I/O，必须换成异步锁。
- **依赖尽量挑树里已有的版本**，避免同一 crate 出现两个版本、白付一次编译。加依赖前先 `grep Cargo.lock` 看一眼是划算的习惯。
- **`dirs` 一度选了 7.x，后来去掉了**：它拖进 `dirs-sys` → `option-ext`，而主目录解析用环境变量 8 行就够了。CLI 的依赖树越小越好。
- **`ureq` 关掉默认的 `rustls`/`gzip`**：只连本机明文端口，用不上。

Tauri 已内置 tokio，`tauri::async_runtime::spawn` 可直接用，无需自建 runtime。

## 11. hook 对接的已核实结论与残留风险

以下结论对着 **官方文档 https://code.claude.com/docs/en/hooks** 和**本机安装的 Claude Code 2.1.296** 双向核实过：文档里的每个事件名（含 `PermissionRequest`、`StopFailure`、`PostToolUseFailure`、`TeammateIdle`、`PostCompact`）以及 `asyncRewake`、`disableAllHooks`、`statusMessage`、`hookSpecificOutput`、`agent_needs_input`、`notification_type`、`stop_hook_active` 等字段，都在 2.1.296 的二进制里存在。细节见 [api.md §4](./api.md#4-智能体接入)。

1. **Claude Code 有 33 个 hook 事件**，名字和大小写以该页面的事件表为准。其中 `PermissionRequest`（工具调用需要权限决策时触发）是「需要授权」的主信号，`Notification` 的 `permission_prompt` 是触发更晚的回落路径。映射表和**明确忽略**的事件清单见 api.md §4.2——把忽略项写清楚同样重要，因为 `TaskCreated`/`FileChanged` 这类事件频繁且与「一轮工作」无关，误用会让灯球乱闪。
2. **`"async": true` 是 `type: "command"` 独有字段**，且异步 hook **不受 `timeout` 约束**、**不能做决策**、**stdout 输出畸形 JSON 会崩溃会话**（v2.1.202 之前）。因此 CLI 必须自己限制 HTTP 超时，且 hook 模式下 stdout 必须为空。
3. **Codex 与 Cursor 都有 hook 系统**，字段与 Claude Code 大致同构（Codex 是 PascalCase + `session_id`，Cursor 是 camelCase + `conversation_id`），**不需要日志监听**。三家的配置路径、事件名、字段差异见 api.md §4.6 / §4.7。

仍然残留的风险：

- 事件处于活跃演进中，我们核实的是 2.1.296 这一个版本。映射表是 `match` 语句，将来加分支的成本很低；不需要为了「未来可能有新事件」预先设计抽象。
- Codex 的 `PermissionRequest` 输出 JSON 的确切键名只在解析器里见过（`decision`，未能确认是否为 `permissionDecision`）。我们不上报决策，所以不影响。
- Cursor 没有可直接映射的「需要授权」事件（它的授权是靠 hook 返回 `permission: allow|deny|ask` 实现的，上报型 hook 不返回该字段）。这是 Cursor 侧的能力缺口，不要假装有。
- Codex 的 `SessionEnd` 默认超时只有 1 秒（上限 3 秒），且总是同步执行——这条路径上的 HTTP 调用必须极快，超时要设得比其它事件更短。

### 11.1 「更多智能体」为什么不是加 `match` 分支就能解决的

上面六家（Claude Code / Codex / Cursor / Gemini CLI / Goose，加命令行上报的 Pi Agent）都是**逐家核实过**的。想把「市面上常见的智能体」都加进来，直觉是「加几条 `match` 分支」—— 但加一家需要三样确切信息：**配置路径 + 事件名 + handler 形状**，而这三样各家都不同、也都在变。

猜测的代价不是「不生效」，而是**静默失效**：`hooks.rs` 顶部那三条安全底线里，第二条（「解析失败就中止，绝不覆盖」）防的正是拿一个猜的格式去写用户的配置文件。所以本项目立的标准是「对着官方文档**和**本机二进制双向核实过才写」—— `§11` 开头那句就是它。

**`signalhub run`（api.md §4.13）是绕开这个问题的另一条路**：不猜格式，改成**包一条命令**。任何跑在终端里的工具都能这么接，对方不需要任何 hook 支持。它换来的代价是**状态粒度粗**（只有 working / done / error，报不出「需要授权」）—— 但那比「猜一个格式、装上去了、不报错也不上报」好得多。

**这一节也记下了接不了的**：只活在 VS Code 侧边栏面板里的扩展（Cline / Roo Code / Continue 这类）没有可包的进程、也没有可写的 hook 配置 —— 通用的两条路对它都不适用。**不要为了「覆盖面」假装支持它们。**
